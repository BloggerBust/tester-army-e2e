`e2e mcp` gives a coding agent such as Claude Code, Codex, or Cursor a live
session on your app, on web, iOS, or Android. The agent sees the screen,
acts on it, and checks its work.

## Why it matters

| Task | Without `e2e mcp` | With `e2e mcp` |
| --- | --- | --- |
| Write a test | Guesses locators, runs, fails, guesses again | Writes the test as it walks the flow, from checked test lines and lines it ran with `run_code` |
| Change the UI | Done when it compiles | Opens the page and checks the result |
| Reproduce a bug | Guesses from the code | Follows the steps in the app |
| Fix a failing test | Clicks through the flow again | Runs the test and stops on the failure |
| Show a change in a PR | Describes it | Records a video |

The MCP server itself doesn't need a model. You only need one if you run a
test with an uncached agent step.

## Set it up

The [e2e plugin](/coding-agents) for Codex and Cursor includes the server
as `npx -y e2e@<version> mcp`, running the plugin's e2e release even when
the project has another version installed. In Claude Code (or without the
plugin), register it in your project. `e2e init` can write the config for
`.mcp.json` (Claude Code), `.cursor/mcp.json` (Cursor), and
`.codex/config.toml` (Codex). Install your project dependencies and launch
your MCP client in the project directory so `npx` (or `bunx`) picks up the
installed `e2e` version. To set it up by hand:

<Tabs>
  <Tab title="Claude Code">
    <CodeGroup>
    ```bash npm
    claude mcp add --scope project e2e -- npx e2e mcp
    ```

    ```bash pnpm
    claude mcp add --scope project e2e -- pnpm exec e2e mcp
    ```

    ```bash bun
    claude mcp add --scope project e2e -- bunx e2e mcp
    ```
    </CodeGroup>
  </Tab>
  <Tab title="Codex">
    Run `e2e init --yes --skills none --mcp .codex/config.toml` with the installed CLI,
    or add the entry below. Trust the project and start a new Codex session.
    `codex mcp list`, run in the project, shows the registration:

    ```toml title=".codex/config.toml"
    [mcp_servers.e2e]
    command = "npx"
    args = ["e2e", "mcp"]
    ```
  </Tab>
  <Tab title="Cursor">
    Add the server to `.cursor/mcp.json`. Other clients that read an
    `mcpServers` map take the same block.

    ```json title=".cursor/mcp.json"
    {
      "mcpServers": {
        "e2e": { "command": "npx", "args": ["e2e", "mcp"] }
      }
    }
    ```
  </Tab>
  <Tab title="OpenCode">
    Add the server to `opencode.json` in the project. `opencode mcp list`,
    run in the project, shows it as connected:

    ```json title="opencode.json"
    {
      "$schema": "https://opencode.ai/config.json",
      "mcp": {
        "e2e": { "type": "local", "command": ["npx", "e2e", "mcp"] }
      }
    }
    ```
  </Tab>
</Tabs>

If your target defines an `app.command`, the session starts your app and
prints its URL and port. The config reads the MCP server's environment, not
your agent's shell.

## Try it without a config

If the directory doesn't have an `e2e.config.ts` yet, the agent can still
open a session by naming the engine directly:

```txt
open_session {engine: "@e2e-dev/web", app: {url: "http://localhost:3000"}}
```

`e2e run` still requires a config file. For engine options, device providers,
and installing engines, see [Without a config](/reference/mcp#without-a-config).

## Ask the agent

- "Add a Remember me checkbox to the login form. Check it in the app with e2e."
- "Write a test for checkout while you walk it in the app."
- "Reproduce issue #123 in the app and record a video."

Add "headed" to watch a local browser or simulator.

## How it writes a test line

Each action in a session answers with the test line that repeats it. The
line's locator matched that control alone on the live screen:

```text wrap
Tapped #n31.
Test line: await screen.getByRole("button", "Sign in").tap();
```

The agent copies the lines it needs into the test as it walks the flow.
`test_lines` returns every line so far, in order, with guidance matching
whether the session is a fresh recording, a resumed test, or an attached
held test. See [`test_lines`](/reference/mcp#test_lines) for how a line is built.

## How it checks a locator

For a line no action printed, such as an assertion, the agent tries the
locator in the session first. A wrong guess fails there, not in a test run:

```text wrap
0 nodes match getByLabel("Email").
A test using this locator would fail with LOCATOR_NOT_FOUND. ...

1 node matches getByRole("button", name: "Sign in").
Use: screen.getByRole("button", "Sign in")
```

## How it runs code

The agent runs JavaScript in the open session with `run_code`: a loop over a
list, a value read and computed on, an assertion no action printed. One call
replaces many single actions:

```js
const rows = screen.getByRole('listitem');
const names = await rows.allTextContents();
await rows.nth(names.findIndex((name) => name.includes('Mug'))).getByRole('button', 'Add').tap();
await expect(screen.getByRole('status')).toHaveText('1 item in cart');
return names.length;
```

The lines that pass join the `test_lines` draft. A wrong line fails in
seconds, without a test run:

```text wrap
Failed: LOCATOR_NOT_FOUND: locator matched no nodes within getByRole("button", name: "Save")
Test lines: 2, 1 failed.
1. await screen.getByLabel('Full name').fill('Grace Hopper');
2. failed: await screen.getByRole('button', 'Save').tap();
   LOCATOR_NOT_FOUND: locator matched no nodes within getByRole("button", name: "Save")
```

The code is ordinary JavaScript on the objects a test body gets. See
[`run_code`](/reference/mcp#run_code).

## Fix a failing test

`open_session {test: "tests/checkout.e2e.ts:12"}` runs one test in the
session and stops on the screen where it failed. The agent reads the
failure, checks the screen, and edits the test:

```text wrap
Test "a member checks out" (tests/checkout.e2e.ts:12) failed after 30.25s; 8 steps ran.
LOCATOR_NOT_FOUND: locator matched no nodes within getByLabel("Name")
At tests/checkout.e2e.ts:20:3
On screen, closest to what the locator asked for:
  #n32 textbox "Full name"
```

Each action from that screen prints its
[test line](#how-it-writes-a-test-line), and `run_code` runs a fixed line
there. The agent puts those lines in the test in place of the one that
failed.

To rerun the edited test, the agent closes the session and opens a new one
with the same `test`. Agent steps replay from the cache as in `e2e run`.
See [Running a test](/reference/mcp#running-a-test) for what runs and the
limits.

## Run tests next to a session

An interactive session doesn't write test reports, and only tests launched
via `open_session {test}` use the replay cache. Your agent can keep a session
open while running suites with `e2e run` and jump straight to any failing
screen afterward.

On web, whether `e2e run` can run alongside an open session depends on your
`app` config:

| Target's `app` | Running `e2e run` while a session is open |
| --- | --- |
| No `command` | Both share the server you started yourself. |
| `url` on port [`0`](/web#let-the-runner-pick-the-port) | Each starts its own server instance (note that servers like `next dev` don't allow two instances in the same directory). |
| `command` with [`reuseExisting: true`](/web#starting-your-app) | The test run reuses the session's server. Closing the session stops that server. |
| `command` on a fixed port without `reuseExisting` | Fails because the port is already in use. |

In CI, e2e ignores `reuseExisting`, so a fixed port behaves like the last
row. Close the session before running tests if they would collide on the port
or mobile device.

## Run several agents

Each agent, subagents included, opens its own session with its own browser
or device, up to four by default. On mobile, give each session its own
target.

## Secrets

`type_secret`, or a `fill` in `run_code`, fills a secret without showing it
to the agent. Screenshots mask secure fields only, so a secret the app
shows anywhere else is in them.

<Warning>
Videos from `start_recording` are not masked.
</Warning>
