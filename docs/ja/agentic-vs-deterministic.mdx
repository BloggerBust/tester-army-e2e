---
title: エージェント型と決定論的テスト
description: エンドツーエンドテストで、エージェント型と決定論的な操作・アサーションを使い分けます。
---

エージェント型テストでは、ユーザーの意図と期待する結果を自然言語で記述します。
エージェントが操作を選び、画面が期待を満たすかを判定します。
テストは結果に集中でき、UI の変更に合わせてセレクターを保守する必要がありません。

決定論的テストでは、操作とチェックをコードで指定します。
どちらもユーザーが得る結果をテストでき、e2e では 1 つのテストに組み合わせて使えます。

## エージェント型テストはいつ使う？

UI の変更のたびにテストのセレクターを更新している場合は、エージェント型テストを使ってください。
フォームの入力と送信など、操作は多くても平易な言葉で説明しやすいフローにも適しています。

`agent.act` には、割引コードの適用など、ユーザーの意図を記述します。
エージェントが、使うコントロールと操作を判断します。
`agent.assert` は、合計への割引適用など、指定した結果が画面に表示されているかを確認します。

たとえば、`app` と `agent` フィクスチャを使うテストでは次のように書きます。

```ts
await app.open('/checkout');
await agent.act('apply the discount code SUMMER');
await agent.assert('the checkout shows code SUMMER applied with a 10% discount');
```

割引コードの入力欄、適用ボタン、結果を表示する要素を指定する必要はありません。

CSS クラスやテスト ID に結び付いたテストは、それらの識別子が変わると修正が必要です。
エージェントなら、ボタンが移動したりフォームのデザインが変わったりしても、
画面の情報からユーザーの意図を実行できます。

エージェントはアプリに適応するため、エージェント型テストでは、固定のテストデータを投入せずに
ステージングや本番環境の実データで監視できます。
モデルには画面の内容が渡されるので、テストアカウントを使ってください。
[セキュリティ](/security) を参照してください。

複雑な操作の流れは、平易な言葉で一連のゴールとして記述します。
各ゴールは 1 つの結果に絞り、確認してから次に進みます。
ステップへの分け方は [ゴール](/core-concepts#goals) を参照してください。

## エージェント型アサーションはいつ使う？

複数の文言やレイアウトが同じ要件を満たす場合は、エージェント型アサーションが便利です。
たとえば、バリデーションメッセージが特定の文と完全一致しなくても、
何が問題かを説明できていればよい場合です。

```ts
await agent.assert('the error message explains that an email address is required');
```

視覚的なチェックには `vision: true` を追加して、モデルにスクリーンショットも渡します。

```ts
await agent.assert('the chart trends upward', { vision: true });
```

`agent.assert` は現在の画面を調べ、文が偽の場合や根拠が不十分な場合に失敗します。
UI が期待する状態になるまで時間がかかる場合は、`agent.waitFor` を使います。
両メソッドについては [アサーション](/core-concepts#assertions) を参照してください。

## 決定論的テストはいつ使う？

使うコントロールがわかっている、短く安定したフローにはロケーターを使います。
次の割引テストのように、各フィールドとボタンをコードで指定します。

```ts
await app.open('/checkout');
await screen.getByLabel('Discount code').fill('SUMMER');
await screen.getByRole('button', 'Apply').tap();
await expect(screen.getByRole('status')).toHaveText('10% off');
```

これらの操作とチェックはモデルを呼び出しません。
ユーザーが認識できるコントロールを参照するように、ロールとラベルを優先してください。
決定論的テストでも、CSS クラスやテスト ID に依存する必要はありません。

期待する結果を正確な値、個数、状態で表せる場合は、決定論的アサーションを使います。
モデルの判断なしで確認できます。バリデーションメッセージの文言が決まっているなら、
`expect` でそのテキストをチェックします。

## エージェント型と決定論的テストを組み合わせる

操作とアサーションは別々に選びます。変わりやすい UI の操作はエージェントに任せ、
正確な値は `expect` で確認できます。

```ts
await agent.act('apply the discount code SUMMER');
await expect(screen.getByRole('status')).toHaveText('10% off');
```

ロケーターでフォームを入力・送信し、バリデーションメッセージが問題を説明できているかを
`agent.assert` で確認することもできます。

エージェントの適応は、記述したゴールに従います。曖昧な指示では、意図しない結果が許容される場合があります。
特定の経路が重要なら、ゴールに明記するか、その操作にロケーターを使ってください。
`agent.act` の後に `expect` を置くと、意図しない方法で達成されたゴールを検出できます。

モデルによる操作とアサーションには待ち時間とコストが加わり、誤りも起こり得ます。
[リプレイキャッシュ](/cache) は、記録した `agent.act` の操作をモデル呼び出しなしで繰り返せます。
アサーションはテストの実行ごとに再実行されます。
記録が一致しなくなった場合、strict キャッシュモードが有効でなければ、エージェントが変更後の UI に適応できます。
仕組みは [セルフヒーリングテスト](/self-healing) を参照してください。
