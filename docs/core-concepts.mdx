A test mixes three kinds of steps:

| Step | API | Calls a model? |
| --- | --- | --- |
| [Goal](#goals) | `agent.act` | Yes, unless replayed from [cache](/cache) |
| [Assertion](#assertions) | `agent.assert`, `agent.waitFor`, `agent.extract` | Yes |
| [Locator](#locators) | `screen` and `expect` | No |

If you use a [custom executor](/executors), `act` and `assert` don't need an
LLM either.

```ts title="tests/todos.e2e.ts"
import { describe, test, expect } from 'e2e';

describe('todos', () => {
  test('the Done filter shows only completed todos', async ({ app, agent, screen }) => {
    await app.open('/todos');
    await agent.act('add todos "Buy milk" and "Walk the dog"');
    await agent.act('complete "Buy milk"');
    await agent.waitFor('"Buy milk" is completed and "Walk the dog" is open');

    await screen.getByRole('tab', 'Done').tap();

    await expect(screen.getByTestId('todo')).toHaveCount(1);
    await agent.assert('the only todo listed is "Buy milk"');
  });
});
```

Each test checks one behavior with one goal: set up the starting state, act
toward that goal, then assert the result.

Name repeated locators and values with `const`, share setup with a hook or
fixture, and use a small helper or [page object](/page-object-model) when
several tests drive the same screen, keeping outcome checks visible in the
test. Keep short, single-use instructions inline (or name long ones with a
local `const`), and share recurring instructions in a TypeScript module with
`params` for test data.

Always `await` every `agent`, `screen`, and `expect.poll` call. If a test
exits with a step still running, e2e fails it.

## Goals

`agent.act` takes a natural-language instruction, performs the interactions
needed to reach the goal, and throws if it can't. Use the field and button
names shown on screen and specify the order when it matters (for example,
filling shipping info, picking a delivery option, and placing the order).

Start with one call for the behavior under test. Split at a meaningful
transition when the next step needs a known state (such as the payment
page of a long checkout), when a long flow risks `maxSteps` or
`maxModelCalls` budgets, or when a middle failure needs its own step
boundary. Explain why the split is needed and wait for the intermediate
screen state before continuing. Each call has its own
[budgets](/reference/agent#budgets) and can replay from its own recording.

```ts title="Complete one checkout across two screens"
test('places an order with a saved card', async ({ app, agent, screen }) => {
  await app.open('/checkout');

  // The saved card can load after the Payment heading appears.
  await agent.act('Fill the Shipping address with {address}, then choose Continue to payment.', {
    params: { address: '12 Market Street' },
  });
  await screen.getByRole('radio', 'Test card').waitFor();
  await agent.act('Select the saved Test card and choose Place order.');

  await expect(screen.getByText('Order confirmed')).toBeVisible();
});
```

- **Wait after setup, assert at the end.** When setup uses `agent.act`, end
  setup with a wait for the starting state, and check the final outcome in
  the assert block. Any later passing wait or check confirms earlier goals
  for the [replay cache](/cache#when-a-recording-is-written).
- **Match the UI's wording.** Use the labels and terms that actually appear
  on screen.
- **Pass data in `params`.** For passwords or tokens, pass a `Secret` handle
  so the model never sees the plaintext value. See
  [Authentication](/authentication).
- **Wrap dynamic values in `unique()`.** Timestamps or fresh emails change on
  every run; wrapping them lets the [cache still replay](/cache#what-must-match):

```ts
import { unique } from 'e2e';

const email = `ada+${Date.now()}@example.test`;
await agent.act('sign up with email {email}', { params: { email: unique(email) } });
```

`agent.act` automatically grabs screenshots when the text tree isn't enough,
and on supported engines it can tap or type by coordinates. If a goal fails,
tighten the instruction or move shared domain terminology into the agent's
[`context`](/agents).

## Assertions

Agent assertions inspect the current screen independently. The model sees
your statement, a redacted snapshot of the screen, the current URL or
location, and the agent's `context`, not earlier steps or `agent.act`
summaries.

- **`agent.assert`** checks the screen right now and fails if the statement
  is false or there isn't enough evidence.
- **`agent.waitFor`** waits until a condition becomes true, calling the model
  only when the screen or location changes.
- **`agent.extract`** pulls structured data from the screen into any
  [Standard Schema](https://standardschema.dev) type like Zod.

```ts
import { expect } from 'e2e';
import { z } from 'zod';

await agent.assert('the dashboard shows a trial badge');
await agent.waitFor('a download link appears', { timeout: 120_000 });
await agent.assert('the chart trends upward', { vision: true });

const data = await agent.extract('every todo title', {
  schema: z.object({ titles: z.array(z.string()) }),
});
expect(data.titles).toContain('Buy milk');
```

When checking text generated by the model, assert on meaning rather than
exact wording. When exact wording matters, use a [locator](#locators).

For visual checks like charts or layout alignment, pass `vision: true` (or
`vision: 'only'` to judge the screenshot alone). Keep in mind that images add
input tokens. See [vision options](/reference/agent#vision).

## Locators

Locators target known controls directly with no model call. Use them whenever
you know the exact interaction or value you want to check.

```ts
// Role and name first, label second, test ID last.
await screen.getByRole('button', 'Sign in').tap();
await screen.getByLabel('Email').fill('ada@example.test');

// Scope into a row.
const row = screen.getByRole('listitem').filter({ hasText: 'Design review' });
await row.getByRole('button', 'Archive').tap();

// Gestures and coordinates.
await screen.swipe({ direction: 'up' });
await screen.getByRole('image', 'Seat map').tap({ position: { x: 120, y: 48 } });

// Assertions retry until they pass or time out.
await expect(screen.getByRole('status')).toHaveText('2 remaining');
```

- Single-element actions and assertions fail if a locator matches more than
  one control. Narrow it with `.filter()`, `.first()`, or `.nth()`.
- Direct reads like `textContent()` wait for the element to appear, then read
  it once without retrying for a specific value.

See the [screen reference](/reference/screen) and the
[expect reference](/reference/expect#locator-matchers). For routes, cookies,
dialogs, and downloads, see [Working with the browser](/browser).

## Organize tests

```ts
import { beforeEach, describe, test } from 'e2e';

describe('billing', { tags: ['billing'] }, () => {
  beforeEach(async ({ app }) => { await app.open('/billing'); });

  test('upgrades', { retries: 2, timeout: 60_000 }, async ({ agent }) => {
    await agent.act('upgrade to Pro');
  });
});

test('needs two organizations', async ({ app }) => {
  test.skip((await countOrganizations()) < 2, 'nothing to switch to');
  await app.open('/organizations');
});
```

- **Start near the screen you're testing.** Each test runs in its own
  attempt, so skip repetitive navigation by creating data in fixtures,
  restoring a [saved session](/authentication), opening a direct URL, or
  using a mobile [deep link](/mobile#the-device-fixture). (Browsers start a
  fresh context per attempt; mobile devices keep app state until you call
  `app.open()` or `app.clearState()`.)
- **Skip conditionally** with `test.skip(condition, reason)`.
- **Chain dependent tests** with `{ serial: true }` on a `describe` block so
  they run in order on one worker and retry together.
- **Share setup and cleanup** with `test.extend`. See
  [Writing fixtures](/fixtures).
- **Get typed platform fixtures** by importing `test` from `@e2e-dev/web`,
  `@e2e-dev/mobile`, or `@e2e-dev/desktop` for `browser`, `device`, or
  `desktop`.

The [test reference](/reference/test) shows all options.

## Run one test

<CodeGroup>
```bash npm
npx e2e run tests/signup.e2e.ts:12   # the test at line 12
npx e2e run --grep checkout          # tests with a matching title
npx e2e run --target web             # one target
```

```bash pnpm
pnpm exec e2e run tests/signup.e2e.ts:12   # the test at line 12
pnpm exec e2e run --grep checkout          # tests with a matching title
pnpm exec e2e run --target web             # one target
```

```bash bun
bunx e2e run tests/signup.e2e.ts:12   # the test at line 12
bunx e2e run --grep checkout          # tests with a matching title
bunx e2e run --target web             # one target
```
</CodeGroup>

The [CLI reference](/reference/cli#e2e-run) shows all flags.
