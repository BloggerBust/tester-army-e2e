A coding agent such as Claude Code, Codex, or Cursor can write, run, and
debug e2e tests. It learns e2e from the skill, uses the app through the
`e2e mcp` server, and reads the trace page of a failed test.

## Install the skill

<CodeGroup>
```bash npm
npx e2e init
```

```bash pnpm
pnpm dlx e2e init
```

```bash bun
bunx e2e init
```
</CodeGroup>

| Path | Used by |
| --- | --- |
| `.agents/skills/e2e/` | Codex, Cursor, OpenCode, and other agents that read `.agents/skills` |
| `.claude/skills/e2e/` | Claude Code. A symlink to `.agents/skills/e2e/` when both are installed. |

`init` drops `SKILL.md` and topic references into those folders, and
[`e2e upgrade`](/reference/cli#e2e-upgrade) keeps them up to date. Without
`init`, install the skill with `npx skills add e2e-inc/e2e`, or print it from
the installed package with `npx e2e guide [topic]`. The plugin below installs
all three e2e skills globally across projects.

`init` also adds a short pointer to `AGENTS.md` (and `CLAUDE.md` with the
`.claude/skills` path), creating the file if needed, so prompts like "add a
test for checkout" automatically pick up the skill. If you install the skill
another way, add this line yourself:

```md title="AGENTS.md"
End-to-end tests use e2e; read .agents/skills/e2e/SKILL.md before writing or running one.
```

The `e2e` package also ships these docs offline in `node_modules/e2e/docs/`
for agents to read locally.

<Accordion title="Install the Claude Code, Codex, or Cursor plugin">

The e2e repository is a plugin marketplace for Claude Code and Codex, and
for Grok Build, which reads the Claude Code files. Cursor loads the plugin
from its local plugins folder:

<CodeGroup>
```bash Claude
claude plugin marketplace add e2e-inc/e2e
claude plugin install e2e@e2e
```

```bash Codex
codex plugin marketplace add e2e-inc/e2e
codex plugin add e2e@e2e
```

```bash Cursor
repo=$(mktemp -d)
git clone --depth 1 https://github.com/e2e-inc/e2e "$repo"
mkdir -p ~/.cursor/plugins/local
rm -rf ~/.cursor/plugins/local/e2e
cp -R "$repo/plugins/e2e" ~/.cursor/plugins/local/
```
</CodeGroup>

Start a new session. In Cursor, run **Developer: Reload Window**. On Cursor
Teams and Enterprise, local plugins need the admin setting **Allow Local
Plugin Imports**, or an admin imports `e2e-inc/e2e` as a team
marketplace. The plugin adds the
`e2e`, `create-verification-skill`, and `migrate-to-e2e` skills, not the npm
package. In Codex and Cursor it also adds the [MCP server](/mcp-server); in
Claude Code and Grok Build, register it in the project. Invoke the other two under the plugin's
name, `/e2e:<skill>` in Claude Code and `$e2e:<skill>` in Codex, and as
`/<skill>` in Cursor.

The plugin's version follows e2e releases. To update it, run these and
start a new session. In Cursor, run the commands above again.

<CodeGroup>
```bash Claude
claude plugin marketplace update e2e
claude plugin update e2e@e2e
```

```bash Codex
codex plugin marketplace upgrade e2e
```
</CodeGroup>

</Accordion>

<Accordion title="Let pnpm link the skill">

pnpm 12.11 and later can link the skill from the installed `e2e` package
instead of the copy `init` writes. Until you choose, every `pnpm install`
lists `e2e skills` as awaiting approval. Choose in `pnpm-workspace.yaml`
at the workspace root, where pnpm links skills:

- **Keep the copy.** Set `skills: false`. The approval line goes away.
- **Let pnpm link it.** Use pnpm 12.18 or later: older versions name the
  link `pnpm-e2e-e2e`, not the `e2e` that `AGENTS.md` names. Delete
  `.agents/skills/e2e` and `.claude/skills/e2e`, then set `skills: true` or
  run `pnpm approve`. Each install links the skill into the root's skill
  folders and adds the link to their `.gitignore`, so the skill follows
  every `e2e` upgrade. Before the first install the skill is missing: an
  agent that reads a fresh clone finds nothing at that path.

```yaml title="pnpm-workspace.yaml"
permissions:
  e2e:
    skills: true
```

When a copy is still there, pnpm links the skill beside it as
`pnpm-e2e-e2e`, and agents load two `e2e` skills. `init` and `upgrade` warn
about it: delete the copy, then run `pnpm install --force` to rename the
link to `e2e`. Neither command writes over pnpm's link, and `init` adds no
copy where pnpm links the skill, a workspace member included.

</Accordion>

## Let the agent use the app

`e2e mcp` gives the agent a live session on your app. It checks its
locators against the screen before it writes them, and checks its own UI
changes. `init` registers the server. See [MCP server](/mcp-server) for setup and
prompts.

## How an agent writes and runs a test

The skill tells your agent to read your config and an existing test first.
With `e2e mcp`, it walks through the flow in a live session and writes each
step as it goes. Each test checks one behavior: arrange the starting state,
act toward one goal, then verify the outcome at the end:

```ts title="tests/shop.e2e.ts"
import { test, expect } from 'e2e';

test('filters the shop to items under $20', { session: 'customer' }, async ({ app, agent, screen }) => {
  const results = screen.getByRole('status', 'Results');
  const products = screen.getByRole('list', 'Products').getByRole('listitem');
  await app.open('/shop');
  await results.waitFor();
  await products.filter({ hasText: 'Leather Backpack, $90' }).waitFor();

  await agent.act('show only items under $20');

  await expect(results).toHaveText('2 items under $20');
  await expect(products).toHaveText(['Canvas Tote, $14', 'Steel Bottle, $18']);
});
```

- **One behavior and one [goal](/core-concepts#goals) per test.** Give
  `agent.act` the specific steps it needs to reach that goal. Split the
  path into calls when a later step needs a known screen state, when a
  long flow risks `maxSteps` or `maxModelCalls` budgets, or when a middle
  failure needs its own step boundary. Explain the split and wait for the
  intermediate screen state before continuing. Check the outcome at the end
  to verify the behavior and confirm the
  [recording](/cache#when-a-recording-is-written).
- **Named locators.** A locator the test uses twice, like `results`, is a
  `const`, so a renamed control is one edit.
- **No sleeps.** Locators poll, actions wait for their target, and `expect`
  retries until its timeout.
- **Give each user a separate session.** A [setup test](/authentication)
  signs in with `credentials.user(name)` and saves the primary user's
  session. For a flow like chat, [open a second session](/core#open-a-host-inside-a-test)
  and check the result in the recipient's session. Never write a password or
  other secret in a test: declare runner credentials in configuration and pass
  a second host's secrets through `launch({ secrets })`.

While iterating, the agent runs just the test it's editing (by line number)
with `--action-timeout 5000` so a wrong locator fails in 5 seconds instead of
30:

<CodeGroup>
```bash npm
npx e2e run tests/checkout.e2e.ts:3 --action-timeout 5000
```

```bash pnpm
pnpm exec e2e run tests/checkout.e2e.ts:3 --action-timeout 5000
```

```bash bun
bunx e2e run tests/checkout.e2e.ts:3 --action-timeout 5000
```
</CodeGroup>

The agent leaves the replay cache on so passing goals replay without calling
a model, and turns retries off (since retries run every goal live). Once the
test passes, it drops `--action-timeout` and runs it once with `--no-cache`
to make sure the live agent still completes every goal. See
[Rerun a test while you fix it](/cache#rerun-a-test-while-you-fix-it).

## How an agent reads a failure

By default ([`trace`](/reference/config#trace)), e2e writes a `trace.md` file
under `.e2e/results/` for every failed, timed-out, interrupted, or flaky
test. The terminal prints the path right under the failure
(`❯ trace .e2e/results/<test>/trace.md`).

Your coding agent reads `trace.md` rather than raw `report.json`. It
includes the failing line, every step's target and outcome, console errors,
failed network requests, the agent's last turns, and the screen at failure.
If the agent needs to check a screen that isn't in the trace, it opens that
URL directly in an MCP session instead of re-walking the flow from scratch.

To inspect individual model calls, pass `--ai-trace --no-cache` and read the
output with [unbox-ai](/debugging#agent-steps). Don't paste the raw
`ai-trace.json` into an agent's context, since it repeats prompts across
turns and can grow to several megabytes.

## Generate a verification skill for your app

The `e2e` skill teaches the framework, not your app. The
`create-verification-skill` skill generates a project-local
`.agents/skills/verify-<app>/` skill tailored to your app and tests it once
before finishing.

<CodeGroup>
```bash npm
npx skills add e2e-inc/e2e --skill create-verification-skill
```

```bash pnpm
pnpm dlx skills add e2e-inc/e2e --skill create-verification-skill
```

```bash bun
bunx skills add e2e-inc/e2e --skill create-verification-skill
```
</CodeGroup>

Then ask the agent for `/create-verification-skill`.

<Accordion title="What the generated skill holds">
- Launch and doctor commands from your config.
- The two ways to drive the app: a live `e2e mcp` session and a test.
- The evidence a proof keeps.
- A feature map with one `e2e explore` charter for each feature, so a
  [bug bash](/bug-bash) fans out from the map.

The generated skill says only what is true of your app and links to the e2e
skill for the rest. It is based on
[create-verification-skill](https://github.com/cursor/plugins/tree/main/pstack/skills/create-verification-skill)
from poteto's pstack, with e2e in place of a hand-rolled harness.
</Accordion>

## Migrate an existing suite

The `migrate-to-e2e` skill moves a Playwright, Cypress, Selenium, Appium,
Detox, Maestro, or TesterArmy suite to e2e one slice per session. The old suite keeps
running beside the new tests, so you can stop after any session.

<CodeGroup>
```bash npm
npx skills add e2e-inc/e2e --skill migrate-to-e2e
```

```bash pnpm
pnpm dlx skills add e2e-inc/e2e --skill migrate-to-e2e
```

```bash bun
bunx skills add e2e-inc/e2e --skill migrate-to-e2e
```
</CodeGroup>

Then ask the agent for `/migrate-to-e2e`. It ports the slice you pick and
runs each ported test three times on every target. A `MIGRATION.md` file
records progress for the next session. Optionally, the agent plants a temporary bug
in the app, such as a wrong checkout total, and checks whether both
suites fail on it. The agent deletes an old test only when you confirm. It first reads the migration guide for your runner:
[Playwright](/migrate/playwright), [Cypress](/migrate/cypress),
[Selenium](/migrate/selenium), [Appium](/migrate/appium), [Detox](/migrate/detox),
[Maestro](/migrate/maestro), or [TesterArmy](/migrate/testerarmy).
