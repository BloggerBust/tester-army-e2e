`@e2e-dev/github` é um reporter que publica os resultados dos testes como um
comentário no pull request a partir do GitHub Actions e os escreve no resumo
do job. Uma reexecução atualiza o mesmo comentário.

## Configuração

<CodeGroup>
```bash npm
npm install --save-dev @e2e-dev/github
```

```bash pnpm
pnpm add -D @e2e-dev/github
```

```bash bun
bun add -d @e2e-dev/github
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { github } from '@e2e-dev/github';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  reporters: ['list', github()],
} satisfies E2EConfig;
```

Dê ao workflow a permissão `pull-requests: write`. Passe o `GITHUB_TOKEN` ao
step dos testes:

```yaml title=".github/workflows/e2e.yml"
permissions:
  contents: read
  pull-requests: write

jobs:
  e2e:
    steps:
      # ...checkout, install, browsers
      - name: Run e2e
        run: npx e2e run --reporter list,junit
        env:
          GITHUB_TOKEN: ${{ github.token }}
      - name: Upload artifacts
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
        with:
          name: e2e-artifacts
          path: .e2e/results
```

Faça upload dos artefatos também quando uma nova tentativa passa: os links de
evidências de cada falha abrem a seção Artifacts da execução. Mantenha
`path: .e2e/results` para que o download tenha os mesmos diretórios por teste
que o relatório.

Os links para o código-fonte partem do diretório mais próximo com `.git`
dentro de `GITHUB_WORKSPACE`. Um projeto abaixo dele, como
`packages/e2e-tests`, recebe links sob esse caminho. O `actions/checkout` com
um input `path` também funciona.

Erros no nível da execução, quando existem, vêm antes das falhas. A lista de
testes só tem uma coluna de agente quando a execução usou o agente.

Uma execução cujos [filtros de testes](/filters) deixaram testes de fora diz
isso no título, como `e2e: 7 passed, 35 left out by filters`, para que ela
nunca pareça a suíte inteira. Acima da lista de testes, uma linha indica a
mudança que os filtros avaliaram, como `12 files changed since abc1234`,
depois uma linha por filtro diz o que ele manteve, e uma tabela recolhida
lista cada teste que ele deixou de fora, com o motivo. Quando nenhum filtro
rodou, como quando nenhum arquivo mudou, uma linha diz por quê.

O reporter encurta um relatório grande para caber no limite de tamanho de um
comentário do GitHub. Texto do app que o GitHub transformaria em uma menção,
um link para uma issue ou uma URL aparece como código, então uma tela que
mostra `@someone` não notifica ninguém. O reporter embutido `markdown` escreve
o mesmo resumo em `.e2e/summary.md`.

## Reexecutando os testes que falharam

Uma reexecução com `--last-failed` atualiza o comentário como uma só execução
junto com a primeira rodada, cobrindo a suíte inteira:

```yaml
      - name: Run e2e
        run: npx e2e run || npx e2e run --last-failed
        env:
          GITHUB_TOKEN: ${{ github.token }}
```

| Primeira rodada | Reexecução | O comentário mostra |
| --- | --- | --- |
| falhou | passou | instável |
| falhou | falhou | falhou |
| foi interrompida | passou | passou |
| qualquer outro resultado | não rodou | o resultado da primeira rodada |

O comentário mantém as linhas de filtro e os testes deixados de fora da
primeira rodada. Uma segunda reexecução é incorporada do mesmo jeito, então os
resultados da primeira rodada continuam no comentário.

O comentário continua vermelho enquanto a reexecução tiver deixado de fora
algo que devia ter rodado: um teste que falhou, um teste que `--max-failures`
ou `--max-duration` deixou sem rodar, ou um `beforeAll` ou `afterAll` com
falha cujos testes outro filtro deixou de fora. Ele mostra ⏹️ quando a
reexecução deixou de fora um teste que a primeira rodada nunca terminou. O
código de saída da própria reexecução conta só o que ela rodou. As evidências
de cada tentativa apontam para os arquivos dela.

## Jobs em matriz

O reporter encontra o comentário dele pelo projeto, pelo workflow e pelo job,
que os jobs de uma matriz compartilham. Dê a cada entrada da matriz uma `key`
própria:

```ts
reporters: ['list', github({ key: process.env.MATRIX_BROWSER })],
```

Defina `MATRIX_BROWSER: ${{ matrix.browser }}` no `env` do step. A chave
aparece no título, como `e2e chromium: 77 passed`. Mantenha-a estável entre
execuções para que uma reexecução atualize o comentário existente.

## Explorações

Uma execução do [`e2e explore`](/explore) publica um comentário próprio, então
um job pode rodar os testes e depois explorar. Dê à exploração um `--output`
próprio, como `npx e2e explore --output .e2e-explore`, e faça upload desse
diretório também. Caso contrário, ela substitui os resultados da execução dos
testes, e os links de evidências no comentário dessa execução quebram.

## Quando nada é publicado

O reporter nunca muda o status nem o código de saída da execução. Quando não
consegue publicar, uma linha abaixo do resumo dá o motivo:

```
       GitHub  not posted: set GITHUB_TOKEN in the step's env (GITHUB_TOKEN: ${{ github.token }}); written to the job summary
```

| Situação | O que acontece |
| --- | --- |
| Fora do GitHub Actions | Nada é escrito. A linha diz isso. |
| Uma execução de `push`, `schedule` ou `workflow_dispatch` | O resumo do job é escrito. Não há pull request para comentar. |
| Nenhum `GITHUB_TOKEN` no `env` do step | O resumo do job é escrito. A linha mostra o que adicionar. O reporter também lê `GH_TOKEN`. |
| Um evento `pull_request` vindo de um fork | O token é somente leitura, então a publicação falha. A linha diz por quê. |
| Um evento `issue_comment` | Na conversa de um pull request, o comentário não tem links para o código-fonte, porque o commit do checkout está na branch padrão. |
| Falta `pull-requests: write` | A publicação falha, e o reporter nomeia a permissão. |
| Limite de taxa da API do GitHub | A publicação é interrompida e informa a limitação. Espere o reset do limite ou o `Retry-After` antes de rodar o job de novo. |

O reporter lê o token quando a execução termina, e o relatório não o inclui.
No GitHub Enterprise Server, o reporter usa `GITHUB_SERVER_URL` e
`GITHUB_API_URL`.
