`@e2e-dev/github` एक रिपोर्टर है। यह GitHub Actions से टेस्ट के नतीजे पुल
रिक्वेस्ट पर कमेंट में पोस्ट करता है, और उन्हें जॉब समरी में भी लिखता है।
दोबारा चलाने पर वही कमेंट अपडेट होता है।

## सेटअप

<CodeGroup>
```bash npm
npm install --save-dev @e2e-dev/github
```

```bash pnpm
pnpm add -D @e2e-dev/github
```

```bash bun
bun add -d @e2e-dev/github
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { github } from '@e2e-dev/github';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  reporters: ['list', github()],
} satisfies E2EConfig;
```

वर्कफ़्लो को `pull-requests: write` दें। टेस्ट वाले स्टेप को `GITHUB_TOKEN`
दें:

```yaml title=".github/workflows/e2e.yml"
permissions:
  contents: read
  pull-requests: write

jobs:
  e2e:
    steps:
      # ...checkout, install, browsers
      - name: Run e2e
        run: npx e2e run --reporter list,junit
        env:
          GITHUB_TOKEN: ${{ github.token }}
      - name: Upload artifacts
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
        with:
          name: e2e-artifacts
          path: .e2e/results
```

रीट्राई पास हो जाए, तब भी आर्टिफ़ैक्ट अपलोड करें। हर फ़ेलियर के सबूत वाले लिंक
रन का Artifacts सेक्शन खोलते हैं। `path: .e2e/results` ही रहने दें, ताकि
डाउनलोड में हर टेस्ट की वही डायरेक्टरी हों जो रिपोर्ट में हैं।

सोर्स लिंक `GITHUB_WORKSPACE` के अंदर `.git` वाली सबसे नज़दीकी डायरेक्टरी से
शुरू होते हैं। प्रोजेक्ट उसके नीचे हो, जैसे `packages/e2e-tests`, तो लिंक उसी
पाथ के अंदर बनते हैं। `path` इनपुट के साथ `actions/checkout` भी चलता है।

रन-लेवल एरर हों, तो वे फ़ेलियर से पहले आते हैं। टेस्ट लिस्ट में एजेंट वाला
कॉलम तभी होता है, जब रन ने एजेंट इस्तेमाल किया हो।

[टेस्ट फ़िल्टर](/filters) ने कुछ टेस्ट छोड़े हों, तो हेडलाइन में यह लिखा होता
है, जैसे `e2e: 7 passed, 35 left out by filters`। इसलिए यह कभी पूरे सूट का
नतीजा नहीं लगता। टेस्ट लिस्ट के ऊपर एक लाइन बताती है कि फ़िल्टर ने कौन-सा बदलाव
परखा, जैसे `12 files changed since abc1234`। फिर हर फ़िल्टर की एक लाइन बताती है
कि उसने क्या रखा। एक फ़ोल्ड की हुई टेबल हर छोड़े गए टेस्ट को वजह के साथ दिखाती
है। कोई फ़िल्टर नहीं चला, जैसे जब कोई फ़ाइल नहीं बदली, तो एक लाइन इसकी वजह
बताती है।

बड़ी रिपोर्ट को रिपोर्टर छोटा कर देता है, ताकि वह GitHub के कमेंट की लिमिट में
आ जाए। ऐप के जिस टेक्स्ट को GitHub मेंशन, इश्यू लिंक या URL में बदल देता, वह कोड
की तरह दिखता है। इसलिए जिस स्क्रीन पर `@someone` लिखा हो, उससे किसी को
नोटिफ़िकेशन नहीं जाता। बिल्ट-इन `markdown` रिपोर्टर यही समरी `.e2e/summary.md`
में लिखता है।

## फ़ेल हुए टेस्ट दोबारा चलाना

`--last-failed` वाला दोबारा रन कमेंट को पहले रन के साथ मिलाकर एक ही रन की तरह
अपडेट करता है, जिसमें पूरा सूट आता है:

```yaml
      - name: Run e2e
        run: npx e2e run || npx e2e run --last-failed
        env:
          GITHUB_TOKEN: ${{ github.token }}
```

| पहला रन | दोबारा वाला रन | कमेंट में दिखता है |
| --- | --- | --- |
| फ़ेल | पास | फ़्लेकी |
| फ़ेल | फ़ेल | फ़ेल |
| बीच में रुका | पास | पास |
| कोई और नतीजा | नहीं चला | पहले रन का नतीजा |

कमेंट में पहले रन की फ़िल्टर वाली लाइनें और छोड़े गए टेस्ट बने रहते हैं। दूसरा
दोबारा वाला रन भी इसी तरह जुड़ता है, इसलिए पहले रन के नतीजे कमेंट से नहीं
हटते।

दोबारा वाले रन ने कोई ऐसी चीज़ छोड़ दी जो उसे चलानी थी, तो कमेंट लाल रहता है। ये
चीज़ें हैं: कोई फ़ेल हुआ टेस्ट, कोई टेस्ट जिसे `--max-failures` या `--max-duration` ने
चलने से पहले रोक दिया, या कोई फ़ेल हुआ `beforeAll` या `afterAll` जिसके टेस्ट
किसी और फ़िल्टर ने बाहर रखे। दोबारा वाले रन ने कोई ऐसा टेस्ट छोड़ा जिसे पहला
रन कभी पूरा नहीं कर पाया, तो कमेंट ⏹️ दिखाता है। दोबारा वाले रन का अपना
एग्ज़िट कोड सिर्फ़ वही गिनता है जो उसने चलाया। हर अटेम्प्ट के सबूत उसकी अपनी
फ़ाइलों से लिंक होते हैं।

## मैट्रिक्स जॉब

रिपोर्टर अपना कमेंट प्रोजेक्ट, वर्कफ़्लो और जॉब से ढूँढता है। मैट्रिक्स के सारे
जॉब में ये तीनों एक जैसे होते हैं। इसलिए हर मैट्रिक्स एंट्री को उसकी अपनी `key`
दें:

```ts
reporters: ['list', github({ key: process.env.MATRIX_BROWSER })],
```

स्टेप के `env` में `MATRIX_BROWSER: ${{ matrix.browser }}` सेट करें। Key हेडलाइन
में दिखती है, जैसे `e2e chromium: 77 passed`। इसे हर रन में एक जैसी रखें, ताकि
दोबारा चलाने पर पहले वाला कमेंट ही अपडेट हो।

## एक्सप्लोरेशन

[`e2e explore`](/explore) रन अपना अलग कमेंट पोस्ट करता है। इसलिए एक ही जॉब पहले
टेस्ट चला सकता है और फिर explore कर सकता है। एक्सप्लोरेशन को उसका अपना
`--output` दें, जैसे `npx e2e explore --output .e2e-explore`, और वह डायरेक्टरी
भी अपलोड करें। ऐसा न करें, तो एक्सप्लोरेशन टेस्ट रन के नतीजों की जगह ले लेता है,
और टेस्ट रन के कमेंट में सबूत वाले लिंक टूट जाते हैं।

## जब कुछ पोस्ट नहीं होता

रिपोर्टर रन का स्टेटस या एग्ज़िट कोड कभी नहीं बदलता। जब वह पोस्ट नहीं कर पाता,
तो समरी के नीचे एक लाइन इसकी वजह बताती है:

```
       GitHub  not posted: set GITHUB_TOKEN in the step's env (GITHUB_TOKEN: ${{ github.token }}); written to the job summary
```

| स्थिति | क्या होता है |
| --- | --- |
| GitHub Actions पर नहीं | कुछ नहीं लिखा जाता। लाइन यही बताती है। |
| `push`, `schedule` या `workflow_dispatch` रन | जॉब समरी लिखी जाती है। कमेंट करने के लिए कोई पुल रिक्वेस्ट नहीं है। |
| स्टेप के `env` में `GITHUB_TOKEN` नहीं है | जॉब समरी लिखी जाती है। लाइन में दिखता है कि क्या जोड़ना है। रिपोर्टर `GH_TOKEN` भी पढ़ता है। |
| फ़ोर्क से आया `pull_request` इवेंट | टोकन रीड-ओनली होता है, इसलिए पोस्ट करना फ़ेल होता है। लाइन इसकी वजह बताती है। |
| `issue_comment` इवेंट | पुल रिक्वेस्ट के थ्रेड पर कमेंट में सोर्स लिंक नहीं होते, क्योंकि चेकआउट किया गया कमिट डिफ़ॉल्ट ब्रांच का है। |
| `pull-requests: write` नहीं है | पोस्ट करना फ़ेल होता है, और रिपोर्टर उस परमिशन का नाम बताता है। |
| GitHub API की रेट लिमिट | पोस्ट करना रुक जाता है, और रिपोर्टर थ्रॉटलिंग की बात बताता है। जॉब दोबारा चलाने से पहले रीसेट या `Retry-After` तक रुकें। |

रिपोर्टर टोकन रन ख़त्म होने पर पढ़ता है, और रिपोर्ट में टोकन नहीं होता। GitHub
Enterprise Server पर रिपोर्टर `GITHUB_SERVER_URL` और `GITHUB_API_URL` इस्तेमाल
करता है।
