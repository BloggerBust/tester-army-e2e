`e2e explore` में आप टेस्ट फ़ाइल की जगह एक लक्ष्य देते हैं, और एजेंट उसी के
हिसाब से आपका ऐप चलाता है। एजेंट एक स्टेप प्लान करता है, उसे करता है और जो
फ़ाइंडिंग मिलें, उन्हें नोट करता है। यह तब तक चलता है जब तक लक्ष्य कवर न हो
जाए या बजट ख़त्म न हो जाए। आख़िर में वह एक असेसमेंट लिखता है। मॉडल, टूल और
एक्शन के नियम वही हैं जो `agent.act()` में हैं।

## एक्सप्लोरेशन शुरू करें

फ़्लो और यूज़र का लक्ष्य बताएँ। ज़रूरत हो तो कुछ सीमाएँ भी जोड़ दें:

<CodeGroup>
```bash npm
npx e2e explore 'Explore the checkout flow like a first-time buyer and report anything off'
```

```bash pnpm
pnpm exec e2e explore 'Explore the checkout flow like a first-time buyer and report anything off'
```

```bash bun
bunx e2e explore 'Explore the checkout flow like a first-time buyer and report anything off'
```
</CodeGroup>

सीमा कुछ ऐसी हो सकती है: "ऑर्डर प्लेस करने से पहले रुक जाएँ"। लक्ष्य न दें, तो
explore `Explore the app and find bugs` इस्तेमाल करता है। कोई स्टेप फ़ेल हो जाए,
तब भी रन नहीं रुकता।

अगर `e2e.config.ts` नहीं है, तो explore पहले
[`e2e init`](/reference/cli#e2e-init) विज़ार्ड चलाता है। अगर हाथ से करने को कुछ
नहीं बचा, तो एक्सप्लोरेशन उसके ठीक बाद शुरू हो जाता है। वरना init बचे हुए
स्टेप की लिस्ट दिखाता है, जैसे `npm install` या मॉडल की key सेट करना।
टर्मिनल न हो, जैसे CI में, तो explore `CONFIG_NOT_FOUND` के साथ फ़ेल होता है।

## नतीजे पढ़ें

टर्मिनल हर फ़ाइंडिंग और हर पूरा हुआ स्टेप उसी वक़्त दिखाता है:

```text
 ❯  web  Exploring  Explore this bookshop like a careful first-time buyer: browse the catalog, ...
   ⚑ medium issue  Home greeting exposes an unresolved userName template (/)
   ⚑ high issue  Neuromancer shows an impossible negative stock availability (/catalog)
   ✓ 1  Catalog browsing 31.46s · 7 actions · 4 findings
   ⚑ high issue  Cart total does not update when Hyperion quantity increases (/cart)
   ⚑ trivial warning  Checkout newsletter label misspells Receive (/checkout)
   ✓ 2  Cart quantities and removal 19.47s · 4 actions · 3 findings
   ended: the agent covered the goal
```

`issue` मिलने पर रन एग्ज़िट कोड 1 के साथ फ़ेल होता है। `warning` से रन फ़ेल
नहीं होता। आख़िरी रिपोर्ट में सबसे गंभीर इश्यू सबसे ऊपर रहते हैं। हर फ़ाइंडिंग
के साथ उसे रीप्रोड्यूस करने के स्टेप होते हैं, और जहाँ हो सके, एक स्क्रीनशॉट
भी। किसी फ़ाइंडिंग पर काम शुरू करने से पहले उसे उसके सबूत से मिलाकर देख लें।
बाकी एग्ज़िट कोड, JSON रिपोर्ट और आर्टिफ़ैक्ट पाथ के लिए
[CLI रेफ़रेंस](/reference/cli#e2e-explore) देखें।

## दूसरे स्क्रीन साइज़ चेक करें

अगर टारगेट का इंजन व्यूपोर्ट का साइज़ बदल सकता है (वेब इंजन बदल सकता है), तो
आप लक्ष्य में दूसरी चौड़ाइयों पर लेआउट चेक करने को कह सकते हैं:

<CodeGroup>
```bash npm
npx e2e explore 'Check the pricing page at desktop, tablet, and phone widths for broken layouts'
```

```bash pnpm
pnpm exec e2e explore 'Check the pricing page at desktop, tablet, and phone widths for broken layouts'
```

```bash bun
bunx e2e explore 'Check the pricing page at desktop, tablet, and phone widths for broken layouts'
```
</CodeGroup>

## साइन इन करके शुरू करें

`--session <name>` जोड़ें। इसमें उस सेशन का नाम दें जिसे कोई
[सेटअप टेस्ट](/authentication) सेव करता है:

<CodeGroup>
```bash npm
npx e2e explore --session admin 'Explore the admin settings and find bugs'
```

```bash pnpm
pnpm exec e2e explore --session admin 'Explore the admin settings and find bugs'
```

```bash bun
bunx e2e explore --session admin 'Explore the admin settings and find bugs'
```
</CodeGroup>

explore सिर्फ़ वही सेटअप टेस्ट चलाता है और सेशन रिस्टोर कर देता है। एक्सप्लोरर
जानता है कि ऐप पहले से साइन इन होकर शुरू होता है, और वह साइन इन का कोई स्टेप
प्लान नहीं करता।

स्क्रीनशॉट में पासवर्ड फ़ील्ड मास्क रहता है। लेकिन ऐप कोई वैल्यू कहीं और दिखाए,
तो वह मॉडल तक पहुँच जाती है।
[सीक्रेट भरने के बाद स्क्रीनशॉट](/reference/security#screenshots-after-a-secret-fill) देखें।

## पुल रिक्वेस्ट का बदलाव एक्सप्लोर करें

ब्रांच में जो बदला है, उसे एक्सप्लोर करने के लिए `--changed-since <ref>` जोड़ें।
प्लानर ref के साथ मर्ज बेस से अब तक के कमिट मैसेज और कमिट हुआ डिफ़ पढ़ता है।
फिर वह अपने स्टेप उन स्क्रीन पर लगाता है जिन पर इस बदलाव का असर पड़ सकता है।

<CodeGroup>
```bash npm
npx e2e explore --changed-since origin/main
```

```bash pnpm
pnpm exec e2e explore --changed-since origin/main
```

```bash bun
bunx e2e explore --changed-since origin/main
```
</CodeGroup>

सिर्फ़ वही डिफ़ेक्ट `issue` गिना जाता है जो इस बदलाव से हो सकता है। ऐप में कहीं
और का डिफ़ेक्ट `warning` होता है, और उससे रन फ़ेल नहीं होता।

लक्ष्य न दें, तो लक्ष्य `Explore what this change affects and find bugs in it`
होता है। ऐसे में प्लानर कोई ऐसा बदलाव स्किप कर सकता है जो किसी यूज़र को दिखता
ही नहीं, जैसे सिर्फ़ डॉक्स या सिर्फ़ टेस्ट। तब रन `skipped` पर ख़त्म होता है और
पास होता है। स्किप सिर्फ़ तभी होता है जब प्लानर ने पूरा बदलाव पढ़ा हो। बड़ा
डिफ़, कोई बाइनरी फ़ाइल या बिना कमिट की फ़ाइल हो, तो स्किप नहीं होता।

ब्रांच के अपने कमिट मैसेज और कोड इस फ़ैसले पर असर डाल सकते हैं। स्किप और साफ़
निकले एक्सप्लोरेशन में फ़र्क़ करने के लिए `run.explore.ended` पढ़ें।

मॉडल क्या-क्या पढ़ता है, यह
[सुरक्षा](/reference/security#mcp-and-explore) में देखें।

GitHub Actions पर इसे `pull_request` पर अलग जॉब में चलाएँ। कॉन्फ़िग में
[GitHub रिपोर्टर](/github) हो, तो फ़ाइंडिंग एक अलग पुल रिक्वेस्ट कमेंट में जाती
हैं। फ़ोर्क से चला रन पोस्ट नहीं कर सकता।
[जब कुछ भी पोस्ट नहीं होता](/github#when-nothing-is-posted) देखें।

```yaml title=".github/workflows/explore.yml"
on: pull_request

jobs:
  explore:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    # An issue exits 1. Keep the findings as a review aid, not a merge gate.
    continue-on-error: true
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
      # ...install, browsers
      - run: npx e2e explore --changed-since origin/${{ github.base_ref }} --max-steps 4
        env:
          AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
          GITHUB_TOKEN: ${{ github.token }}
```

`fetch-depth: 0` से बेस ब्रांच चेकआउट में आ जाती है। इसके बिना रन
`INVALID_CHANGED_SINCE` के साथ फ़ेल होता है।

इंस्टॉल और बिल्ड के बाद वर्किंग ट्री साफ़ रखें, वरना रन कभी स्किप नहीं होगा।
`.e2e/` और बिल्ड आउटपुट को इग्नोर करें। e2e को `npx` से चलाएँ, `pnpm exec` से
नहीं, क्योंकि `pnpm exec` `pnpm-lock.yaml` को दोबारा लिख सकता है।

<Warning>
इसे कभी भी `pull_request_target` पर न चलाएँ। उस रन के पास आपके सीक्रेट होते हैं,
और मॉडल किसी फ़ोर्क के लिखे डिफ़ और कमिट मैसेज पढ़ता है।
</Warning>

## अगर रन बहुत जल्दी रुक जाए

रन 8 स्टेप या 10 मिनट के बाद रुक जाता है। फ़्लो में और आगे जाना हो, तो
`--max-steps <n>` (100 तक) या `--timeout <ms>` (`7200000` तक, यानी 2 घंटे)
बढ़ा दें।

मेन फ़्लो पूरे होने के बाद अगर समय बचता है, तो रन उन फ़्लो पर लौटता है। इस
बार वह एज-केस इनपुट, एक साथ कई फ़िल्टर और रीलोड आज़माता है। अगर एक से ज़्यादा
अकाउंट कॉन्फ़िगर हैं और `--session` नहीं दिया है, तो वह दूसरा अकाउंट भी आज़माता
है। रन जल्दी तभी ख़त्म होता है जब पहुँचने लायक कुछ भी नया न बचे।

## टारगेट और एजेंट चुनें

explore `e2e.config.ts` से टारगेट, ऐप कमांड, मॉडल और एजेंट लेता है। इन्हें
`--target <name>` और `--agent <name>` से चुनें। `--target` न दें, तो explore
पहला टारगेट लेता है।

## कोड से एक्सप्लोर करें

अपने कोड से एक्सप्लोरेशन शुरू करना हो, तो
[`e2e/runner` से `explore`](/reference/runner#explore) कॉल करें। इसमें आप
कॉन्फ़िग वैल्यू दे सकते हैं, रन कैंसल कर सकते हैं और प्रोग्रेस इवेंट पा सकते हैं।
