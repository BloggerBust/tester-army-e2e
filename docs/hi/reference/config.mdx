`e2e.config.ts` रनर को कॉन्फ़िगर करता है: जिन टारगेट्स पर टेस्ट चलते हैं, हर टारगेट जो
ऐप टेस्ट करता है, एजेंट्स, और रीप्ले कैश। `satisfies E2EConfig` के साथ एक ऑब्जेक्ट
एक्सपोर्ट करें, जो इसका शेप चेक करता है और इसके इनफ़र्ड टाइप बनाए रखता है। लोड होने पर
रनर कॉन्फ़िग को फिर से जाँचता है, उन रेंज और नियमों के साथ जिन्हें TypeScript चेक नहीं
कर सकता। ज़्यादातर प्रोजेक्ट जो ऑप्शन बदलते हैं, उनके लिए
[प्रोजेक्ट कॉन्फ़िगर करें](/quickstart#configure-the-project) देखें।

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';

export default {
  targets: [
    {
      name: 'web',
      engine: web({ browser: 'chromium' }),
      app: { url: process.env.APP_URL ?? 'http://localhost:3000' },
    },
  ],
} satisfies E2EConfig;
```

### टॉप लेवल

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |

| [`targets`](#targets) | `Target[]` | ज़रूरी |
| [`tests`](#tests) | `string \| string[]` | `'tests/**/*.e2e.ts'` |

| [`maxDuration`](#maxduration) | `number` | - |
| [`workers`](#workers) | `number` | आधे कोर, CI में `1` |

| [`secrets`](#secrets) | `Record<string, SecretConfig>` | - |

पूरा डिक्लेरेशन [`E2EConfig`](#e2econfig) में है।

- किसी भी लेवल पर अनजान key देने पर `INVALID_CONFIG` आता है। कोई टॉप-लेवल `app` key नहीं
  होती: हर टारगेट [वह ऐप डिक्लेयर करता है जिसे वह टेस्ट करता है](#the-app-under-test)।
- हर संख्या वाली वैल्यू एक सुरक्षित इंटीजर होनी चाहिए।
- यहाँ, `app.command` में, और `agents` में मिलीसेकंड का हर टाइमआउट ज़्यादा से ज़्यादा
  2147483647 (लगभग 24 दिन) हो सकता है। इससे बड़ा होने पर `INVALID_CONFIG` आता है।
- ऑप्शनल की में वैल्यू दी जाती है या उसे छोड़ दिया जाता है। `exactOptionalPropertyTypes`
  के तहत `undefined` टाइप एरर होता है, इसलिए `store: process.env.CACHE_URL && createStore(...)`
  कंपाइल नहीं होता। रनटाइम पर `undefined` को अनसेट माना जाता है।
- टारगेट के `app` फ़ील्ड अपने टाइप में `undefined` भी स्वीकार करते हैं, ताकि वे सीधे
  `process.env` पढ़ सकें। एनवायरनमेंट पर निर्भर किसी भी दूसरी key को तभी स्प्रेड करें जब
  उसके पास कोई वैल्यू हो:

```ts
export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  ...(process.env.CACHE_URL === undefined ? {} : { cache: { store: createStore(process.env.CACHE_URL) } }),
} satisfies E2EConfig;
```

#### `projectId`

प्रोजेक्ट के लिए एक स्थिर id।

```ts
projectId: 'acme-web', // default: the root package.json name
```

- 1 से 256 कैरेक्टर।
- रूट `package.json` में `name` न होने पर, यह `unportable-<sha256 of the project root, 32 hex>`
  पर फ़ॉलबैक करता है।

#### `tests`

प्रोजेक्ट रूट के हिसाब से टेस्ट फ़ाइल के ग्लॉब।

```ts
tests: ['tests/**/*.e2e.ts', '!tests/wip/**'], // default: 'tests/**/*.e2e.ts'
```

- ग्लॉब में `*`, `?`, और पूरा `**` सेगमेंट चलता है। `?` एक Unicode कोड पॉइंट से मैच करता
  है, इमोजी समेत।
- `!` से शुरू होने वाली एंट्री एक्सक्लूड करती है। ऊपर का उदाहरण `tests/wip/` के नीचे की
  फ़ाइलों को छोड़कर हर टेस्ट फ़ाइल चुनता है।
- कोई फ़ाइल तब चुनी जाती है जब कोई इन्क्लूड ग्लॉब उससे मैच करे और कोई एक्सक्लूज़न न करे,
  लिस्ट का क्रम कुछ भी हो।
- डिस्कवरी सिर्फ़ उन्हीं डायरेक्टरीज़ में जाती है जो मैच हो सकती हैं। यह उस डायरेक्टरी में
  कभी नहीं जाती जिसे कोई एक्सक्लूज़न पूरा हटा दे, `node_modules` को छोड़ देती है, और
  सिमलिंक को नज़रअंदाज़ करती है।
- डॉट से शुरू होने वाली डायरेक्टरी तभी शामिल होती है जब कोई ग्लॉब सेगमेंट डॉट से शुरू हो।
- डिफ़ॉल्ट सिर्फ़ TypeScript चुनता है। JavaScript टेस्ट्स के लिए `'tests/**/*.e2e.js'`
  सेट करें ([JavaScript](#javascript))।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | लिस्ट में सिर्फ़ एक्सक्लूज़न हों। |
| `INVALID_GLOB` | बिना वाइल्डकार्ड वाली एंट्री किसी डायरेक्टरी का नाम दे (`'!tests/wip'`)। ग्लॉब फ़ाइलों का नाम देता है; एरर बताता है कि कौन सा ग्लॉब लिखें (`'!tests/wip/**'`)। |
| `NO_TESTS` | `e2e run` को पास की गई फ़ाइल किसी एक्सक्लूज़न से बाहर हो जाए। एरर उस एंट्री का नाम बताता है। |

#### `timeout`

एक टेस्ट अटेम्प्ट की डेडलाइन, मिलीसेकंड में।

```ts
timeout: 180_000, // default: 120000
```

#### `launchTimeout`

इंजन इनिट और अटेम्प्ट स्टार्ट का बजट, मिलीसेकंड में।

```ts
launchTimeout: 90_000, // default: 60000
```

#### `actionTimeout`

हर इंजन ऑपरेशन का बजट, मिलीसेकंड में।

```ts
actionTimeout: 10_000, // default: 30000
```

- टारगेटेड एजेंट एक्शन `actionTimeout` और 15 s में से जो छोटा हो उससे बँधा होता है।
- कॉल का अपना `timeout` ऑप्शन इस पर भारी पड़ता है। `timeout: 0` उस कॉल के लिए कोई
  डेडलाइन नहीं रखता; टेस्ट टाइमआउट, या `afterEach` में `cleanupTimeout`, फिर भी इसे
  सीमित रखता है।
- `--action-timeout <ms>` एक रन के लिए इसे ओवरराइड करता है।

#### `assertionTimeout`

डिफ़ॉल्ट `expect` डेडलाइन, मिलीसेकंड में।

```ts
assertionTimeout: 10_000, // default: 5000
```

- मैचर का अपना `timeout` ऑप्शन इस पर भारी पड़ता है। `timeout: 0` उस मैचर के लिए कोई
  डेडलाइन नहीं रखता; टेस्ट टाइमआउट, या `afterEach` में `cleanupTimeout`, फिर भी इसे
  सीमित रखता है।
- `--assertion-timeout <ms>` एक रन के लिए इसे ओवरराइड करता है।

#### `toPass`

[ब्लॉक को दोबारा चलाने](/reference/expect#retrying-a-block) के लिए डिफ़ॉल्ट टाइमआउट और
पॉज़। हर कॉल ऑप्शन संबंधित कॉन्फ़िग फ़ील्ड से ऊपर रहता है।

```ts
toPass: { timeout: 10_000, intervals: [100, 250, 500] },
```

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |
| `timeout` | `number` | `0` |
| `intervals` | `readonly number[]` | `[100, 250, 500, 1000]` |

- `timeout` मिलीसेकंड में 0 से 2147483647 तक का इंटीजर होता है। `0` पर रीट्राई सिर्फ़
  टेस्ट या हुक की डेडलाइन से सीमित होते हैं।
- `intervals` मिलीसेकंड में धनात्मक इंटीजर्स की नॉन-एम्प्टी लिस्ट होती है। आखिरी पॉज़
  दोहराया जाता है।

कॉन्फ़िग लोड पर इनवैलिड वैल्यू या अनजान key `INVALID_CONFIG` के रूप में रिपोर्ट होती हैं।

`beforeAll`, `afterAll`, और वर्कर फ़िक्स्चर टियरडाउन में कॉन्फ़िगर किए गए डिफ़ॉल्ट
`expect.poll` और `toPass` पर लागू होते हैं। रीट्राई हुक की डेडलाइन तक सीमित रहते हैं।

#### `cleanupTimeout`

हर `afterEach` हुक, फ़िक्स्चर टियरडाउन, और इंजन क्लीनअप का बजट, मिलीसेकंड में।

```ts
cleanupTimeout: 60_000, // default: 30000
```

#### `retries`

हर टेस्ट के लिए रीट्राई।

```ts
retries: 2, // default: 1 in CI, else 0
```

- 0 से 10 तक।

#### `failOnSkippedFailure`

जब कोई टेस्ट किसी पहले फ़ेल हुए अटेम्प्ट के बाद रीट्राई को स्किप कर दे, तो रन को एग्ज़िट
कोड 1 के साथ फ़ेल कर देता है।

```ts
failOnSkippedFailure: true, // default: false
```

- टेस्ट का `skipped` स्टेटस और कारण वही रहता है।
- उसकी फ़ेलियर रिपोर्ट में बनी रहती हैं, और दोनों सेटिंग में CLI उन्हें
  `Skipped After Failure` के नीचे दिखाता है।
- साफ़ स्किप, पास हुए रीट्राई, और इंजन क्लीनअप डायग्नोस्टिक्स इसे ट्रिगर नहीं करते।

<Note>
फ़ेल हुए `expect.soft` के बाद स्किप के लिए किसी ऑप्शन की ज़रूरत नहीं होती: वह
[अटेम्प्ट को फ़ेल कर देता है](/reference/test#members)।
</Note>

#### `maxDuration`

टेस्ट चलाने का वॉल-क्लॉक बजट, मिलीसेकंड में। यह ज़्यादा देर तक चलने वाले रन को रोक देता है।

```ts
export default { targets, maxDuration: 900_000 } satisfies E2EConfig; // default: none
```

- ज़्यादा से ज़्यादा 2147483647 (लगभग 24 दिन)।
- घड़ी तब शुरू होती है जब टेस्ट शुरू होते हैं। ऐप स्टार्टअप को इसकी जगह ऐप कमांड का
  [`startupTimeout`](#command) सीमित करता है।
- समय खत्म होने पर रनर आगे कुछ डिस्पैच नहीं करता। चल रहे टेस्ट `interrupted` पर खत्म
  होते हैं, और जो टेस्ट शुरू नहीं हुए उन्हें `time-limit` कारण के साथ स्किप कर दिया जाता
  है। रन में `RUN_TIMEOUT` एरर दर्ज होता है और यह एग्ज़िट कोड 1 से बाहर निकलता है।
- अगली बार `--last-failed` इंटरप्ट और स्किप हुए टेस्ट्स को चलाता है।
- `--max-duration <ms>` एक रन के लिए इसे ओवरराइड करता है।
- `e2e explore` इसे नज़रअंदाज़ करता है और अपना `--timeout` इस्तेमाल करता है।

#### `workers`

समानांतर वर्कर।

```ts
workers: 4, // default: 1 in CI, else half the cores
```

- 1 से 1024 तक।
- लोकली डिफ़ॉल्ट `max(1, floor(availableParallelism() / 2))` है।
- इंजन इसे नीचे कैप कर सकता है: `workers` कभी भी किसी टारगेट के इंजन से डिक्लेयर की
  गई संख्या से ज़्यादा नहीं होता।
- एक से ज़्यादा वर्कर होने पर, हर टारगेट की फ़ाइलें [टाइमिंग हिस्ट्री](/ci#cache-the-timings-history)
  के हिसाब से सबसे लंबी फ़ाइल से शुरू होती हैं। बिना टाइम वाली फ़ाइल टाइम वाली फ़ाइलों से
  पहले शुरू होती है। `--changed-since` के साथ, सबसे ज़्यादा संभावना वाली फ़ाइलें उससे भी
  पहले शुरू होती हैं, जैसा [सबसे ज़्यादा संभावना वाले पहले चलाएँ](/filters#start-the-likeliest-first)
  में बताया गया है।

#### `reporters`

रन के रिपोर्टर: बिल्ट-इन id, और `e2e/reporters` की फ़ैक्ट्री जैसे रिपोर्टर ऑब्जेक्ट।

```ts
reporters: ['list', 'junit'], // default: ['list']
```

| वैल्यू | क्या करता है |
| --- | --- |
| `'list'`, `list()` | टर्मिनल प्रोग्रेस, फ़ेलियर, और रन समरी। |
| `'dot'`, `dot()` | कॉम्पैक्ट टर्मिनल प्रोग्रेस, फ़ेलियर, और रन समरी। |
| `'line'`, `line()` | टर्मिनल प्रोग्रेस की एक लाइन, हर फ़ेलियर होते ही प्रिंट, और रन समरी। |
| `'junit'`, `junit()` | `<output>/junit.xml` या `outputFile` लिखता है। |
| `'markdown'`, `markdown()` | `<output>/summary.md` या `outputFile` लिखता है। |
| `'ctrf'`, `ctrf()` | CTRF फ़ॉर्मेट में `<output>/ctrf.json` या `outputFile` लिखता है। |
| `'json'`, `json()` | रिपोर्ट को stdout पर प्रिंट करता है। इसके साथ `list`, `dot`, या `line` तब तक stderr पर प्रिंट करते हैं जब तक उन्हें `stream` न दिया जाए। |
| कोई और `Reporter` ऑब्जेक्ट | बिल्ट-इन वालों के साथ चलता है। `--reporter` इसे कभी नहीं हटाता। |

कोई id बिना ऑप्शन के कॉल की गई अपनी फ़ैक्ट्री के बराबर है। अनजान id पर `INVALID_CONFIG`
आता है, और `list`, `dot`, और `line` में से किन्हीं दो को साथ देने पर भी।
[रिपोर्टर](/reference/reporters) देखें।

### targets

टारगेट एक नाम वाला सरफ़ेस है जिस पर टेस्ट चलते हैं: टेस्ट हो रहा ऐप और उसे चलाने वाला
[इंजन](#engine)। `targets` ज़रूरी है और इसमें कम से कम एक एंट्री होनी चाहिए।

```ts title="e2e.config.ts"
targets: [
  { name: 'chromium', engine: web(), app: { url: 'http://localhost:3000' } },
  { name: 'firefox', engine: web({ browser: 'firefox' }), app: { url: 'http://localhost:3000' } },
],
```

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |
| [`name`](#name) | `string` | प्लेटफ़ॉर्म |
| [`platform`](#platform) | `string` | इंजन का प्लेटफ़ॉर्म |
| [`engine`](#engine) | `EngineHandle` | - |
| [`app`](#the-app-under-test) | `TargetApp` | - |
| [`trace`](#trace) | `RecordingMode` | कॉन्फ़िग का `trace` |
| [`video`](#video) | `RecordingMode` | कॉन्फ़िग का `video` |

- `{ engine: web(), app: { url } }` एक पूरा टारगेट है।
- जिस टेस्ट के `platforms` में टारगेट का प्लेटफ़ॉर्म न हो, वह उसके लिए स्किप हो जाता है।
  चुना गया टेस्ट जिस `test.setup` पर निर्भर करता है वह वहाँ चलने लायक होना चाहिए, वरना
  सिलेक्शन `COLLECTION_ERROR` से फ़ेल होता है।

पूरा डिक्लेरेशन [`Target`](#target) में है।

#### `name`

वह id जिसे `--target`, रिपोर्ट, सेशन, और आर्टिफ़ैक्ट पाथ इस्तेमाल करते हैं।

```ts
name: 'chromium', // default: the platform
```

- ASCII अक्षर, अंक, `_`, `-`, और `.`, लेकिन सिर्फ़ डॉट्स नहीं (`.` और `..` पाथ सेगमेंट
  होते हैं)।
- सभी टारगेट्स में अलग होना चाहिए। एक ही प्लेटफ़ॉर्म पर दो टारगेट हों तो उन्हें नाम देना
  ज़रूरी है।

#### `platform`

प्लेटफ़ॉर्म लेबल।

```ts
platform: 'web', // default: inherited from the engine
```

- बिना इंजन वाले टारगेट के लिए ज़रूरी है।
- जब टारगेट और उसका इंजन दोनों एक नाम दें, तो दोनों का मेल खाना ज़रूरी है।

#### `engine`

सरफ़ेस को चलाने वाला इंजन: `web(...)`, `mobile(...)`, या कोई भी `defineEngine` हैंडल।

```ts
engine: web({ browser: 'firefox' }),
```

बिना इंजन वाला टारगेट एजेंट टूल और पूरे URL पर [`request`](/reference/request) कॉल से
चलता है। `app` वाले लेकिन बिना इंजन वाले टारगेट पर `INVALID_CONFIG` आता है।

### टेस्ट हो रहा ऐप

टारगेट जिस ऐप को टेस्ट करता है उसे `app` में डिक्लेयर करता है; इंजन सिर्फ़ उसे चलाता है।
ब्राउज़र टारगेट उस URL का नाम देता है जिसे वह खोलता है, डिवाइस टारगेट उस इंस्टॉल ऐप या
बिल्ड का जिसे वह लॉन्च करता है। रनर कॉन्फ़िग लोड पर `app` को रिज़ॉल्व करता है।

```ts title="e2e.config.ts"
targets: [
  {
    name: 'web',
    engine: web({ viewport: { width: 1440, height: 900 } }),
    app: {
      url: 'http://localhost:3000',
      command: { executable: 'npm', args: ['run', 'dev'] },
      readyUrl: 'http://localhost:3000/health',
    },
  },
  {
    name: 'ios',
    engine: mobile({ platform: 'ios' }),
    app: {
      bundleId: 'com.example.app',
      appPath: './build/App.app',
      launchArguments: ['-e2e', 'YES'],
      permissions: { camera: 'grant' },
    },
  },
],
```

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |
| [`url`](#url) | `string` | - |
| [`bundleId`](#bundleid) | `string` | - |
| [`appPath`](#apppath) | `string` | - |
| [`linkBase`](#linkbase) | `string` | - |
| [`identity`](#identity) | `string` | ऐप से निकाला गया |
| [`environment`](#environment) | `'test' \| 'staging' \| 'production'` | `'test'` या `'production'` |
| [`launchArguments`](#launcharguments) | `string[] \| Record<string, LaunchArgumentValue>` | - |
| [`permissions`](#permissions) | `Record<string, AppPermissionState>` | - |
| [`command`](#command) | `CommandConfig` | - |
| [`readyUrl`](#readyurl) | `string` | `url` |

हर इंजन कॉन्फ़िग लोड पर keys चेक करता है, और गड़बड़ी पर टारगेट के नाम के साथ
`INVALID_CONFIG` देता है। `app` वाले टारगेट को [इंजन](#engine) चाहिए होता है।

- `web()` टारगेट को `app.url` चाहिए होता है और वह `bundleId`, `appPath`, और
  `launchArguments` को मना करता है।
- `mobile()` टारगेट को `app.bundleId` या `app.appPath` चाहिए होता है। मोबाइल टारगेट पर
  `app.url` अभी सपोर्ट नहीं है।
- `desktop()` टारगेट को `app.bundleId` या `app.appPath` चाहिए होता है और वह `app.url`
  और `app.permissions` को मना करता है। दोनों होने पर वह `appPath` बिल्ड लॉन्च करता है,
  जिसकी बंडल id `bundleId` के बराबर होनी चाहिए।
- `app.linkBase` के लिए ऐसा इंजन चाहिए जो लिंक खोल सके, जैसे `mobile()`।
- `app` या `app.command` में अनजान key देने पर सुझाव के साथ एरर आता है।

<Note>
पुरानी स्पेलिंग अनजान key हैं और कॉन्फ़िग लोड पर `INVALID_CONFIG` से फ़ेल होती हैं:
`web({ url })` और `web()` और `mobile()` के पुराने app ऑप्शन, `mobile({ app })` (अब
`app.bundleId`), सीधे टारगेट पर कोई app key, टॉप-लेवल `app` या `url`, और कहीं भी
[`services`](#services)।
</Note>

#### `url`

बेस URL: `app.open()` इसे खोलता है और रिलेटिव नेविगेशन इसी के हिसाब से रिज़ॉल्व होता है।

```ts
url: 'http://localhost:3000',
```

- WHATWG-नॉर्मलाइज़्ड; कोई userinfo, क्वेरी, या फ़्रैगमेंट नहीं।
- स्कीम न होने पर यह `https://` बन जाता है, या लूपबैक होस्ट के लिए `http://`।
- सादा HTTP सिर्फ़ लूपबैक होस्ट के लिए स्वीकार किया जाता है।
- `file:` URL लोकली लॉन्च हुए ब्राउज़र में इस मशीन की एक फ़ाइल खोलता है:
  [ऐप के तौर पर फ़ाइल](#a-file-as-the-app) देखें।
- `127.0.0.1` या `[::1]` पर पोर्ट `0` [फ़्री पोर्ट](#free-ports) माँगता है।
- इसका ऑरिजिन इंजन के रिक्वेस्ट क्रेडेंशियल का स्कोप तय करता है, और इसकी साइट ऑब्ज़र्व
  किए जाने वाले फ़्रेम्स का: [ऐप की साइट](#the-apps-site) देखें।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_APP_URL` | `127.0.0.1` या `[::1]` के अलावा किसी भी होस्ट (`localhost` समेत) पर पोर्ट `0`। |
| `INVALID_APP_URL` | होस्ट वाला `file:` URL, या ऐसा जो किसी डायरेक्टरी का नाम दे। |
| `INVALID_CONFIG` | पोर्ट-0 वाला `url` जिसके लिए शुरू करने को कुछ न हो (`app.command` न हो)। |
| `INVALID_CONFIG` | ब्राउज़र प्रोवाइडर, `connect`, `headers`, या `basicAuth` वाले `web()` टारगेट पर `file:` URL, या ऐसे इंजन पर जो `fileApps` डिक्लेयर न करे। |

#### `bundleId`

वह इंस्टॉल ऐप जिसे डिवाइस लॉन्च करता है: बंडल id, Android पैकेज नाम, या ऐसा डिस्प्ले
नाम जिसे डिवाइस रिज़ॉल्व करे (`Settings`)। `desktop()` टारगेट पर किसी इंस्टॉल macOS ऐप
की बंडल id या नाम।

```ts
bundleId: 'com.example.app',
```

लिंक देने पर `INVALID_CONFIG` आता है: टेस्ट लिंक को `device.openLink` से खोलता है।

#### `appPath`

वह बिल्ड जिस पर सूट चलता है, प्रोजेक्ट रूट के हिसाब से रिज़ॉल्व किया गया iOS `.app` बंडल
या Android `.apk`। `desktop()` टारगेट पर macOS `.app` बंडल।

```ts
appPath: './build/App.app',
```

`bundleId` न होने पर, यह जो ऐप इंस्टॉल करता है वही लॉन्च होता है। यह कब इंस्टॉल होता है,
इसके लिए [डिवाइस इंजन](/reference/mobile#engine) देखें।

#### `linkBase`

डिवाइस टारगेट पर `app.open(path)` कहाँ खुलता है: पाथ लिंक बेस से जुड़ता है, और लिंक पिन
किए गए ऐप में खुलता है।

```ts
linkBase: 'https://shop.example.com', // app.open('/orders/42') opens https://shop.example.com/orders/42
linkBase: 'shopapp://', // app.open('/orders/42') opens shopapp://orders/42
```

- बेस और पाथ के बीच एक स्लैश जुड़ता है; सीधे स्कीम (`shopapp://`) के बाद कोई स्लैश नहीं
  आता।
- `app.open` को पास किया गया पूरा लिंक जैसा दिया गया है वैसा ही खुलता है (कस्टम ऐप स्कीम
  समेत); `file:`, `data:`, `javascript:`, `view-source:`, `blob:`, और `filesystem:`
  लिंक `POLICY_DENIED` होते हैं।
- `linkBase` के बिना, डिवाइस पर `app.open()` ऐप लॉन्च करता है और कोई पाथ नहीं लेता
  (`APP_URL_REQUIRED`)।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | इंजन लिंक नहीं खोलता (`web()` टारगेट), वैल्यू पूरा URL या स्कीम नहीं है, उसमें क्वेरी या फ़्रैगमेंट है (खाली `?` या `#` समेत), शुरू या अंत में वाइटस्पेस है, या उसमें `file:`, `data:`, `javascript:`, `view-source:`, `blob:`, या `filesystem:` है। |
| `POLICY_DENIED` | `app.open` को इनमें से किसी स्कीम वाला पूरा लिंक मिला। |

#### `identity`

वह स्थिर पहचान जो रीप्ले कैश और सेशन एंट्रीज़ की की बनाती है।

```ts
identity: 'checkout-web', // default: the URL's origin and base path, else bundleId, else appPath
```

प्रीव्यू URL या वर्ज़न वाले बिल्ड पाथ के बीच एंट्रीज़ दोबारा इस्तेमाल करने के लिए एक स्थिर
वैल्यू सेट करें। [फ़्री पोर्ट](#free-ports) के साथ डिफ़ॉल्ट डिक्लेयर किए गए `:0` से निकलता
है, इसलिए पोर्ट बदलने पर कैश और सेशन एंट्रीज़ बेकार नहीं होतीं।

<Note>
अलग-अलग ऐप्स की आइडेंटिटी अलग होनी चाहिए। साझा आइडेंटिटी उनके बीच रिकॉर्डिंग रीप्ले कर
देती है।
</Note>

#### `environment`

रिपोर्ट में टारगेट को लेबल करता है और कैश और सेशन आइडेंटिटी डाइजेस्ट में जुड़ता है। यह कभी
किसी रन को रोकता नहीं।

```ts
environment: 'staging', // default: 'test' for a local host or no URL, else 'production'
```

- `'test'`, `'staging'`, या `'production'`।
- लोकल होस्ट का मतलब है लूपबैक, `.localhost`, या `.test` होस्ट।

#### `launchArguments`

वे आर्ग्युमेंट जो हर नए लॉन्च (`app.open()`, `app.restart()`, और `app.clearState()`)
पर ऐप को पास किए जाते हैं। स्ट्रिंग्स की लिस्ट (खुद आर्ग्युमेंट) या आर्ग्युमेंट नाम से
वैल्यू का ऑब्जेक्ट दें। iOS और macOS पर हर एंट्री `-name value` बनती है। Android पर यह
वैल्यू के टाइप का `am start` एक्स्ट्रा बनती है: स्ट्रिंग के लिए `--es`, बूलियन के लिए
`--ez`, पूर्ण संख्या के लिए `--ei` (Java के `int` से बाहर `--el`), दशमलव के लिए
`--ef`, लिस्ट के लिए `--esa`।

```ts
launchArguments: ['-e2e', 'YES'],
```

```ts
launchArguments: { AppleLanguages: ['fr'], AppleLocale: 'fr_FR', e2e: true },
```

```ts
type LaunchArgumentValue = string | number | boolean | readonly string[];
type LaunchArguments = readonly string[] | Readonly<Record<string, LaunchArgumentValue | undefined>>;
```

- ऑब्जेक्ट की वैल्यू स्ट्रिंग, 2^53 से कम परिमाण की सीमित संख्या, बूलियन, या स्ट्रिंग्स की
  लिस्ट होती है। नाम में शुरू में डैश, वाइटस्पेस, या कंट्रोल कैरेक्टर नहीं होते, और कहीं
  भी NUL कैरेक्टर नहीं होता। एनवायरनमेंट से पढ़ी गई वैल्यू `undefined` हो सकती है: उस
  एंट्री को छोड़ दिया जाता है।
- [लॉन्च आर्ग्युमेंट और परमिशन](/reference/mobile#launch-arguments-and-permissions)
  की टेबल iOS और Android पर हर वैल्यू टाइप को दिखाती है।
- जो आर्ग्युमेंट बिल्ड मोड चुनते हैं, वे ऐप का रूप बदल देते हैं। हर मोड को अपनी अलग
  `identity` दें।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | ऐसा लिस्ट आइटम जो स्ट्रिंग न हो। ऐसा ऑब्जेक्ट जिसमें खाली नाम हो, नाम में वाइटस्पेस या कंट्रोल कैरेक्टर हो, किसी और टाइप की वैल्यू हो, 2^53 - 1 से ज़्यादा परिमाण की संख्या हो, या कहीं भी NUL कैरेक्टर हो। इंजन अपने नियम जोड़ता है: [मोबाइल रेफ़रेंस](/reference/mobile#launch-arguments-and-permissions) देखें। |

#### `permissions`

ऐप के पास जो परमिशन होंगी, नाम से।

```ts
permissions: { camera: 'grant' },
```

हर एक `'grant'`, `'deny'`, या `'reset'` होती है।

- `mobile()` टारगेट हर नए लॉन्च से पहले इनमें से हर एक को सेट करता है।
  [परमिशन](/reference/mobile#engine) देखें।
- `web()` टारगेट सिर्फ़ `'grant'` लेता है और इसे अटेम्प्ट के हर पेज पर, किसी भी ऑरिजिन के
  लिए ग्रांट कर देता है। हेडलेस Chromium छोड़ी गई परमिशन को मना कर देता है।
  [ब्राउज़र परमिशन ग्रांट करना](/web#granting-browser-permissions) देखें।

| ब्राउज़र | नाम |
| --- | --- |
| `chromium` | `accelerometer`, `ambient-light-sensor`, `background-sync`, `camera`, `clipboard-read`, `clipboard-write`, `geolocation`, `gyroscope`, `local-fonts`, `local-network-access`, `magnetometer`, `microphone`, `midi`, `midi-sysex`, `notifications`, `payment-handler`, `screen-wake-lock`, `storage-access` |
| `firefox` | `geolocation`, `local-network-access`, `notifications`, `persistent-storage`, `push`, `screen-wake-lock` |
| `webkit` | `camera`, `clipboard-read`, `geolocation`, `microphone`, `notifications`, `screen-wake-lock` |

ब्राउज़र प्रोवाइडर या `connect` `chromium` वाले नाम लेता है: इंजन इसे CDP पर चलाता है,
Lightpanda समेत।

#### `command`

वह प्रोसेस जिसे रनर पहले टेस्ट से पहले शुरू करता है और हर एग्ज़िट पाथ पर बंद करता है:
जैसे डेव सर्वर, या डीबग बिल्ड के लिए Metro।

```ts
command: {
  executable: 'pnpm',
  args: ['dev', '--port', '{port}'],
  inheritEnv: ['STRIPE_*'],
  startupTimeout: 120_000, // default: 60000
},
```

| फ़ील्ड | उदाहरण | डिफ़ॉल्ट |
| --- | --- | --- |
| `executable` | `'npm'` | ज़रूरी |
| `args` | `['run', 'dev']` | कोई नहीं |
| `cwd` | `'apps/web'` | प्रोजेक्ट रूट |
| `env` | `{ PORT: '{port}' }` | कोई नहीं |
| `inheritEnv` | `['STRIPE_*']` | कोई नहीं |
| `startupTimeout` | `120_000` | `60000` |
| `shutdownTimeout` | `5_000` | `10000` |
| `log` | `'.e2e/logs/app.log'` | आउटपुट छोड़ दिया जाता है |
| `reuseExisting` | `true` | `false` |

- `executable` `PATH` से रिज़ॉल्व होता है और कभी शेल में इंटरप्रेट नहीं होता।
- `args` ज्यों के त्यों पास होते हैं। `args` और `env` वैल्यू में `{port}` `url` के पोर्ट
  में बदल जाता है।
- `cwd` प्रोजेक्ट रूट से रिज़ॉल्व होता है।
- चाइल्ड प्रोसेस को सिर्फ़ `PATH`, `HOME`, टेम्प-डायरेक्टरी वेरिएबल, `inheritEnv` से मैच
  होने वाले वेरिएबल, और `command.env` मिलते हैं। ऐप को जो चाहिए वह साफ़-साफ़ पास करें।
- `inheritEnv` ठीक नाम या `*` पर खत्म होने वाले प्रीफ़िक्स (`'STRIPE_*'`) लेता है। यह
  किसी वेरिएबल को तभी कॉपी करता है जब वह सेट हो। इनहेरिट हुई वैल्यू पर `env` भारी पड़ता
  है।
- हर `args` एंट्री और `env` वैल्यू स्ट्रिंग होती है। `undefined` `env` वैल्यू छोड़ दी
  जाती है।
- `startupTimeout` [`readyUrl`](#readyurl) प्रोब का बजट होता है।
- `shutdownTimeout` फ़ोर्स-किल से पहले का ग्रेस पीरियड होता है।
- `e2e run` में, अगर कोई कमांड रेडी होने के बाद बंद हो जाए और किसी निर्भर टारगेट का काम
  बाकी हो, तो रन `APP_UNREACHABLE` से फ़ेल हो जाता है। इसमें एग्ज़िट कोड 0 और सिग्नल से
  बंद होना भी शामिल है। रनर सिर्फ़ उन्हीं टारगेट्स के एक्टिव टेस्ट इंटरप्ट करता है और क्यू
  हुए टेस्ट स्किप करता है। जिन टारगेट्स का काम पूरा हो चुका है वे इस एग्ज़िट को नज़रअंदाज़
  करते हैं।
- `log` में प्रोसेस का stdout और stderr अपेंड होता है, जो प्रोजेक्ट रूट से रिज़ॉल्व होता है।
  इसे प्रोजेक्ट रूट के अंदर ही रहना होता है।
- `log` सेट होने पर, स्टार्टअप टाइमआउट और कमांड एग्ज़िट में कमांड शुरू होने के बाद जुड़ी
  लाइनें कोट की जाती हैं। 8 KiB के अंदर 40 लाइनों तक का लॉग पूरा कोट होता है। वरना कोट
  में दोनों सिरों से अधिकतम 20-20 लाइनें रखी जाती हैं, बीच में `[startup output omitted]`
  के साथ, और 8 KiB से बड़े लॉग के लिए वे लाइनें उसके पहले और आखिरी 4 KiB से ली जाती हैं।
  खाली या न पढ़े जा सकने वाले लॉग पर `no output in <log>` आता है। साझा लॉग में दूसरे
  प्रोसेस की लाइनें भी आ सकती हैं। कोट में कम से कम 4 कैरेक्टर वाली `command.env` और
  `inheritEnv` वैल्यू `<secret:NAME>` मार्कर से बदल दी जाती हैं। `log` के बिना, ये एरर
  आपसे इसे सेट करने को कहते हैं। जो कमांड स्पॉन ही न हो सके वह इसकी जगह स्पॉन एरर बताती
  है।
- `reuseExisting`: अगर कमांड शुरू होने से पहले ही रेडीनेस URL जवाब दे रहा हो, तो रनर उसी
  प्रोसेस को इस्तेमाल कर लेता है। वह कुछ शुरू नहीं करता और कुछ बंद नहीं करता। CI एक नोटिस
  के साथ इसे नज़रअंदाज़ करता है और हमेशा कमांड शुरू करता है।
- एक ही कमांड डिक्लेयर करने वाले टारगेट एक ही प्रोसेस शेयर करते हैं, जिसकी जाँच पहले
  डिक्लेयर करने वाले टारगेट के `readyUrl` पर होती है।
- रनर कभी उस प्रोसेस को बंद नहीं करता जिसे उसने शुरू नहीं किया।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | `inheritEnv` में सीधा `'*'`। |
| `INVALID_CONFIG` | ऐसी `args` एंट्री या `env` वैल्यू जो स्ट्रिंग न हो (संख्या या `secrets.get()` हैंडल समेत)। |
| `INVALID_CONFIG` | ऐसे ऐप पर `reuseExisting` जिसका `url` पोर्ट 0 माँगता है: पहले से चल रहा प्रोसेस रन से दिए गए पोर्ट पर सर्व नहीं कर सकता। |
| `APP_URL_REQUIRED` | कॉन्फ़िग लोड पर ऐसा `app.command` जिसके पास न `app.url` हो न `app.readyUrl`। |
| `APP_ALREADY_RUNNING` | `reuseExisting` के बिना, ऐसा `readyUrl` जो पहले से जवाब दे रहा हो। |
| `APP_UNREACHABLE` | कमांड स्पॉन नहीं हो पाई, उसका `log` नहीं खुल सका, `startupTimeout` पूरा हो गया, कमांड रेडी होने से पहले बंद हो गई, या `e2e run` के दौरान अचानक बंद हो गई। |

<Warning>
`log` में कच्चा आउटपुट होता है जिसमें कुछ भी छिपाया नहीं जाता। इसे gitignore की हुई डायरेक्टरी में
रखें।
</Warning>

पूरा डिक्लेरेशन [`CommandConfig`](#commandconfig) में है।

#### `readyUrl`

वह URL जिस पर `command` के रेडी होने तक (200-499 स्टेटस पर) पोल किया जाता है।

```ts
readyUrl: 'http://localhost:3000/health', // default: url
```

- `url` न होने पर ज़रूरी है।
- इसमें `{port}` `url` का पोर्ट होता है।

#### ऐप की साइट

टेस्ट या एजेंट कोई भी http(s) URL और `about:blank` खोल सकता है। बाकी हर स्कीम (`file:`,
`data:`, `javascript:`, `view-source:`, `blob:`) `POLICY_DENIED` है। `url` की साइट उसका
रजिस्ट्रेबल डोमेन होती है: `app.example.com` और `auth.example.com` एक ही साइट हैं। साइट
के बाहर के चाइल्ड फ़्रेम ऑब्ज़र्वेशन से बाहर रहते हैं।

#### ऐप के तौर पर फ़ाइल

```ts
import { pathToFileURL } from 'node:url';

app: { url: pathToFileURL('dist/index.html').href },
```

- URL बिना होस्ट के एक फ़ाइल का नाम देता है। डायरेक्टरी मना है।
- नेविगेशन `file:` URL सिर्फ़ उस फ़ाइल की डायरेक्टरी या उसके नीचे की फ़ाइल के लिए लेता
  है: `app.open('pages/about.html')`। इसके बाहर की कोई फ़ाइल या कोई भी डायरेक्टरी
  `POLICY_DENIED` होती है, सिमलिंक रिज़ॉल्व करके। `/` से शुरू होने वाला पाथ डिस्क का रूट
  होता है, इसलिए इसे रिलेटिव लिखें।
- वही डायरेक्टरी वह जगह है जिसे एजेंट पढ़ सकता है। फ़ाइल को ऐसे फ़ोल्डर में रखें जिसमें
  सिर्फ़ ऐप हो, न कि `.env` के बगल में प्रोजेक्ट रूट में।
  [नेविगेशन](/reference/security#navigation) देखें।
- फ़ाइल की कोई साइट और कोई ऑरिजिन नहीं होता। दूसरे डॉक्यूमेंट लोड करने वाले फ़्रेम
  ऑब्ज़र्वेशन से बाहर रहते हैं, और `environment` डिफ़ॉल्ट रूप से `'test'` होता है।
- एजेंट सिर्फ़ ट्री से काम करता है: उसे कोई स्क्रीनशॉट नहीं भेजा जाता, क्योंकि उसमें किसी
  और लोकल फ़ाइल का फ़्रेम दिख सकता है। `vision: true` वाला `agent.assert` ट्री से जज
  करता है, `vision: 'only'` `POLICY_DENIED` होता है, और न `agent.assert` न फ़ेलियर कोई
  स्क्रीनशॉट रखता है।
- इसके साथ `command` होने पर `readyUrl` चाहिए होता है, क्योंकि फ़ाइल पोल का जवाब नहीं
  देती।
- ब्राउज़र फ़ाइल को अपनी मशीन की डिस्क से पढ़ता है, इसलिए ब्राउज़र प्रोवाइडर या `connect`
  वाला `web()` टारगेट इसे मना कर देता है। इंजन फ़ाइल ऐप तभी खोलता है जब वह इसे
  [डिक्लेयर करे](/reference/engine#capabilities)।
- `agent.act` की रिकॉर्डिंग फ़ाइल के पूरे पाथ से की होती है, इसलिए यह तभी रीप्ले होती है
  जब फ़ाइल उसी पाथ पर हो।

ब्राउज़र इंजन के [`headers`](/reference/web#headers) और
[`basicAuth`](/reference/web#basicauth) का स्कोप और कड़ा होता है: `url` के ऑरिजिन
(स्कीम, होस्ट, और पोर्ट, रन के फ़्री पोर्ट समेत) और आपके लिस्ट किए गए ऑरिजिन्स तक।
[रिक्वेस्ट क्रेडेंशियल](/reference/security#request-credentials) देखें।

#### फ़्री पोर्ट

पोर्ट `0` के साथ लिटरल लूपबैक पते वाला `url` (`http://127.0.0.1:0`, `http://[::1]:0`)
रन से एक खाली TCP पोर्ट माँगता है। कॉन्फ़िग लोड होने पर रनर एक पोर्ट चुनता है। जहाँ भी
डिक्लेरेशन में यह था (बेस URL, डिफ़ॉल्ट `readyUrl`, और रिपोर्ट), वहाँ वह यह पोर्ट रख देता
है। कमांड को `args` या `env` में `{port}` के ज़रिए यह पोर्ट लेना होता है।

```ts title="e2e.config.ts"
engine: web(),
app: {
  url: 'http://127.0.0.1:0',
  command: { executable: 'pnpm', args: ['dev', '--port', '{port}'], env: { PORT: '{port}' } },
},
```

- `localhost:0` [`INVALID_APP_URL`](#url) है: यह उस पते से अलग पते पर रिज़ॉल्व हो सकता
  है जिस पर कमांड बाइंड होती है। वही पता लिखें जिस पर कमांड बाइंड होगी।
- पोर्ट `0` माँगने वाले हर टारगेट को अपना अलग पोर्ट और अपना अलग प्रोसेस मिलता है। फ़िक्स
  पोर्ट पर एक ही कमांड डिक्लेयर करने वाले दो टारगेट एक प्रोसेस शेयर करते हैं।
- डिफ़ॉल्ट [`identity`](#identity) डिक्लेयर किए गए `:0` से निकलता है।
- टेस्ट एलोकेट किया गया URL [`app.baseUrl`](/reference/app) से पढ़ते हैं।

#### services

<Note>
यह वर्ज़न कोई डिपेंडेंसी प्रोसेस (डेटाबेस, API मॉक, या कई टारगेट्स का साझा डेव सर्वर)
शुरू नहीं करता, और `services` जहाँ भी आए वह अनजान key है। उन्हें रन से पहले शुरू करें, या
`app.command` से ऐसी स्क्रिप्ट चलाएँ जो उन्हें शुरू करे और ऐप सर्व करे। services API
आगे के रिलीज़ में वापस आएगी।
</Note>

### output

वह डायरेक्टरी जिसके नीचे रन अपने बारे में जो कुछ भी लिखता है वह सब जाता है, प्रोजेक्ट रूट
से रिज़ॉल्व होकर।

```ts
output: 'test-results/e2e', // default: '.e2e'
```

[`e2e run`](/reference/cli#e2e-run) और `e2e explore` पर `--output <dir>` एक रन के लिए
इसे ओवरराइड करता है।

| output के नीचे पाथ | क्या है |
| --- | --- |
| `report.json` | मुख्य रिपोर्ट; `--last-failed` यहीं से पढ़ता है |
| `junit.xml`, `summary.md`, `ctrf.json` | `junit`, `markdown`, और `ctrf` रिपोर्टर की फ़ाइलें |
| `ai-trace.json` | `--ai-trace` |
| `timings.json` | हर फ़ाइल में कितना समय लगा, हाल के रन्स का औसत। एक से ज़्यादा वर्कर वाला रन इसी के हिसाब से सबसे लंबी फ़ाइलें पहले चलाता है; [टाइमिंग हिस्ट्री कैश करें](/ci#cache-the-timings-history) देखें |
| `report-with-reruns.json` | `--last-failed` रीरन से लिखी जाती है: पहला रन और उसके बाद के हर रीरन को एक रिपोर्ट के रूप में, `report.json` वाली ही रन id के साथ। बिना `--last-failed` वाला रन इसे हटा देता है |
| `results/` | हर टेस्ट के लिए एक डायरेक्टरी: उसका [ट्रेस पेज](/debugging#traces), `trace.md`, जब [`trace`](#trace) मोड उसे रखे, और उसके स्क्रीनशॉट, वीडियो, डाउनलोड, और लॉग, हर अटेम्प्ट के लिए एक `attempt-<n>/`। रन के टेस्ट शुरू होते ही यह साफ़ हो जाती है, ताकि इसमें ताज़ा रन के सबूत रहें और ऐसा कुछ न रहे जिसका नाम रिपोर्ट में न हो। `--last-failed` रीरन पिछले रन्स की फ़ाइलें रखता है और अपने अटेम्प्ट हर टेस्ट के `rerun-<n>/` के नीचे लिखता है |
| `sessions/` | रन के एन्क्रिप्टेड `test.setup` सेशन, जो रन खत्म होने पर डिलीट हो जाते हैं |
| `videos/<session>/` | [`e2e mcp`](/reference/mcp#recording) सेशन रिकॉर्डिंग |

- जो रन अपने टेस्ट शुरू होने से पहले ही रुक जाए, वह यहाँ कुछ नहीं लिखता। ऐसे रुकाव हैं:
  ऐसा सिलेक्शन जिससे कोई टेस्ट मैच न हो (`NO_TESTS`, गलत लिखा `--grep`), कलेक्शन एरर,
  ऐसा टारगेट जो माँगी गई चीज़ रिकॉर्ड न कर सके (`UNSUPPORTED_ARTIFACT`), `NO_LAST_RUN`,
  ऐप कमांड का शुरू न हो पाना, या इंटरप्ट। पिछले रन की `report.json`, `ai-trace.json`, और
  `results/` वैसी ही बनी रहती हैं, ताकि `--last-failed` फिर भी आखिरी चले हुए रन को पढ़ सके।
- `e2e mcp` सेशन अपने अटेम्प्ट के आर्टिफ़ैक्ट `results/mcp/` के नीचे लिखता है और इसे कभी
  साफ़ नहीं करता।
- `output` कुछ भी कहे, रीप्ले कैश [`cache.dir`](#dir) में ही रहता है, इसलिए रिज़ल्ट्स
  हटाने-बदलने से रिकॉर्डिंग नहीं हिलतीं।
- `e2e init` सिर्फ़ डिफ़ॉल्ट `.e2e/` पाथ के लिए `.gitignore` एंट्री लिखता है। `output`
  कहीं और सेट होने पर उस डायरेक्टरी को `.gitignore` में खुद जोड़ें।

रन आउटपुट डायरेक्टरी के एक हिस्से को साफ़ करता है और उसका मालिक होता है। इसलिए जब डायरेक्टरी
इनमें से कोई हो, तो कॉन्फ़िग लोड कारण बताते हुए `INVALID_CONFIG` से फ़ेल होता है:

- प्रोजेक्ट रूट हो, या उसके बाहर हो;
- कोई फ़ाइल हो, या किसी फ़ाइल के नीचे का पाथ हो (गायब डायरेक्टरी बना दी जाती है);
- कैश डायरेक्टरी (`cache.dir`, `--cache-dir`, या `E2E_CACHE_DIR`) हो या उसके अंदर हो, या
  वह `results/`, `sessions/`, या `videos/` के नीचे कैश डायरेक्टरी को रखती हो;
- ऐसी डायरेक्टरी रखती हो जिसे कोई `tests` ग्लॉब स्कैन करता है (डिफ़ॉल्ट `tests/**/*.e2e.ts`
  के साथ `output: 'tests'`)।

पाथ की तुलना सिमलिंक रिज़ॉल्व करके की जाती है। सिमलिंक से लिखा गया पूरा पाथ (macOS पर
`/private/tmp` के लिए `/tmp`) उसी डायरेक्टरी को बताता है। जिस सिमलिंक का टारगेट अभी बना
न हो उसे भी फ़ॉलो किया जाता है, इसलिए प्रोजेक्ट रूट के बाहर इशारा करने वाले सिमलिंक से
आउटपुट मना किया जाता है।

<Note>
हटाया जा चुका `--artifacts <dir>` फ़्लैग उस `--output` के नाम के साथ फ़ेल होता है जिस पर
वह मैप होता है। पहले रिपोर्ट उस डायरेक्टरी के पैरेंट में जाती थी, इसलिए
`--artifacts out/artifacts` का मतलब `--output out` है। ऐसा पैरेंट जो आउटपुट नहीं बन
सकता (प्रोजेक्ट रूट या उसके बाहर) `--output .e2e` पर मैप होता है।
</Note>

### artifacts

`artifacts` बताता है कि आर्टिफ़ैक्ट कहाँ जाएँगे, यह नहीं कि कौन से बनेंगे। `{ store }`
हर आर्टिफ़ैक्ट बनते ही उसे होस्ट स्टोर को सौंप देता है; इसके बिना फ़ाइलें सिर्फ़ लोकल रहती
हैं।

```ts
artifacts: {
  store: {
    async put(artifact) {
      const key = await bucket.upload(artifact.path, artifact.bytes);
      return { ref: key };
    },
  },
},
```

| मेंबर | क्या लौटाता है |
| --- | --- |
| [`store.put`](#put) | `Promise<{ ref }>` |
| [`store.putLink`](#putlink) | `Promise<{ ref }>` |

- [`trace` और `video`](#recording) रिकॉर्डिंग चुनते हैं। जब भी इंजन कर सके, रनर फ़ेलियर
  का स्क्रीनशॉट और स्क्रीन टेक्स्ट कैप्चर करता है।
- हर वर्कर कॉन्फ़िग मॉड्यूल से अपना स्टोर खुद बनाता है।
- फ़ेल हुआ `put` या `putLink` कभी रन को फ़ेल नहीं करता।

हटाए गए रूप `INVALID_CONFIG` से फ़ेल होते हैं और बताते हैं कि उनकी जगह क्या आया है:

| लिखा गया | अब |
| --- | --- |
| काइंड्स की लिस्ट (`artifacts: ['screenshot', 'trace']` या `artifacts.kinds`) | उसका मतलब वाला `trace` मोड |
| `record: 'retries'` के साथ `artifacts.trace` | `trace: 'on-all-retries'`, `trace` रखने वाली काइंड्स लिस्ट के साथ पढ़कर, ताकि जोड़ी का मतलब फिर भी सिर्फ़ रीट्राई रहे |
| `artifacts.video` | `video` ऑप्शन |

डिक्लेरेशन [`ArtifactsConfig`](#artifactsconfig) में हैं।

#### `put`

डिस्क पर पूरा बनते ही हर आर्टिफ़ैक्ट इसे मिलता है और यह एक रेफ़रेंस लौटाता है जिसे रिपोर्ट
लोकल पाथ के बगल में `ref` के रूप में दर्ज करती है।

```ts
async put(artifact) {
  return { ref: await bucket.upload(artifact.path, artifact.bytes) };
},
```

- हर स्टोर पर ज़रूरी है।
- `artifact.redaction` रिपोर्ट का लेबल है। जो स्टोर सिर्फ़ उन्हीं चीज़ों को एक्सपोर्ट करता
  है जिनकी गारंटी रनर देता है, वह `incomplete` आर्टिफ़ैक्ट को रोक लेता है: जैसे वीडियो या
  ऐसा डाउनलोड जिसे रनर ने दोबारा नहीं लिखा।

#### `putLink`

होस्टेड सर्विस जो वीडियो रखती है ([प्रोवाइडर की अपनी रिकॉर्डिंग](#what-a-video-writes)),
वह इसे मिलता है। ऐसा वीडियो बिना बाइट्स का लिंक होता है, इसलिए `put` को वह कभी नहीं मिलता।

```ts
async putLink(link) {
  return { ref: await index.record(link.url, link.attemptId) };
},
```

- ऑप्शनल है। अटेम्प्ट के रिकॉर्डिंग रोकने के बाद हर लिंक के लिए कॉल होता है।
- इसका `ref` रिपोर्ट के आर्टिफ़ैक्ट में `url` के बगल में आता है।
- `retain-on-failure` के तहत पास हुए अटेम्प्ट का लिंक कभी नहीं दिया जाता, क्योंकि रिपोर्ट
  भी उसे छोड़ देती है।

### रिकॉर्डिंग

`trace` और `video` एक ही सेट के मोड्स से चुनते हैं कि क्या रिकॉर्ड होगा।

```ts
trace: 'on',
video: 'retain-on-failure',
targets: [
  { name: 'chromium', engine: web(), app: { url } },
  { name: 'firefox', engine: web({ browser: 'firefox' }), app: { url }, video: 'on-first-retry' },
],
```

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |
| [`trace`](#trace) | `RecordingMode` | `'retain-on-failure'` |
| [`video`](#video) | `RecordingMode` | `'off'` |

```ts
/** Which tests keep a trace page, or which attempts record a video. */
export type RecordingMode = 'off' | 'on' | 'retain-on-failure' | 'on-first-retry' | 'on-all-retries';
```

| मोड | ट्रेस पेज | वीडियो |
| --- | --- | --- |
| `off` | कोई नहीं | कोई नहीं |
| `on` | हर टेस्ट, पास होने वाले भी | हर अटेम्प्ट |
| `retain-on-failure` | हर फ़ेल, टाइमआउट, इंटरप्ट, या फ़्लेकी टेस्ट | हर अटेम्प्ट, उनमें से जो पास न हों वे रखे जाते हैं |
| `on-first-retry` | हर वह टेस्ट जिसका पहला रीट्राई चला | सिर्फ़ पहला रीट्राई, यानी दूसरा अटेम्प्ट |
| `on-all-retries` | हर वह टेस्ट जिसे रीट्राई किया गया | पहले के बाद हर अटेम्प्ट |

ये नाम Playwright के `use.trace` और `use.video` मोड्स के हैं। रीट्राई मोड में `retries: 0`
वाला टेस्ट कुछ रिकॉर्ड नहीं करता, और न ही ऐसी फ़ेलियर जिसे रनर रीट्राई नहीं करता, जैसे
`LAUNCH_TIMEOUT`। जब ऐसा टेस्ट चलता है, तो रन प्लान के समय हर किस्म का एक नोटिस प्रिंट
करता है: उसके लिए कोई ट्रेस (या वीडियो) रिकॉर्ड नहीं होगा।

चार जगहें मोड सेट करती हैं, सबसे कम प्राथमिकता से शुरू होकर। हर अगली जगह पिछली को बदल
देती है, `trace` और `video` दोनों के लिए:

1. कॉन्फ़िग के टॉप पर `trace` या `video`।
2. टारगेट का `trace` या `video`।
3. [`e2e run`](/reference/cli#e2e-run) पर `--trace [mode]` या `--video [mode]`, जो
   कॉन्फ़िग और हर टारगेट से ऊपर होता है। सीधा फ़्लैग `on` होता है।
4. टेस्ट या describe का अपना [`trace` या `video` ऑप्शन](/reference/test#options),
   सबसे अंदर वाला जीतता है: `test('checkout', { video: 'on' }, ...)`।

- सीरियल ग्रुप एक यूनिट की तरह रिकॉर्ड होता है, इसलिए उसके मेंबर `trace` या `video` सेट
  नहीं कर सकते (`retries` की तरह `COLLECTION_ERROR`)। सीरियल `describe` या उसके बाहर के
  ग्रुप की वैल्यू हर मेंबर पर लागू होती है।
- `e2e explore` एक अटेम्प्ट होता है और टारगेट का मोड (`--trace` और `--video` समेत)
  इस्तेमाल करता है, इसलिए रीट्राई मोड वहाँ कुछ रिकॉर्ड नहीं करता।
- `e2e mcp` सेशन कोई ट्रेस नहीं लिखता और कॉन्फ़िगर किए गए मोड से वीडियो रिकॉर्ड नहीं करता।
  इसकी रिकॉर्डिंग वे होती हैं जो `start_recording` और `stop_recording` बनाते हैं।
- टॉप पर या टारगेट पर `trace` और `video` न कॉन्फ़िग डाइजेस्ट में जाते हैं और न रीप्ले की
  [कैश key](/cache#what-must-match) में। इन्हें चालू या बंद करने से कैश हुए रीप्ले कभी
  इनवैलिडेट नहीं होते।

<Note>
पुरानी ट्रेस स्पेलिंग जहाँ भी मोड जाए (कॉन्फ़िग, टारगेट, टेस्ट, `--trace`) वहाँ
`INVALID_CONFIG` से फ़ेल होती हैं और बताती हैं कि उनका कौन सा मोड मतलब था: `'all'` और
`{ record: 'all' }` का मतलब `'on'` है, और `'retries'` और `{ record: 'retries' }` का
मतलब `'on-all-retries'`।
</Note>

#### `trace`

कौन से टेस्ट ट्रेस पेज रखते हैं।

```ts
trace: 'on', // default: 'retain-on-failure'
```

- लोकली और CI में डिफ़ॉल्ट एक ही है।
- ट्रेस पेज मार्कडाउन होता है, `<output>/results/` के नीचे टेस्ट की डायरेक्टरी में
  `trace.md`, जैसे `.e2e/results/checkout-applies-the-coupon-1a2b3c4d5e6f7a8b/trace.md`:
  हर स्टेप और उसने क्या किया, कैश के फ़ैसले, ऐप ने क्या लॉग किया, और फ़ेलियर पर स्क्रीन।
- यह हर इंजन पर काम करता है। [डीबगिंग](/debugging#traces) में एक उदाहरण है।

#### `video`

कौन से अटेम्प्ट वीडियो रिकॉर्ड करते हैं।

```ts
video: 'retain-on-failure', // default: 'off'
```

- मोड कहाँ सेट किया गया है, यह तय करता है कि जो इंजन रिकॉर्ड नहीं कर सकता वह क्या करे।
  [जो इंजन रिकॉर्ड नहीं कर सकते](#engines-that-cannot-record) देखें।
- वीडियो में CPU लगता है और इसमें स्क्रीन पर जो कुछ दिखा (सीक्रेट्स समेत) सब आता है, इसलिए
  इसे हमेशा खुद माँगना होता है।

#### जो इंजन रिकॉर्ड नहीं कर सकते

कोई भी टेस्ट शुरू होने से पहले रन हर टारगेट की जाँच करता है। `video` मोड कहाँ सेट हुआ था,
उससे तय होता है कि जो इंजन वीडियो रिकॉर्ड नहीं कर सकता वह क्या करे:

- कॉन्फ़िग के टॉप पर या `--video` से सेट होने पर: मोड उन्हीं टारगेट्स पर लागू होता है
  जिनका इंजन रिकॉर्ड कर सकता है। रन प्लान के समय एक नोटिस प्रिंट करता है जिसमें न कर सकने
  वाले टारगेट्स के नाम होते हैं, और उन्हें बिना वीडियो के चलाता है।
- किसी टारगेट पर, या उस टारगेट पर चलने वाले टेस्ट पर सेट होने पर: मोड ज़रूरी होता है। जिस
  टारगेट का इंजन रिकॉर्ड न कर सके, वह `UNSUPPORTED_ARTIFACT` से रन को फ़ेल कर देता है,
  जिसमें टारगेट और (टेस्ट का होने पर) टेस्ट का नाम होता है।

सिर्फ़ वही मोड गिना जाता है जो किसी अटेम्प्ट पर रिकॉर्ड करे: जिस रन के सभी टेस्ट `off` पर
या `retries: 0` के साथ रीट्राई मोड पर रिज़ॉल्व हों, वह इंजन से कुछ नहीं माँगता।

#### वीडियो क्या लिखता है

| रिकॉर्डर | अटेम्प्ट की आर्टिफ़ैक्ट डायरेक्टरी के नीचे फ़ाइलें |
| --- | --- |
| ब्राउज़र इंजन, Playwright स्क्रीनकास्ट | `video/video.webm`, अटेम्प्ट के दिखाए हर पेज का एक सेगमेंट, बाद वाले `video/video-part<n>.webm`। [`web({ screencast })`](/reference/web#options) फ़्रेम साइज़ और क्वालिटी सेट करता है |
| मोबाइल इंजन, agent-device | `video/video.mp4` |
| प्रोवाइडर की अपनी रिकॉर्डिंग ([`BrowserProvider.record`](/browser#recording-on-the-provider), [`DeviceProvider.record`](/mobile#hosted-devices)) | प्रोवाइडर की लिखी फ़ाइल, `video/<file>` के रूप में: Kernel की `video/replay.mp4` होती है। या सर्विस से रखी रिकॉर्डिंग का लिंक, जिसे `path` की जगह `url` से दर्ज किया जाता है; रनर इसे कभी डाउनलोड नहीं करता |

- हर सेगमेंट में `startedAt` होता है, इसलिए `step.startedAt - artifact.startedAt` उसमें
  स्टेप का ऑफ़सेट होता है।
- रिकॉर्डिंग कुछ मास्क नहीं करती और `redaction: 'incomplete'` के साथ दर्ज होती है।

<Note>
`retain-on-failure` के तहत पास हुए अटेम्प्ट की रिपोर्ट में लिंक नहीं रखा जाता, लेकिन
सर्विस के पास रिकॉर्डिंग फिर भी रहती है।
</Note>

### agents

नेम्ड एजेंट, हर एक सादा ऑब्जेक्ट: बिल्ट-इन एजेंट के ऑप्शन, या कस्टम ब्रेन के लिए
`{ executor }`।

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';
import { houseBrain } from './house-brain.ts';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  agents: {
    default: { model: gateway('openai/gpt-6-luna-fast') },
    ux: { model: gateway('openai/gpt-6-luna-fast'), system: 'Check labels, contrast, and keyboard access.' },
    thorough: { model: gateway('anthropic/claude-opus-5'), context: 'Verify every claim on screen.' },
    buyer: {
      model: gateway('openai/gpt-6-luna-fast'),
      system: 'You are a first-time buyer.',
      context: 'Plans are called tiers. Billing lives under Settings.',
      maxSteps: 40,
    },
    house: { executor: houseBrain, model: gateway('openai/gpt-6-luna-fast'), maxModelCalls: 10 },
  },
} satisfies E2EConfig;
```

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |
| [`model`](#model) | `ModelInstance` | - |
| [`judge`](#judge) | `ModelInstance` | `model` |
| [`context`](#context) | `string` | - |
| [`system`](#system) | `string` | - |
| [`tools`](#tools) | `Record<string, AgentTool>` | - |
| [`executor`](#executor) | `StepExecutor` | बिल्ट-इन एजेंट |
| [`maxSteps`](#maxsteps) | `number` | `25` |
| [`maxModelCalls`](#maxmodelcalls) | `number` | `25` |
| [`judgmentTimeout`](#judgmenttimeout) | `number` | `30000` |
| [`maxObservationBytes`](#maxobservationbytes) | `number` | `262144` |
| [`maxInputTokens`](#maxinputtokens) | `number` | `64000` |
| [`providerOptions`](#provideroptions) | `ProviderOptions` | - |

- जब तक आप कोई और न चुनें (`e2e run --agent <name>`, टेस्ट या ग्रुप ऑप्शन, या
  `agent.*` कॉल से), टेस्ट `default` एजेंट इस्तेमाल करते हैं। `{ agent: ['buyer', 'admin'] }`
  वाला टेस्ट हर एजेंट के लिए एक बार चलता है।
- कॉन्फ़िग कोई एजेंट डिक्लेयर न करे तब भी `default` मौजूद रहता है, लेकिन उसके पास कोई
  मॉडल नहीं होता।
- हर एंट्री बिल्ट-इन डिफ़ॉल्ट्स से शुरू होती है। एजेंट एक-दूसरे से इनहेरिट नहीं करते:
  ऊपर वाले `ux` को `default` से `context` नहीं मिलता। किसी एंट्री में छोड़ी गई key
  डिफ़ॉल्ट वैल्यू लेती है, किसी दूसरी एंट्री की नहीं।
- हर वर्कर इस कॉन्फ़िग मॉड्यूल से अपने एजेंट खुद बनाता है।
- नामों में ASCII अक्षर, अंक, `_`, `-`, या `.` हो सकते हैं, और वे कभी सिर्फ़ डॉट्स नहीं
  होते: नाम एक आर्टिफ़ैक्ट पाथ सेगमेंट होता है।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | `--agent` फ़्लैग पर अनजान एजेंट नाम। |
| `COLLECTION_ERROR` | टेस्ट या ग्रुप पर अनजान एजेंट नाम। |
| `INVALID_ARGUMENT` | कॉल पर अनजान एजेंट नाम। |

[एजेंट्स और पर्सोना](/agents) देखें। डिक्लेरेशन [`AgentConfig`](#agentconfig) में हैं।

#### `model`

एक AI SDK मॉडल इंस्टेंस। कोई इनबिल्ट डिफ़ॉल्ट नहीं होता।

```ts
model: gateway('openai/gpt-6-luna-fast'),
```

अपने कॉन्फ़िग में किसी AI SDK प्रोवाइडर से मॉडल बनाएँ। टूल कॉल सपोर्ट करने वाला हर
प्रोवाइडर काम करता है; [AI SDK प्रोवाइडर](/models#ai-sdk-providers) देखें। सब्सक्रिप्शन
साइन-इन के लिए [`e2e/oauth/*` मॉडल](/subscriptions) इस्तेमाल करें।

| गेटवे | कंस्ट्रक्टर | पैकेज | क्या पढ़ता है |
| --- | --- | --- | --- |
| [Vercel AI Gateway](https://vercel.com/docs/ai-gateway) | `gateway('openai/gpt-6-luna-fast')` | `ai` | `AI_GATEWAY_API_KEY`, या उसके बिना Vercel OIDC टोकन |
| [OpenRouter](https://openrouter.ai/models) | `openrouter('openai/gpt-6-luna-fast')` | `@openrouter/ai-sdk-provider` | `OPENROUTER_API_KEY` |
| कोई भी OpenAI-कम्पैटिबल एंडपॉइंट | `createOpenAICompatible({ name, baseURL, apiKey? }).chatModel('llama3.2')` | `@ai-sdk/openai-compatible` | `apiKey`, जब एंडपॉइंट को ज़रूरत हो |
| सीधा प्रोवाइडर | `openai('gpt-6-luna')`, `anthropic(...)`, ... | `@ai-sdk/openai`, `@ai-sdk/anthropic`, ... | प्रोवाइडर का अपना वेरिएबल |

- रिपोर्ट हर स्टेप पर `provider` और `modelId` दर्ज करती है।
- हर वर्कर कॉन्फ़िग मॉड्यूल से अपना इंस्टेंस खुद बनाता है। रनर और वर्कर के बीच डाइजेस्ट
  अलग होने पर `CONFIG_NOT_DETERMINISTIC` आता है।
- स्ट्रिंग देने पर `INVALID_CONFIG` आता है और मैसेज बताता है कि कौन सा कंस्ट्रक्टर लिखें।
- कोई एजेंट कभी `default` के मॉडल पर फ़ॉलबैक नहीं करता। [रिज़ॉल्यूशन क्रम](#resolution-order)
  देखें।

[मॉडल](/models) और [`ModelInstance`](#modelinstance) देखें।

#### `judge`

नॉन-एक्सप्लोरिंग `assert`, `waitFor`, और `extract` के लिए मॉडल। बिल्ट-इन एक्सप्लोरिंग
असर्शन `judge` सेट होने पर भी `agents.<name>.model` इस्तेमाल करते हैं।

```ts
judge: gateway('anthropic/claude-opus-5'), // default: model
```

- परख हर कॉल पर 8192 आउटपुट टोकन अलाउ करती है।
- परख को निर्देश, उसके पैरामीटर, एजेंट का कॉन्टेक्स्ट, और लोकेशन के साथ मौजूदा स्क्रीन
  दिखती है।

[अपना अलग जज](/models#a-judge-of-its-own) देखें।

#### `context`

ऐप चीज़ों को क्या नाम देता है, जो इस एजेंट के हर मॉडल कॉल (act टर्न और परख दोनों) को
बताया जाता है।

```ts
context: 'Plans are called tiers. Billing lives under Settings.',
```

ज़्यादा से ज़्यादा 16384 बाइट्स।

#### `system`

एक्शन करने वाले एजेंट को कैसे काम करना चाहिए, जो बिल्ट-इन नियमों के अंत में जुड़ता है।
इसे सिर्फ़ act लूप पढ़ता है।

```ts
system: 'You are a first-time buyer.',
```

`executor` के साथ इसे देने पर `INVALID_CONFIG` आता है: एक्ज़ीक्यूटर अपना प्रॉम्प्ट खुद
लाता है।

#### `tools`

`defineTool` (`e2e/agent`) से बने प्रोजेक्ट टूल, जो बिल्ट-इन टूलसेट के साथ दिए जाते हैं।

```ts
tools: { lookupOrder },
```

`executor` के साथ इसे देने पर `INVALID_CONFIG` आता है: एक्ज़ीक्यूटर अपने टूल खुद लाता है।

#### `executor`

एक कस्टम ब्रेन जिसे बिल्ट-इन एजेंट के बजाय `agent.act()` कॉल करता है।

```ts
house: { executor: houseBrain, model: gateway('openai/gpt-6-luna-fast'), maxModelCalls: 10 },
```

- `model`, `judge`, `context`, और बजट फिर भी लागू रहते हैं; परख के लिए मॉडल चाहिए होता
  है। इसके साथ [`system`](#system) और [`tools`](#tools) देने पर `INVALID_CONFIG` आता है।
- `maxModelCalls` एक स्टेप के मॉडल टर्न की सीमा तय करता है।
- ऐसा `model` या `judge` जो एक्ज़ीक्यूटर के लाए मॉडल से अलग हो, वह `INVALID_CONFIG` है।

[कस्टम एक्ज़ीक्यूटर](/executors) देखें।

#### `maxSteps`

हर एजेंट कॉल पर कमिट किए गए एक्शन।

```ts
maxSteps: 40, // default: 25
```

1 से 100 तक।

#### `maxModelCalls`

हर एजेंट कॉल पर मॉडल रिक्वेस्ट।

```ts
maxModelCalls: 10, // default: 25
```

1 से 100 तक।

#### `judgmentTimeout`

एक `assert`, `waitFor`, या `extract` कॉल की डेडलाइन, मिलीसेकंड में।

```ts
judgmentTimeout: 60_000, // default: 30000
```

धीमे जज के लिए इसे बढ़ाएँ। इंजन ऑपरेशन अपना `actionTimeout` बनाए रखते हैं।

#### `maxObservationBytes`

act टर्न और परख के लिए ऑब्ज़र्वेशन पेलोड की ऊपरी सीमा।

```ts
maxObservationBytes: 524_288, // default: 262144
```

1024 से 16777216 तक।

#### `maxInputTokens`

हर मॉडल रिक्वेस्ट के लिए इनपुट टोकन।

```ts
maxInputTokens: 128_000, // default: 64000
```

- 1 से 1000000 तक।
- घनी स्क्रीन को इसके अंदर फ़िट करने के लिए छोटा कर दिया जाता है।

#### `providerOptions`

वे प्रोवाइडर ऑप्शन जो हर मॉडल कॉल के साथ जाते हैं, जैसे रीज़निंग एफ़र्ट।

```ts
providerOptions: { openai: { reasoningEffort: 'low' } },
```

जब तक यहाँ सेट न हो, OpenAI और Azure OpenAI Responses कॉल `store: false` और एक प्रॉम्प्ट
कैश key भी साथ भेजते हैं।

#### हटाए गए ऑप्शन

अनजान key (एरर सबसे क़रीबी जानी-पहचानी key का नाम बताता है), हटाई गई key, या पुराने शेप
की वैल्यू कॉन्फ़िग लोड को `INVALID_CONFIG` से फ़ेल कर देती है:

| लिखा गया | अब |
| --- | --- |
| एंट्री के रूप में सीधा `StepExecutor` | `{ executor }` |
| `timeout` | `judgmentTimeout` |
| `maxTurns` (एंट्री या `createToolLoopExecutor` पर) | `maxModelCalls` |
| टॉप-लेवल `limits.maxModelTokensPerCall` | हर एजेंट पर `maxInputTokens` |
| टॉप-लेवल `limits.maxAgentContextBytes`, `maxLedgerBytes`, `maxEventsPerStep` | हटा दिए गए; रनर इन्हें 16384 बाइट्स, 8192 बाइट्स, और 1000 इवेंट्स पर फ़िक्स रखता है |

### filters

[टेस्ट फ़िल्टर](/filters) जो उन टेस्ट्स को छोड़ देते हैं जिन पर बदलाव का असर नहीं पड़
सकता; जब रन `--changed-since` पास करता है तो ये क्रम में लागू होते हैं।

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';
import { decisionFilter } from '@e2e-dev/decision';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  filters: [decisionFilter({ model: gateway.decisionModel('typesafe-ai/jev') })],
} satisfies E2EConfig;
```

कौन से टेस्ट हमेशा चलते हैं, यह [टेस्ट फ़िल्टर](/filters#what-always-runs) पर बताया गया
है। `name` टारगेट के नाम के नियमों पर चलता है, अधिकतम 256 कैरेक्टर का होता है, और
`filters` में अनूठा होता है।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | गलत `name`, ऐसा आइटम जो `{ name, filter }` न हो, या `decisionFilter({ model })` की जगह सीधा `decisionFilter` फ़ंक्शन। |

डिक्लेरेशन [`TestFilter`](#testfilter) में हैं, जो `e2e` से एक्सपोर्ट होता है।

### credentials

नेम्ड अकाउंट। हर एंट्री में एक यूज़रनेम और एक पासवर्ड होता है जिसे मॉडल कभी नहीं देखता।

```ts
credentials: {
  admin: { username: 'admin@example.com', password: () => readFile('.secrets/admin', 'utf8') },
},
```

| फ़ील्ड | टाइप |
| --- | --- |
| [`username`](#username) | `string` |
| [`password`](#password) | `string \| SecretProvider` |

- क्रेडेंशियल और सीक्रेट अलग-अलग नेमस्पेस हैं। `secrets.get(name)` सिर्फ़ `secrets`
  एंट्री लौटाता है। क्रेडेंशियल का पासवर्ड सिर्फ़ `credentials.user(name).password` से
  मिलता है।
- एजेंट, रीप्ले कैश, और रिपोर्ट उस पासवर्ड को `<name>.password` नाम के सीक्रेट
  (`<secret:admin.password>`) के रूप में जानते हैं। इसलिए `credentials.admin` और
  `secrets.admin` दोनों एक साथ रह सकते हैं।

| थ्रो करता है | कब |
| --- | --- |
| `INVALID_CONFIG` | `admin` क्रेडेंशियल के साथ ठीक `admin.password` नाम की `secrets` एंट्री। |
| `INVALID_CONFIG` | दो क्रेडेंशियल जिनके नाम एक ही `E2E_USER_<NAME>_*` ओवरराइड पर मैप हों, जैसे `svc-a` और `svc_a` ([एनवायरनमेंट वेरिएबल](/reference/environment) देखें)। |

[ऑथेंटिकेशन](/authentication) देखें। डिक्लेरेशन [`CredentialConfig`](#credentialconfig)
में हैं।

#### `username`

अकाउंट का सादा यूज़रनेम।

```ts
username: 'admin@example.com',
```

`E2E_USER_<NAME>_USERNAME` कॉन्फ़िग वैल्यू से ऊपर रहता है। दोनों न होने पर एंट्री
`INVALID_CONFIG` होती है।

#### `password`

अकाउंट का पासवर्ड: एक स्थिर वैल्यू, या `SecretProvider` फ़ंक्शन।

```ts
password: () => readFile('.secrets/admin', 'utf8'),
```

- स्थिर पासवर्ड [सीक्रेट](#secrets) की तरह कम से कम 6 कैरेक्टर (कोड पॉइंट) का होना चाहिए,
  वरना `INVALID_CONFIG` आता है।
- `SecretProvider` हर ऑथराइज़्ड फ़िल पर चलता है (वॉल्ट लुकअप, ताज़ा बना TOTP)। कॉन्फ़िग
  डाइजेस्ट इसे सिर्फ़ नाम से दर्ज करता है। 6 से कम कैरेक्टर लौटाने वाला प्रोवाइडर फ़िल को
  `AUTH_CREDENTIAL_UNAVAILABLE` से फ़ेल कर देता है।
- `E2E_USER_<NAME>_PASSWORD` दोनों से ऊपर रहता है।

#### `credentials.user()`

टेस्ट में किसी कॉन्फ़िगर की गई एंट्री को `Credential` में रिज़ॉल्व करता है।

```ts
const admin = credentials.user('admin');
```

- यूज़रनेम सादा स्ट्रिंग होता है। पासवर्ड एक ओपेक `Secret` होता है जिसे टेस्ट कोड नहीं पढ़
  सकता, और जिसे सिर्फ़ `locator.fill` और `agent.act` के पैरामीटर लेते हैं।
- बिना कॉन्फ़िगर किया नाम `AUTH_CREDENTIAL_UNAVAILABLE` थ्रो करता है।

### secrets

नाम वाली वैल्यू जिन्हें मॉडल को कभी नहीं देखना चाहिए: API key, टोकन, एनवायरनमेंट से आने
वाली कोई भी चीज़।

```ts
secrets: {
  apiKey: () => readFile('.secrets/api-key', 'utf8'),
},
```

| एंट्री | उदाहरण | कब जाँच होती है |
| --- | --- | --- |
| स्थिर वैल्यू | `'sk_test_51Hx…'` | कॉन्फ़िग लोड पर |
| प्रोवाइडर | `() => readFile('.secrets/api-key', 'utf8')` | हर ऑथराइज़्ड फ़िल पर |

- प्रोवाइडर हर ऑथराइज़्ड फ़िल पर चलता है (वॉल्ट लुकअप, ताज़ा बना TOTP)। कॉन्फ़िग
  डाइजेस्ट इसे सिर्फ़ नाम से दर्ज करता है।
- `E2E_SECRET_<NAME>` ओवरराइड दोनों से ऊपर रहता है।
- हर एंट्री को कम से कम 6 कैरेक्टर (कोड पॉइंट) की स्ट्रिंग या फ़ंक्शन पर रिज़ॉल्व होना
  चाहिए; बाकी कुछ भी `INVALID_CONFIG` होता है। फ़िल के समय प्रोवाइडर की वैल्यू पर भी
  यही न्यूनतम सीमा लागू होती है, गड़बड़ी पर `SECRET_UNAVAILABLE` आता है।
- यह न्यूनतम सीमा रेडैक्शन के लिए है। वैल्यू जहाँ भी आए वह `<secret:name>` बन जाती है,
  इसलिए छोटी वैल्यू रिपोर्ट और आउटपुट के आम शब्दों को भी बदल देती।
- दो एंट्रीज़ जिनके नाम एक ही वेरिएबल पर मैप हों (जैसे `api-key` और `api_key`), वे
  `INVALID_CONFIG` होती हैं।

डिक्लेरेशन [`SecretConfig`](#secretconfig) में हैं।
[पासवर्ड के अलावा सीक्रेट्स](/authentication#secrets-that-are-not-passwords) देखें।

#### `secrets.get()`

कॉन्फ़िगर की गई एंट्री के लिए ओपेक `Secret` लौटाता है।

```ts
await screen.getByLabel('API key').fill(secrets.get('apiKey'));
```

- इसका कोई प्लेनटेक्स्ट एक्सेसर नहीं होता और इसे सिर्फ़ `locator.fill` और `agent.act`
  के पैरामीटर लेते हैं।
- रनर फ़ील्ड में वैल्यू भरता है, हर ऑब्ज़र्वेशन में उसे मास्क करता है, और लॉग्स, ट्रेस,
  और रिपोर्ट से उसे छिपाता है।
- बिना कॉन्फ़िगर किया नाम `SECRET_UNAVAILABLE` थ्रो करता है।

#### इंजन ऑप्शन में सीक्रेट्स

जब `e2e.config.ts` इवैल्यूएट होता है (किसी भी रन से पहले), तब `secrets.get(name)` नाम से
एक रेफ़रेंस लौटाता है जिसे कोई इंजन ऑप्शन रख सकता है।

```ts
engine: web({ basicAuth: { username, password: secrets.get('previewPassword') } }),
```

- इंजन इसे डिक्लेयर करता है। जब उस नाम की कोई `secrets` एंट्री न हो, तो कॉन्फ़िग लोड
  `INVALID_CONFIG` से फ़ेल हो जाता है। क्रेडेंशियल का पासवर्ड इसमें नहीं आता: इंजन ऑप्शन
  को जो वैल्यू चाहिए उसे `secrets` में डिक्लेयर करें।
- हर अटेम्प्ट शुरू होने पर इंजन वैल्यू रिज़ॉल्व करता है, इसलिए प्रोवाइडर हर बार दोबारा
  चलता है। फिर वह वैल्यू अटेम्प्ट के रेडैक्शन में जुड़ जाती है। यह पेज पर नहीं बल्कि इंजन
  को जाती है, इसलिए इसमें फ़िल वाले स्क्रीनशॉट प्रतिबंध नहीं लगते।
- डाइजेस्ट सिर्फ़ नाम दर्ज करता है।
- रेफ़रेंस खुद वैल्यू नहीं होता। इसे स्ट्रिंग में बदलने पर (टेम्पलेट लिटरल, `String()`,
  `+`, `JSON.stringify`) `INVALID_CONFIG` थ्रो होता है। यही बात `app.command` की `args`
  एंट्री या `env` वैल्यू में रेफ़रेंस देने पर भी लागू होती है, क्योंकि वे सिर्फ़ स्ट्रिंग
  और प्लेसहोल्डर लेते हैं। जिस वैल्यू को स्ट्रिंग में चाहिए (जैसे ऐप की API key), उसे
  खुद `process.env` से पढ़ें।

### cache

रीप्ले कैश का मोड या ऑप्शन। `read-write` मोड में रीप्ले कैश `agent.act()` को तभी
रिकॉर्ड करता है जब उसके बाद की कोई जाँच पास हो जाए, जैसे लोकेटर असर्शन या
`agent.assert()`।

```ts
cache: { mode: 'read-write', dir: '.e2e/cache', strict: true },
```

| ऑप्शन | टाइप | डिफ़ॉल्ट |
| --- | --- | --- |
| [`mode`](#mode) | `CacheMode` | `'read-write'`, CI में `'read-only'` |
| [`store`](#store) | `CacheStore` | `dir` पर फ़ाइल स्टोर |
| [`dir`](#dir) | `string` | `'.e2e/cache'` |
| [`strict`](#strict) | `boolean` | `false` |

सीधी स्ट्रिंग `{ mode }` का शॉर्टहैंड है: `cache: 'read-only'`। [कैशिंग](/cache) देखें।
डिक्लेरेशन [`CacheConfig`](#cacheconfig) में हैं।

#### `mode`

रीप्ले कैश क्या पढ़ता और लिखता है।

```ts
cache: 'read-write', // default: 'read-write' locally, 'read-only' in CI
```

| मोड | क्या करता है |
| --- | --- |
| `'read-write'` | एंट्रीज़ रीप्ले करता है और नई रिकॉर्ड करता है। |
| `'read-only'` | मौजूदा एंट्रीज़ रीप्ले करता है और कोई नई नहीं लिखता। |
| `'off'` | दोनों बंद रखता है। |

- साफ़-साफ़ दिया गया मोड डिफ़ॉल्ट को ओवरराइड करता है। जब CI अपनी कैश सर्विस से कैश
  रिस्टोर करता हो, तो `'read-write'` साफ़-साफ़ सेट करें।
- `--no-cache` दोनों से ऊपर रहता है और उस रन के लिए कैशिंग बंद कर देता है।

#### `store`

कस्टम एंट्री स्टोर जो फ़ाइल स्टोर की जगह लेता है।

```ts
cache: { store: createStore(cacheUrl) },
```

- हर वर्कर अपना स्टोर खुद बनाता है।
- CI डिमोशन से बाहर रहता है: यह `writable` के ज़रिए अपना भरोसा खुद बताता है।
- इसके साथ `--cache-dir` देने पर `INVALID_CONFIG` आता है, और `E2E_CACHE_DIR` नज़रअंदाज़
  होता है।

`CacheStore`, `CacheReadResult`, `TraceEntry`, और `ActionTrace` `e2e` से एक्सपोर्ट
होते हैं।

#### `dir`

फ़ाइल स्टोर की डायरेक्टरी, प्रोजेक्ट रूट के हिसाब से रिज़ॉल्व होकर।

```ts
cache: { dir: '.cache/e2e' }, // default: '.e2e/cache'
```

- `output` कुछ भी कहे, यह वहीं रहती है जहाँ सेट की गई है।
- `--cache-dir` और `E2E_CACHE_DIR` इसे बदल देते हैं।

#### `strict`

जिस स्टेप की रिकॉर्डिंग मौजूद है लेकिन अब रीप्ले नहीं हो पा रही, उसे एजेंट को सौंपने के
बजाय `REPLAY_STALE` से फ़ेल कर देता है।

```ts
cache: { strict: true }, // default: false
```

- `--strict-cache` एक रन के लिए इसे चालू करता है।
- तब रन कभी कैश में नहीं लिखता।

[पुरानी पड़ चुकी रिकॉर्डिंग पर फ़ेल करें](/cache#fail-on-a-stale-recording) देखें।

#### रीप्ले कैश कमिट करना

`e2e init` `.gitignore` में `.e2e/cache/` जोड़ता है, इसलिए एंट्रीज़ कमिट करना आपकी मर्ज़ी
पर है। CI और टीम के साथियों के साथ रीप्ले शेयर करने के लिए वह लाइन हटा दें। जब तक
`cache: 'read-write'` सेट न हो, CI `read-only` ही रहता है।
[कैशिंग](/cache#commit-the-replay-cache) देखें।

## रन की सीमाएँ

रिपोर्ट का `run.limits` ब्लॉक वे ऊपरी सीमाएँ दर्ज करता है जो रन ने लागू कीं। कोई `limits`
की नहीं होती: दो फ़ील्ड एजेंट्स से आते हैं, और बाकी रनर खुद फ़िक्स रखता है।

| रिपोर्ट फ़ील्ड | वैल्यू |
| --- | --- |
| `maxAgentContextBytes` | 16384: एजेंट का `context` और टेस्ट का `agentContext` |
| `maxLedgerBytes` | 8192: पिछले स्टेप्स का लेजर जिसे act स्टेप पढ़ता है |
| `maxEventsPerStep` | 1000: हर स्टेप पर दर्ज होने वाले इवेंट |
| `maxObservationBytes` | सबसे बड़ा `agents.<name>.maxObservationBytes` |
| `maxModelTokensPerCall` | सबसे बड़ा `agents.<name>.maxInputTokens` |

पर-कॉल ऑप्शन एजेंट के बजट को सिर्फ़ कम कर सकते हैं।

## एनवायरनमेंट वेरिएबल

रनर एक तय सेट पढ़ता है, जिसकी सूची [एनवायरनमेंट वेरिएबल](/reference/environment) पेज पर
है। `E2E_USER_<NAME>_USERNAME` और `E2E_USER_<NAME>_PASSWORD` किसी क्रेडेंशियल को,
`E2E_SECRET_<NAME>` किसी सीक्रेट को ओवरराइड करते हैं, और `CI` नीचे दिए डिफ़ॉल्ट बदल देता
है।

### रिज़ॉल्यूशन क्रम

| सेटिंग | क्रम |
| --- | --- |
| बेस URL | टारगेट का `app.url`, वरना पहले नेविगेशन पर `APP_URL_REQUIRED`। रनर कोई `APP_URL` नहीं पढ़ता; स्कैफ़ोल्ड किया गया कॉन्फ़िग खुद उसे पढ़ता है |
| बिल्ट-इन एजेंट मॉडल | `agents.<name>.model`, फिर `agent` लेते समय `MODEL_UNAVAILABLE`; एजेंट कभी `default` के मॉडल पर फ़ॉलबैक नहीं करता |
| कस्टम एक्ज़ीक्यूटर मॉडल | `agents.<name>.model`, वरना एक्ज़ीक्यूटर का लाया मॉडल; दो अलग वैल्यू होने पर `INVALID_CONFIG` |
| मॉडल क्रेडेंशियल | प्रोवाइडर पैकेज का अपना वेरिएबल या बनाते समय पास की गई key, जिसे प्रोवाइडर पहले मॉडल कॉल पर पढ़ता है |
| क्रेडेंशियल यूज़रनेम और पासवर्ड | `E2E_USER_*` वेरिएबल, फिर कॉन्फ़िग वैल्यू |

बिल्ट-इन एजेंट हर रन में एक बार गायब मॉडल की जाँच करता है, जब पहली बार `agent` फ़िक्स्चर
लिया जाता है, और एग्ज़िट 2 के साथ रन रोक देता है। कस्टम [एक्ज़ीक्यूटर](#executor) बिना
मॉडल के `act` और `assert` चला सकता है। `waitFor` और `extract` को फिर भी मॉडल चाहिए।

### CI

जब तक `CI` अनसेट, खाली, `0`, या `false` न हो, CI मोड चालू रहता है।

| सेटिंग | लोकल | CI |
| --- | --- | --- |
| `retries` | `0` | `1` |
| `workers` | `max(1, floor(availableParallelism() / 2))` | `1` |
| `cache` | `read-write` | अनसेट होने पर `read-only` |
| `test.only` | अलाउ है | `ONLY_IN_CI`, एग्ज़िट कोड 2 |
| `command.reuseExisting` | माना जाता है | नोटिस के साथ नज़रअंदाज़ |

## लोडिंग

रनर कॉन्फ़िग कैसे ढूँढता है और उसे और उसके इम्पोर्ट किए गए फ़ाइलों को कैसे लोड करता है।

### कॉन्फ़िग फ़ाइल ढूँढना

- `--config <path>` सीधे एक फ़ाइल चुनता है।
- वरना रनर वर्किंग डायरेक्टरी और हर पैरेंट में `e2e.config.ts`, `e2e.config.mts`,
  `e2e.config.js`, या `e2e.config.mjs` खोजता है, और रिपॉज़िटरी रूट पर रुक जाता है।
- एक ही डायरेक्टरी में TypeScript कॉन्फ़िग JavaScript कॉन्फ़िग पर भारी पड़ता है, इसलिए
  `e2e.config.ts` के बगल में `tsc` से बनाई गई `e2e.config.js` नज़रअंदाज़ होती है।
- एक ही डायरेक्टरी में दोनों TypeScript नाम या दोनों JavaScript नाम होने पर
  `CONFIG_AMBIGUOUS` आता है।
- चुनी गई फ़ाइल की डायरेक्टरी प्रोजेक्ट रूट बनती है।

### `.env` फ़ाइलें

e2e खुद कोई `.env` फ़ाइल लोड नहीं करता। `e2e.config.ts` के ऊपर Node के
`process.loadEnvFile()` से एक लोड करें। हर वर्कर कॉन्फ़िग को फिर से इम्पोर्ट करता है,
इसलिए वेरिएबल वर्कर्स तक भी पहुँच जाते हैं:

```ts title="e2e.config.ts"
process.loadEnvFile('.env');
```

फ़ाइल न मिलने पर यह थ्रो करता है; जब सिर्फ़ कुछ मशीनों पर यह फ़ाइल हो, तो `node:fs` के
`existsSync` से गार्ड लगाएँ। पाथ उस डायरेक्टरी के हिसाब से रिज़ॉल्व होता है जहाँ से e2e
चलता है, लेकिन वर्कर कॉन्फ़िग की डायरेक्टरी में शुरू होते हैं। किसी सबडायरेक्टरी से चलाने
के लिए इसकी जगह `new URL('.env', import.meta.url)` पास करें।

### मॉड्यूल फ़ॉर्मेट

- सबसे क़रीबी `package.json` का `type` कुछ भी कहे, कॉन्फ़िग और टेस्ट फ़ाइलें ESM के रूप
  में चलती हैं। उनसे जुड़ने वाली हर `.ts`, `.mts`, `.tsx`, और `.jsx` फ़ाइल भी: पाथ से
  इम्पोर्ट किया हेल्पर, नाम से अपना `.ts` सोर्स एक्सपोर्ट करने वाला पैकेज, या किसी
  CommonJS फ़ाइल से require की गई `.ts` फ़ाइल।
- `.cts` फ़ाइल CommonJS होती है, जिसे `require`, `import x = require()`, और `export =`
  के साथ लिखा जाता है; इसके `import` स्टेटमेंट `require` कॉल में नहीं बदले जाते।
- `require` या `module.exports` के साथ लिखी `.ts` फ़ाइल लोड नहीं होती: उसे `.cts` नाम दें।
- JavaScript वही फ़ॉर्मेट रखता है जो उसका पैकेज डिक्लेयर करता है।

### JavaScript

कॉन्फ़िग और टेस्ट बिना `tsconfig.json` के सादा JavaScript भी हो सकते हैं:

```js title="e2e.config.js"
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';

/** @type {import('e2e').E2EConfig} */
export default {
  tests: 'tests/**/*.e2e.js',
  agents: { default: { model: gateway('openai/gpt-6-luna-fast') } },
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
};
```

- कॉन्फ़िग का नाम `e2e.config.js` या `e2e.config.mjs` रखें
  ([कॉन्फ़िग फ़ाइल ढूँढना](#finding-the-config-file))।
- ES मॉड्यूल लिखें। `package.json` में `"type": "module"` सेट करें, या फ़ाइलों का नाम
  `.mjs` रखें। दोनों न होने पर Node.js हर लोड पर चेतावनी देता है कि उसने फ़ाइल को फिर से
  ESM की तरह पार्स किया।
- [`tests`](#tests) सेट करें: डिफ़ॉल्ट सिर्फ़ `*.e2e.ts` चुनता है। `.mjs` टेस्ट्स के लिए
  `'tests/**/*.e2e.mjs'` इस्तेमाल करें। सूट माइग्रेट करते समय दोनों किस्म चलाने के लिए
  `'tests/**/*.e2e.ts'` भी साथ लिखें।
- `@type` कमेंट `satisfies E2EConfig` जैसा काम करता है: एडिटर keys पूरा करता है और उनका
  डॉक्यूमेंटेशन दिखाता है। टेस्ट फ़िक्स्चर को बिना किसी एनोटेशन के `test` इम्पोर्ट से अपने
  टाइप मिल जाते हैं।
- रनर कभी टाइप-चेक नहीं करता। एडिटर एरर के लिए फ़ाइल में `// @ts-check` जोड़ें, या
  `jsconfig.json` में `"checkJs": true`।
- JavaScript फ़ाइल TypeScript हेल्पर को उसके `.ts` नाम (`'./helpers.ts'`) से इम्पोर्ट
  करती है, `.js` से नहीं; [इम्पोर्ट रिज़ॉल्यूशन](#import-resolution) देखें। `checkJs` के
  तहत उस इम्पोर्ट को `"allowImportingTsExtensions": true` और `"noEmit": true` भी
  चाहिए।

### इम्पोर्ट रिज़ॉल्यूशन

e2e खुद TypeScript और JSX कंपाइल करता है। ऐसी फ़ाइल में इम्पोर्ट उसी तरह रिज़ॉल्व होता है
जैसे TypeScript करता है:

- `./helper.js` और `./helper` `helper.ts` लोड करते हैं, और `./view.jsx` `view.tsx` लोड
  करता है।
- `./lib` उस फ़ाइल को लोड करता है जिसे `lib/package.json` `main` बताता है, वरना
  `lib/index.ts`।
- ऐसा बेयर इम्पोर्ट जिसे `tsconfig.json` `paths` या `baseUrl` से मैप करता है, मैप की गई
  फ़ाइल लोड करता है।
- ऐसा `#` इम्पोर्ट या पैकेज एक्सपोर्ट जो गायब `./x.js`, `./x.jsx`, या `./x` का नाम दे,
  इम्पोर्ट करने पर उसका `x.ts` या `x.tsx` सोर्स लोड करता है।
- ऐसा `#` इम्पोर्ट या पैकेज एक्सपोर्ट जो किसी डायरेक्टरी का नाम दे, या बिना `exports` वाले
  पैकेज का ऐसा सबपाथ जो डायरेक्टरी हो (`@acme/db/enums`), वह `./lib` की तरह लोड होता है।
  Yarn PnP के तहत वह पैकेज सबपाथ फिर भी फ़ेल होता है।
- आखिरी दोनों में से किसी का भी `require()` वैसे ही फ़ेल होता है जैसे Node.js रिपोर्ट करता
  है।
- JavaScript फ़ाइल में लिखा इम्पोर्ट वैसे ही रिज़ॉल्व होता है जैसे Node.js करता है।

### `tsconfig.json`

- फ़ाइल के ऊपर सबसे क़रीबी `tsconfig.json` लिया जाता है। जब उसमें `references` हों और वह
  खुद उस फ़ाइल को शामिल न करे (जैसा Vite लिखता है), तो वह ट्रांज़िटिवली रेफ़रेंस किया गया
  कॉन्फ़िग लिया जाता है जो उसे शामिल करता है।
- रेफ़रेंस डिक्लेरेशन के क्रम में देखे जाते हैं, और साइकिल छोड़ दी जाती हैं। अगर कोई भी
  फ़ाइल का मालिक न हो, तो सबसे क़रीबी कॉन्फ़िग फ़ॉलबैक बना रहता है।
- e2e हर प्रोसेस में एक बार (और `e2e mcp` के हर नए सेशन के लिए फिर से) इसके `paths`,
  `baseUrl`, `jsx`, `jsxFactory`, `jsxFragmentFactory`, `jsxImportSource`,
  `experimentalDecorators`, `emitDecoratorMetadata`, `useDefineForClassFields` (और
  `target`, जो इसका डिफ़ॉल्ट सेट करता है), और `verbatimModuleSyntax` पढ़ता है।
- जो `tsconfig.json` e2e न पढ़ सके (जैसे ऐसा जो किसी ऐसे पैकेज को `extends` करे जो इंस्टॉल
  नहीं है), उसे चेतावनी के साथ छोड़ दिया जाता है।
- इंस्टॉल किए गए पैकेज के अंदर का TypeScript प्रोजेक्ट के `tsconfig.json` के बिना कंपाइल
  होता है।

### क्या कंपाइल नहीं होता

- e2e फ़ाइल और लाइन का नाम बताते हुए दो चीज़ों को मना कर देता है जिन्हें वह कंपाइल नहीं कर
  सकता: ऑटो-एक्सेसर (`accessor x = 1`) और `experimentalDecorators` के बिना डेकोरेटर।
- हर फ़ाइल बिना टाइप जानकारी के अपने आप कंपाइल होती है। इसलिए `import type` के बिना
  इम्पोर्ट किया गया टाइप तब लोड होने में फ़ेल होता है जब वह इम्पोर्ट आउटपुट में बना रहे
  (`emitDecoratorMetadata` के तहत डेकोरेटेड मेंबर का टाइप, या री-एक्सपोर्ट किया टाइप)।
  एरर उस इम्पोर्ट का नाम बताता है जिसे बदलना है।
- `with { type: 'json' }` के बिना इम्पोर्ट की गई JSON फ़ाइल अपने पार्स किए गए कंटेंट को
  डिफ़ॉल्ट एक्सपोर्ट के रूप में लोड करती है।
- स्टैक ट्रेस और फ़ेलियर लोकेशन TypeScript सोर्स की तरफ़ इशारा करते हैं, किसी दूसरे लोडर
  के सोर्स मैप के पार भी (`NODE_OPTIONS=--import tsx`)।

interface TestFilter {

  readonly projectRoot: string;

  readonly changes: TestFilterChanges;
  /** The config file the run loaded, relative to `changes.root` like `changes.files`; `undefined` for a config object or one outside the repository. */
  readonly configFile?: string | undefined;
  /** Aborts when the run is interrupted, or with a `TimeoutError` after 5 minutes. */
  readonly signal: AbortSignal;
  /** Prints one progress line. */
  log(line: string): void;
  /** Replaces every fixed-value secret and credential password in `text`, and any run of 8 or more consecutive characters of one. */
  redact(text: string): string;
}

  readonly base: string;
  /** Absolute path of the repository root, spelled as on disk like `projectRoot`. */
  readonly root: string;
  /** Repository-relative POSIX paths of every changed file, uncommitted and untracked files included. Sorted, never empty. */
  readonly files: readonly string[];

  /** The tests to leave out, by `id`, each with a non-empty reason the report shows. An `id` of a collected test this filter wasn't given is ignored; any other fails the filter. */
  readonly exclude: Readonly<Record<string, string>>;
  /** How likely each test is to fail on this change, by `id` as for `exclude`, from 0 to 1; any other score fails the filter. Each target starts the files of the likeliest first, in bands at 75%, 50%, and 25%, and targets go by the band of their best file, ties in config order. A test no filter scores counts as 0, and a test several filters score keeps its highest. */

  readonly note?: string;

`TestFilter`, `TestFilterCandidate`, `TestFilterContext`, `TestFilterChanges`, और
`TestFilterResult` `e2e` से एक्सपोर्ट होते हैं।

जो फ़िल्टर थ्रो करे, इनवैलिड रिज़ल्ट लौटाए, या 5 मिनट से ज़्यादा चले, वह किसी टेस्ट को
बाहर नहीं करता और चेतावनी देता है। जो एरर वह थ्रो करे, उसमें `TestFilterResult` के शेप
में `relevance` हो सकता है: रन फिर भी सबसे ज़्यादा संभावना वाले टेस्ट्स पहले चलाता है।
[टेस्ट फ़िल्टर](/filters#write-your-own) देखें।

/** Replay cache options. */
export interface CacheConfig {

  store?: CacheStore;

/** Where the replay cache keeps its entries: the file store by default, or a host's own through `cache.store`. */
export interface CacheStore {
  readonly writable: boolean;
  read(keyHash: string): Promise<CacheReadResult>;
  /** Persists one trace, returning its size, or undefined when not written. */
  write(keyHash: string, payload: ActionTrace): Promise<{ bytes: number } | undefined>;
  /**
   * Evicts one entry, best-effort. Called when a replayed or just-recorded
   * flow is implicated in a failed attempt: the entry re-records on the next
   * pass instead of replaying a poisoned flow forever. Optional: a store
   * without eviction merely stays stale until the next confirmed write.
   */
  delete?(keyHash: string): Promise<void>;
}

export type CacheReadResult =
  | { readonly status: 'hit'; readonly entry: TraceEntry; readonly bytes: number }
  | { readonly status: 'miss' }
  | { readonly status: 'invalid'; readonly reason: string; readonly bytes?: number };
