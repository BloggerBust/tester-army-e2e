`e2e mcp` Claude Code और Cursor जैसे कोडिंग एजेंट को टेस्ट लिखते समय आपके ऐप
की जाँच करने, लोकेटर आज़माने, टेस्ट लाइन चलाने, और मास्क्ड स्क्रीनशॉट लेने देता
है। यह stdio पर चलता है और प्रोजेक्ट का कॉन्फ़िगर किया हुआ इंजन इस्तेमाल करता है।
सेटअप और एजेंट से क्या कहना है, इसके लिए [MCP सर्वर गाइड](/mcp-server) देखें।

```json title=".mcp.json"
{
  "mcpServers": {
    "e2e": { "command": "npx", "args": ["e2e", "mcp"] }
  }
}
```

चार MCP टूल सेशन को मैनेज करते हैं और उसके उपलब्ध ऐप टूल कॉल करते हैं। जब भी कोई
सेशन खुलता है, ऐप टूल कैटलॉग कॉन्फ़िग से फिर से लोड होता है।

## रेफ़रेंस

### फ़्लैग

<CodeGroup>
```bash npm
npx e2e mcp [--config <path>] [--target <name>] [--headed] [--max-sessions <n>]
```

```bash pnpm
pnpm exec e2e mcp [--config <path>] [--target <name>] [--headed] [--max-sessions <n>]
```

```bash bun
bunx e2e mcp [--config <path>] [--target <name>] [--headed] [--max-sessions <n>]
```
</CodeGroup>

| फ़्लैग | डिफ़ॉल्ट |
| --- | --- |
| [`--config <path>`](#config) | `e2e run` की तरह खोजा गया |
| [`--target <name>`](#target) | एकमात्र टारगेट |
| [`--headed`](#headed) | हेडलेस |
| [`--max-sessions <n>`](#max-sessions) | `4`, Bun पर `1` |

#### `--config`

वह कॉन्फ़िग जिसे हर सेशन लोड करता है, जब तक `open_session` किसी दूसरे का नाम न
दे। हर सेशन इसे सर्वर के एनवायरनमेंट के साथ नए सिरे से लोड करता है
([कई सेशन](#several-sessions)): कॉन्फ़िग में `process.env` वे वेरिएबल पढ़ता है
जिनके साथ MCP क्लाइंट ने `e2e mcp` शुरू किया, न कि एजेंट का शेल।

#### `--target`

वह टारगेट जिस पर सेशन खुलता है जब `open_session` किसी का नाम न दे।

- इसके और किसी नाम के बिना एकमात्र टारगेट इस्तेमाल होता है।
- कई टारगेट हों और कोई नाम न हो, तो `TARGET_REQUIRED` आता है।

#### `--headed`

जब इंजन सपोर्ट करे, तो हर उस सेशन में ब्राउज़र या सिम्युलेटर दिखाता है जिसके
`open_session` ने `headed` सेट नहीं किया है।

- `e2e run` की तरह सेशन डिफ़ॉल्ट रूप से हेडलेस होते हैं।

#### `--max-sessions`

एक साथ कितने सेशन खुले रह सकते हैं, 1 से 16 तक। [Bun](/reference/cli#bun) पर
एक। [कई सेशन](#several-sessions) देखें।

```bash
e2e mcp --max-sessions 8 # default: 4
```

### टूल

| टूल | विवरण |
| --- | --- |
| [`open_session`](#open_session) | सेशन खोलता है |
| [`tools`](#tools-2) | कैटलॉग या एक टूल दिखाता है |
| [`call`](#call) | कैटलॉग का एक टूल चलाता है |
| [`close_session`](#close_session) | सेशन और उसका इंजन बंद करता है |

जब ठीक एक ही सेशन खुला हो, तो `session` छोड़ सकते हैं।
[कई सेशन](#several-sessions) देखें।

#### `open_session`

बिना `attach` के, टारगेट के कॉन्फ़िग, इंजन, और ऐप कमांड से नया अटेम्प्ट शुरू
करता है। ऐप अपने URL पर खुलता है या डिवाइस पर [पिन किए गए ऐप](/mobile#point-at-your-app)
से नए सिरे से शुरू होता है। यह कोई बिल्ड इंस्टॉल नहीं करता, इसलिए लोकल डिवाइस
टारगेट को `app.bundleId` चाहिए। यह सेशन id, कैटलॉग, और पहला ऑब्ज़र्वेशन लौटाता
है। वहाँ कैटलॉग हर सिंगल एक्शन को सिर्फ़ नाम और आर्ग्युमेंट के साथ दिखाता है;
[`tools`](#tools-2) हर एक का ब्यौरा देता है। ऑब्ज़र्वेशन के ऊपर की समरी एजेंट को
टेस्ट लिखने या एडिट करने से पहले `writing-tests` गाइड (`e2e://guide/writing-tests`)
पढ़ने को कहती है; सर्वर के निर्देश भी यही कहते हैं।

समरी में ऐप का URL (अगर फ़्री-पोर्ट `url` है तो मिले हुए पोर्ट के साथ) और ऐप
कमांड का नाम आता है: उसका एक्ज़ीक्यूटेबल, रेडीनेस URL, `env` और `inheritEnv`
के नाम, और लॉग फ़ाइल। यह `args`, `env` की वैल्यू, या URL का userinfo या क्वेरी
प्रिंट नहीं करता। e2e कोई और ऐप प्रोसेस शुरू नहीं करता, इसलिए ऐप जो डेटाबेस
इस्तेमाल करता है वह इसके बाहर चलता है।

```text wrap
App: http://127.0.0.1:57162/ (port 57162, assigned for the declared port 0).
Process: app.command "node" (ready at http://127.0.0.1:57162/; env PORT, DATABASE_URL; log .e2e/app.log). e2e starts no other app process for this session; a database or other service the app uses runs outside e2e.
```

```txt
open_session {target: "web", headed: true}
```

| इनपुट | टाइप | ज़रूरी | क्या करता है |
| --- | --- | --- | --- |
| `target` | string | नहीं | खोलने वाला टारगेट। वरना `--target`, वरना एकमात्र टारगेट। |
| `config` | string (path) | नहीं | इस सेशन का कॉन्फ़िग, एब्सोल्यूट या सर्वर की वर्किंग डायरेक्टरी के सापेक्ष (क्लाइंट के MCP कॉन्फ़िग में `cwd`)। वरना `--config`, वरना `e2e run` की तरह खोजा गया। |
| `headed` | boolean | नहीं | `true` इस सेशन का ब्राउज़र या सिम्युलेटर दिखाता है, `false` छिपाता है। इसके बिना सेशन `--headed` मानता है। |
| `path` | string | नहीं | ऐप URL के रूट की जगह कहाँ खोलना है, जैसे `/settings/members`। पहला ऑब्ज़र्वेशन वही पेज होता है। `test` के साथ नहीं चलता। |
| `test` | string | नहीं | पहले चलाने के लिए एक टेस्ट, `e2e run` के पोज़िशनल की तरह नाम वाले। टेस्ट जहाँ रुकता है सेशन वहीं रुकता है। [टेस्ट चलाना](#running-a-test) देखें। |
| `engine` | string या object | नहीं | बिना कॉन्फ़िग फ़ाइल वाली डायरेक्टरी में सेशन का इंजन, पैकेज नाम या `{package, export, options}` के रूप में। [बिना कॉन्फ़िग के](#without-a-config) देखें। |
| `app` | object | नहीं | `engine` सेशन के लिए टेस्ट हो रहा ऐप, `url`, `bundleId`, या `appPath` के रूप में। |
| `attach` | string | नहीं | [रुके हुए टेस्ट](#attaching-to-a-held-test) के पॉज़ हेडर से मिला ID। सिर्फ़ यही फ़ील्ड पास करें। |

#### `tools`

कैटलॉग लौटाता है, हर टूल के लिए एक लाइन।

```txt
tools {tool: "locate"}
```

| इनपुट | टाइप | ज़रूरी | क्या करता है |
| --- | --- | --- | --- |
| `tool` | string | नहीं | कैटलॉग का एक टूल। उसका पूरा विवरण और आर्ग्युमेंट स्कीमा लौटाता है। |
| `session` | string | कई खुले होने पर | सेशन id। |

#### `call`

कैटलॉग का एक टूल चलाता है।

```txt
call {tool: "tap", args: {target: "n42"}, session: "<id>"}
```

| इनपुट | टाइप | ज़रूरी | क्या करता है |
| --- | --- | --- | --- |
| `tool` | string | हाँ | कैटलॉग टूल का नाम। |
| `args` | object | नहीं | टूल के आर्ग्युमेंट। |
| `session` | string | कई खुले होने पर | सेशन id। |

- टूल के आर्ग्युमेंट `args` के बिना `tool` के बगल में भी रखे जा सकते हैं:
  `call {tool: "tap", target: "n42"}`। दोनों साथ देने पर `INVALID_ARGUMENT` आता
  है।
- आर्ग्युमेंट पहले टूल के क्लोज़्ड स्कीमा पर वैलिडेट होते हैं। गलत टाइप, या
  आर्ग्युमेंट डिक्लेयर करने वाले टूल पर अनडिक्लेयर्ड आर्ग्युमेंट पर
  `INVALID_ARGUMENT` आता है और कुछ नहीं चलता। `back` और `dismiss_keyboard` कोई
  आर्ग्युमेंट नहीं लेते; वे दिए गए किसी भी आर्ग्युमेंट को छोड़कर चल जाते हैं।
- फ़ेल होने वाला एक्शन एरर रिज़ल्ट देता है जिसमें दोबारा ऑब्ज़र्व की गई स्क्रीन
  भी साथ होती है। इसकी शुरुआत टूल, उसके टारगेट, और कोड से होती है:
  `navigate file:///etc/passwd failed: POLICY_DENIED: forbidden URL scheme: file:`।
- प्रोजेक्ट टूल अपने AI SDK `toModelOutput` रेंडरर को मानते हैं, तब भी जब
  `execute` स्ट्रिंग लौटाए। रेंडर किए गए `error-text` और `error-json` आउटपुट
  MCP एरर रिज़ल्ट (`isError: true`) बनते हैं। कोडिंग एजेंट फ़ेल टूल कॉल और सफल
  टूल कॉल में फ़र्क कर सकता है।

#### `close_session`

चल रही रिकॉर्डिंग सेव करता है, अटेम्प्ट खत्म करता है, और इंजन डिस्पोज़ करता है।
सेशन की शुरू की हुई ऐप प्रोसेस को तब रोकता है जब कोई और सेशन उन्हें इस्तेमाल न
कर रहा हो। अटैचमेंट पर इसे इस्तेमाल करने से आप डिटैच हो जाते हैं और टेस्ट रुका
रहता है।

```txt
close_session {session: "<id>"}
```

| इनपुट | टाइप | ज़रूरी | क्या करता है |
| --- | --- | --- | --- |
| `session` | string | कई खुले होने पर | सेशन id। |

### कैटलॉग

`call` क्या चला सकता है, यह सेशन के टारगेट पर निर्भर करता है।

| कैटलॉग टूल | विवरण |
| --- | --- |
| [`observe`](#observe) | ताज़ा ऑब्ज़र्वेशन लौटाता है |
| [एक्शन](#actions) | ऑब्ज़र्व किए गए नोड पर एक्शन करता है |
| [`dismiss_keyboard`](#dismiss_keyboard) | ऑन-स्क्रीन कीबोर्ड छिपाता है |
| [`locate`](#locate) | सिमैंटिक लोकेटर आज़माता है |
| [`run_code`](#run_code) | टेस्ट API पर JavaScript चलाता है |
| [`test_lines`](#test_lines) | सेशन की टेस्ट लाइनें लौटाता है |
| [`screenshot`](#screenshot) | मास्क्ड व्यूपोर्ट लौटाता है, चाहें तो फ़ाइल में सेव भी |
| [पॉइंट टूल](#point-tools) | स्क्रीनशॉट के किसी पॉइंट पर एक्शन करता है |

#### `observe`

ताज़ा ऑब्ज़र्वेशन, हर नोड एक लाइन में `#id role "name" ...` की तरह, मौजूदा पाथ
और रिविज़न के साथ। कोई आर्ग्युमेंट नहीं लेता।

- लिंक का `href` अगर ऐप URL के ऑरिजिन पर हो तो उसका पाथ होता है, वरना ऑरिजिन
  और पाथ।
- `mailto:`, `tel:`, और `blob:` टारगेट अपनी स्कीम बनाए रखते हैं।
- `…` बताता है कि क्या छोड़ा गया है: `?…` क्वेरी, `#…` फ़्रैगमेंट, `data:…` या
  `javascript:…` इनलाइन पेलोड, और अंत में `…` 256 कैरेक्टर पर कटा हुआ टारगेट।

#### एक्शन

`tap`, `double_tap`, `long_press`, `right_click`, `hover`, `type`, `press`,
`select`, `check`, `scroll`, `scroll_to`, `drag`, `upload`, `navigate`, `back`,
`resize_viewport`, `switch_tab`, `close_tab`, `type_secret`। हर एक एक्शन की
समरी, उसे दोहराने वाली [टेस्ट लाइन](#test_lines) (या लाइन न होने का कारण), और
स्क्रीन पर हुए बदलाव लौटाता है।

| इनपुट | क्या करता है |
| --- | --- |
| नोड id | सबसे ताज़ा ऑब्ज़र्वेशन से। |
| वैल्यू, कीबोर्ड का बटन, `checked` स्टेट, दिशा, ड्रॉप टारगेट, प्रोजेक्ट-सापेक्ष या `sample:` `files`, URL, `width` और `height`, या सीक्रेट नाम | वर्ब को जो चाहिए। |
| `modifiers` (ऑप्शनल) | `tap`, `double_tap`, और `right_click` पर, जब इंजन `tapModifiers` डिक्लेयर करे: `Shift`, `Control`, `Alt`, `Meta`, `ControlOrMeta` की लिस्ट, जो क्लिक के समय दबाए रखे जाते हैं। |

- जो वर्ब इंजन डिक्लेयर नहीं करता वह कैटलॉग में नहीं होता।
- `upload` प्रोजेक्ट के बाहर के पाथ, छिपी फ़ाइल, या छिपी डायरेक्टरी की फ़ाइल को
  `POLICY_DENIED` से मना कर देता है। `sample:` फ़ाइल की कोई टेस्ट लाइन नहीं
  होती: उसके लिए प्रोजेक्ट में एक फ़ाइल सेव करें।
- जब कॉन्फ़िग में `credentials` या `secrets` हों और इंजन `fill` एक्शन डिक्लेयर
  करे, तब `type_secret` लिस्ट होता है। प्लेनटेक्स्ट कभी टेक्स्ट के रूप में एजेंट
  तक नहीं पहुँचता;
  [सीक्रेट भरने के बाद स्क्रीनशॉट](/reference/security#screenshots-after-a-secret-fill)
  देखें।

#### `dismiss_keyboard`

ऑन-स्क्रीन कीबोर्ड छिपाता है। कोई आर्ग्युमेंट नहीं लेता। तब लिस्ट होता है जब
इंजन का कीबोर्ड `dismiss` डिक्लेयर करे, जैसे डिवाइस इंजन करते हैं।

#### `locate`

बताता है कि सिमैंटिक लोकेटर से कितने नोड मैच होते हैं, कौन-से, और लिखने के लिए
कौन-सी `screen.*` कॉल बनेगी।

| इनपुट | क्या करता है |
| --- | --- |
| `role` (ऑप्शनल `name` के साथ), `text`, `label`, `placeholder`, `testId` | इनमें से ठीक कोई एक। |
| `exact` | ठीक मैच; सबस्ट्रिंग, केस-इनसेंसिटिव मैच के लिए `false`। |

- शून्य या कई मैच होने पर वह एरर बताता है जो टेस्ट को मिलेगा।
- `name` सिर्फ़ ऐक्सेसिबल नाम से मैच करता है। `observe` `status`, `alert`, या
  `listitem` को उनके टेक्स्ट से दिखाता है, इसलिए इनमें से किसी के साथ कुछ मैच न
  करने वाला नाम देने पर यह `getByRole(role).filter({ hasText })` और `getByText`
  का सुझाव भी देता है।
- नोड के बारे में यह जो दिखाता है वह `observe` की तरह सीक्रेट लेजर से होकर जाता
  है: भरा हुआ सीक्रेट `<secret:name>` दिखता है।

#### `run_code`

लाइव सेशन पर JavaScript चलाता है और बताता है कि कोड ने क्या लौटाया, क्या लॉग
किया, ऐप पर कौन-सी लाइनें चलीं, और स्क्रीन पर क्या बदला। इसे एक ही कॉल में वैल्यू
पढ़ने, उन पर हिसाब करने, एक्शन करने, और टेस्ट में लिखने से पहले किसी लाइन को
चलाकर देखने के लिए इस्तेमाल करें।

```txt
call {tool: "run_code", args: {code: "const rows = screen.getByRole('listitem');\nconst prices = (await rows.allTextContents()).map((text) => Number(text.match(/\\$([\\d.]+)/)[1]));\nawait expect(rows).toHaveCount(12);\nreturn prices;"}}
```

| इनपुट | क्या करता है |
| --- | --- |
| `code` | एक async फ़ंक्शन की बॉडी। स्कोप में `screen`, `app`, `expect`, `credentials`, `secrets`, `console`, और इंजन का फ़िक्स्चर (`browser` या `device`) होते हैं। रुके हुए टेस्ट से जुड़े सेशन में इंजन फ़िक्स्चर नहीं होता। |
| `timeout` | ऑप्शनल। `screen` पर हर एक्शन या मैचर डिफ़ॉल्ट रूप से कितनी देर इंतज़ार करे, ms में, 1 से 120000 तक। इसके बिना: `5000`, या कॉन्फ़िग का टाइमआउट अगर वह छोटा हो। |

```txt
Returned: [12.5,18,24]
Test lines: 2, 1 read not listed.
1. await expect(screen.getByRole('listitem')).toHaveCount(12);
```

- कोड सर्वर की Node प्रोसेस में साधारण JavaScript की तरह चलता है, और स्कोप में
  वही ऑब्जेक्ट होते हैं जो टेस्ट बॉडी को मिलते हैं। कॉल ठीक टेस्ट की तरह इंतज़ार,
  मैच, और फ़ेल करती है, और आपका पास किया फ़ंक्शन (जैसे `browser.route` हैंडलर)
  टेस्ट के हैंडलर की तरह कॉल होता है।
- वैल्यू वापस पाने के लिए JSON वैल्यू `return` करें। `console.log` लाइनें भी
  वापस आती हैं।
- फ़ेल होने वाली लाइन वही एरर अपने `code` के साथ थ्रो करती है जो टेस्ट को मिलता
  है। न पकड़े जाने पर यह कोड रोक देती है और नतीजा एरर रिज़ल्ट होता है। पास हुई
  लाइनों ने ऐप को जहाँ छोड़ा था, वह वहीं रहता है।
- हर लाइन पर `await` लगाएँ। बिना `await` की लाइनें एक साथ शुरू हो जाती हैं और
  क्रम में नहीं चलतीं, इसलिए रीड उसके ऊपर वाले टैप से पहले पूरा हो सकता है। जिस
  फ़ेलियर को कुछ भी await न करे वह कॉल को फ़ेल करता है। ऐसा ही उस प्रॉमिस के साथ
  होता है जिसे कोड ने रिजेक्ट होने छोड़ दिया, और `setTimeout` कॉलबैक के थ्रो किए
  एरर के साथ: कॉल वहीं खत्म हो जाती है। कॉल खत्म होने के बाद किसी हैंडलर से छूटा
  एरर सर्वर के लॉग में चेतावनी बनता है।
- कॉल लौटने के बाद भी चल रहा कोड (जैसे बिना await शुरू किया गया async फ़ंक्शन)
  ऐप पर काम करता रहता है। वे एक्शन नतीजे या ड्राफ़्ट में नहीं आते।
- `expect.soft` अपने फ़ेलियर कॉल के अंत तक रखता है, और फिर कॉल उन्हीं के साथ
  फ़ेल होती है।
- नतीजे में चली हुई लाइनें दिखती हैं। जब कोड कुछ रिटर्न या लॉग न करे, तो रीड
  अपनी वैल्यू वहीं दिखाता है। वरना वैल्यू `return` करें।
- रीड को छोड़कर पास होने वाली लाइनें चलने के क्रम में [`test_lines`](#test_lines)
  ड्राफ़्ट में जुड़ती हैं। रीड का मतलब `screen` या लोकेटर की वह कॉल है जो किसी
  वैल्यू के साथ रिज़ॉल्व हो। `app` या इंजन फ़िक्स्चर की कॉल चाहे जो लौटाए, ड्राफ़्ट
  होती है क्योंकि वह एक्शन भी कर सकती है। जो कॉल कोई ऑब्जेक्ट लौटाए (जैसे नया
  टैब), उसे नाम देने वाली `const` लाइन मिलती है। जो लाइन सर्वर के कॉल करने के लिए
  फ़ंक्शन पास करे (जैसे रूट हैंडलर), वह फ़ंक्शन के टेक्स्ट और इस कमेंट के साथ
  ड्राफ़्ट होती है कि उसमें इस्तेमाल होने वाले वेरिएबल टेस्ट में डिक्लेयर करें। वह
  फ़ंक्शन खुद जो कॉल करता है, वह दोबारा ड्राफ़्ट नहीं होता। पास होने वाला
  `expect(value)` कोई लाइन नहीं छोड़ता।
- `screen` पर हर एक्शन या मैचर डिफ़ॉल्ट रूप से `timeout` तक इंतज़ार करता है।
  लाइन के अपने ऑप्शन का `timeout` इसकी जगह लेता है। `timeout` के बिना हर एक
  5000 ms, या कॉन्फ़िग का [`actionTimeout`](/reference/config#actiontimeout) या
  [`assertionTimeout`](/reference/config#assertiontimeout) (जो छोटा हो) इंतज़ार
  करता है। `app` और इंजन फ़िक्स्चर टेस्ट की तरह इंतज़ार करते हैं।
- `await import()` Node बिल्ट-इन या फ़ाइल का एब्सोल्यूट पाथ लेता है। रिलेटिव पाथ
  प्रोजेक्ट से नहीं, e2e के अपने इंस्टॉल से रिज़ॉल्व होता है।
- पूरी कॉल 5 मिनट तक चल सकती है, वे लाइनें भी जिन्हें उसने चलते छोड़ा। जो कोड
  कभी यील्ड न करे (जैसे `while (true) {}`), वह सर्वर को ब्लॉक कर देता है।
- जहाँ कोई कॉन्फ़िगर सीक्रेट वैल्यू हो, नतीजे में `<secret:name>` दिखता है।

यह कोड किसी सैंडबॉक्स में बंद नहीं है। इसे टेस्ट फ़ाइल जितने अधिकार हैं: यह
मॉड्यूल इंपोर्ट कर सकता है, फ़ाइलें पढ़ सकता है, और ऐप जो वैल्यू दिखाता है उन्हें
पढ़ सकता है, सीक्रेट समेत। `run_code` डिफ़ॉल्ट रूप से चालू है: हर `e2e mcp`
सर्वर इसे देता है, कोई फ़्लैग इसे बंद नहीं करता, और `call` को मंज़ूरी देने वाला
क्लाइंट इसके साथ `run_code` को भी मंज़ूरी देता है। [सुरक्षा](/reference/security)
देखें।

| क्या थ्रो होता है | कब |
| --- | --- |
| `INVALID_ARGUMENT` | कोड पार्स नहीं हो पा रहा। मैसेज लाइन बताता है, और कुछ नहीं चलता। |
| `ASSERTION_FAILED` | कोई `expect` सही नहीं निकला। |
| `POLICY_DENIED` | सिक्योर फ़ील्ड से पढ़ना, जैसे पासवर्ड इनपुट। |

जो एरर रनर का नहीं है, जैसे `TypeError`, वह अपने नाम और जिस लाइन पर थ्रो हुआ उसके
साथ वापस आता है।

#### `test_lines`

सेशन के एक्शन की प्रिंट की हुई हर टेस्ट लाइन और [`run_code`](#run_code) की पास
हुई हर लाइन को क्रम में ड्राफ़्ट टेस्ट बॉडी की तरह लौटाता है। कोई आर्ग्युमेंट
नहीं लेता।

हर एक्शन के नतीजे में समरी के बाद उसकी लाइन होती है:

```txt
Tapped #n31.
Test line: await screen.getByRole("button", "Sign in").tap();
```

- लोकेटर उस टारगेट से बनता है जैसा वह एक्शन चलने से पहले सबसे ताज़ा ऑब्ज़र्वेशन
  में लिस्ट था। रोल और नाम, लेबल, प्लेसहोल्डर, टेक्स्ट, और टेस्ट id इसी क्रम में
  आज़माए जाते हैं, और जो पहला लोकेटर लाइव स्क्रीन पर सिर्फ़ उस टारगेट से मैच हो
  (जैसा [`locate`](#locate) रिपोर्ट करेगा), वही चुना जाता है।
- जो लोकेटर मिलते-जुलते दूसरे नोड से भी मैच हो, उसे संकरा किया जाता है: पहले
  रेंडर होने वाले नोड तक (`{ visible: true }`), फिर किसी कंटेनर के अंदर
  (`getByRole("listitem").filter({ hasText: "Offer B" })`), फिर पोज़िशन से
  (`.nth(1)`, यह बताने वाले कमेंट के साथ)। पोज़िशन तभी इस्तेमाल होती है जब लाइव
  ट्विन वही हों जो ऑब्ज़र्वेशन में लिस्ट थे, अपनी जगह पर या सब एक साथ खिसके हुए।
- जिस कंट्रोल का कोई नाम, लेबल, प्लेसहोल्डर, टेक्स्ट, या टेस्ट id न हो, वह अपने
  रोल से ढूँढा जाता है: अकेला होने पर सिर्फ़ रोल से (`getByRole("spinbutton")`,
  कमेंट के साथ), वरना ट्विन की तरह संकरा करके।
- हर टारगेट पर ज़्यादा से ज़्यादा 10 लोकेटर आज़माए जाते हैं। डिवाइस पर हर कोशिश
  पूरी स्क्रीन पढ़ती है।
- जब कुछ भी अकेले उस टारगेट तक न पहुँच सके, तो नतीजे में `No test line:` और उसका
  कारण लिखा होता है। जो लाइन फ़ेल होगी वह कभी प्रिंट नहीं होती।
- फ़ेल हुआ एक्शन कोई लाइन प्रिंट या रिकॉर्ड नहीं करता। बिना लाइन वाला एक्शन ड्राफ़्ट
  में `//` कमेंट के रूप में दिखता है।

| एक्शन | लाइन |
| --- | --- |
| बिना [`test`](#running-a-test) के सेशन खोलना | `app.open()` |
| `tap`, `double_tap`, `long_press`, `right_click`, `hover` | `tap()`, `doubleTap()`, `longPress()`, `secondaryTap()`, `hover()`, किसी भी `modifiers` के साथ |
| नोड में `type` | `fill(value)`; क्रेडेंशियल का यूज़रनेम `credentials.user(name).username` के रूप में |
| `type_secret` | `fill(credentials.user(name).password)` या `fill(secrets.get(name))`, वैल्यू कभी नहीं |
| नोड पर एक बार `press` | `press(key)` |
| `select`, `check` | `selectOption(label)`, `check()` या `uncheck()` |
| `drag`, `upload` | `dragTo(locator)`, `setInputFiles(files)` |
| नोड तक `scroll_to` | `scrollIntoView()` |
| `navigate`, `back` | `app.open(url)`, ऐप के ऑरिजिन के URL को उसके पाथ के रूप में; `app.back()` |

इनकी कोई लाइन नहीं बनती: बिना टारगेट के `type` या `press`, 1 से ज़्यादा `times`
वाला `press`, `scroll`, टेक्स्ट तक `scroll_to`, `dismiss_keyboard`,
`resize_viewport` (इंजन के बिल्ट-इन फ़िक्स्चर से साइज़ सेट करें, वेब पर
`browser.setViewport`), `switch_tab` और `close_tab` (वेब पर
`browser.tabs()[tab - 1].activate()` और `.close()`), और वह `type` जिसे नोड ने
कीबोर्ड के ज़रिए लिया। [पॉइंट टूल](#point-tools) कुछ प्रिंट नहीं करते।

#### `screenshot`

मास्क्ड व्यूपोर्ट इमेज के रूप में।

| आर्ग्युमेंट | टाइप | विवरण |
| --- | --- | --- |
| `path` | `string` | ऑप्शनल। स्क्रीनशॉट को प्रोजेक्ट रूट के सापेक्ष PNG फ़ाइल के रूप में भी सेव करता है और उसका एब्सोल्यूट पाथ लौटाता है। प्रोजेक्ट के बाहर का पाथ, छिपी फ़ाइल, या छिपी डायरेक्टरी में पाथ `POLICY_DENIED` देता है। |

```json
{ "tool": "screenshot", "args": { "path": "screenshots/checkout.png" } }
```

- इसके बाद से हर एक्शन के नतीजे में एक ताज़ा स्क्रीनशॉट साथ आता है।
- यह सिर्फ़ सिक्योर फ़ील्ड को मास्क करता है, सीक्रेट भरने के बाद भी।
- फ़ाइल एक दूसरा, फ़ुल-रिज़ॉल्यूशन कैप्चर होती है, ठीक `app.screenshot` की तरह
  मास्क्ड। अटैच की गई इमेज छोटी की जा सकती है।

#### पॉइंट टूल

हर एक सबसे ताज़ा स्क्रीनशॉट के पिक्सल में `x` और `y` लेता है। `drag_at` अपना
ड्रॉप पॉइंट `to_x` और `to_y` में लेता है।

| टूल | इनपुट | क्या करता है | कब लिस्ट होता है जब इंजन डिक्लेयर करे |
| --- | --- | --- | --- |
| `tap_at` | `x`, `y` | इंजन के `performAt` से बेयर पॉइंट पर टैप करता है। `performAt` के बिना पॉइंट किसी लिस्टेड कंट्रोल पर पड़ना चाहिए, जिस पर id से टैप होता है। | `tap` या `performAt` |
| `hover_at` | `x`, `y` | उसी तरह हॉवर करता है: `performAt` के `hover` काइंड से बेयर पॉइंट पर, वरना उसके नीचे के लिस्टेड कंट्रोल पर id से। | `hover` एक्शन या पॉइंटर काइंड |
| `drag_at` | `x`, `y`, `to_x`, `to_y` | `performAt` के `dragTo` काइंड से पहले पॉइंट से दूसरे पॉइंट तक ड्रैग करता है। उस काइंड के बिना दोनों पॉइंट दो अलग लिस्टेड कंट्रोल पर पड़ने चाहिए (जिन्हें id से ड्रैग किया जाता है), वरना कॉल `UNSUPPORTED_CAPABILITY` से फ़ेल होती है। | `dragTo` एक्शन या पॉइंटर काइंड |
| `type_at` | `x`, `y`, `value`; कीबोर्ड वाले इंजन पर `replace` | पॉइंट के नीचे के लिस्टेड इनपुट को id से भरता है। कीबोर्ड के साथ बाकी किसी भी चीज़ पर फ़ोकस के लिए टैप करता है और `replace` सेट न होने पर कैरेट पर टाइप करता है। कीबोर्ड के बिना अनलिस्टेड जगह पर पॉइंट फ़ेल होता है। | `type` या कीबोर्ड |
| `press_at` | `x`, `y`, `key` | पॉइंट के नीचे के लिस्टेड कंट्रोल पर कीबोर्ड का बटन id से भेजता है। कीबोर्ड के साथ बाकी किसी भी चीज़ पर फ़ोकस के लिए टैप करता है और बटन कीबोर्ड से जाता है। | `press` या कीबोर्ड |
| `select_at` | `x`, `y`, `value` (ऑप्शन का दिखने वाला लेबल) | पॉइंट के नीचे लिस्टेड सेलेक्ट-जैसे कंट्रोल में ऑप्शन चुनता है। वहाँ कुछ लिस्ट न होने पर फ़ेल होता है। | `select` |

<Note>
सेशन के पहले `screenshot` से पहले हर पॉइंट टूल बिना किसी लागत के यही लाइन जवाब
में देता है कि पहले स्क्रीनशॉट लें।
</Note>

#### रिकॉर्डिंग

`start_recording` और `stop_recording` ऐप का वीडियो रिकॉर्ड करते हैं। दोनों तब
लिस्ट होते हैं जब इंजन वीडियो रिकॉर्ड करता हो।

```txt
call {tool: "start_recording", args: {name: "checkout-flow"}}
call {tool: "stop_recording"}
```

| टूल | इनपुट | क्या करता है |
| --- | --- | --- |
| `start_recording` | `name` (ऑप्शनल): 64 तक अक्षर, अंक, `-`, और `_`, शुरुआत अक्षर या अंक से | एक समय पर एक ही रिकॉर्डिंग। दूसरी बार शुरू करने पर चल रही रिकॉर्डिंग बताता है। |
| `stop_recording` | कोई नहीं | वीडियो सेव करता है और हर फ़ाइल का एब्सोल्यूट पाथ, या जहाँ प्रोवाइडर उसे रखता है वह URL लौटाता है। |

- सेशन सिर्फ़ `start_recording` और `stop_recording` के बीच वीडियो रिकॉर्ड करता है,
  जितनी बार चाहें उतनी बार। कॉन्फ़िगर [`video`](/reference/config#video) मोड रन
  पर लागू होता है, सेशन पर नहीं, और सेशन कोई [ट्रेस](/reference/config#trace)
  नहीं लिखता।
- हर रिकॉर्डिंग `<output>/videos/<session>/<n>[-<name>].webm` (मोबाइल पर `.mp4`,
  और [`output`](/reference/config#output) डिफ़ॉल्ट `.e2e` है) पर सेव होती है,
  जहाँ `n` सेशन की रिकॉर्डिंग गिनता है।
- रीस्टार्ट या स्टेट रीसेट के पार जाने वाली वेब रिकॉर्डिंग में हर पेज की एक फ़ाइल
  होती है (`-part2`, `-part3`, वगैरह) प्ले ऑर्डर में।
- जो ब्राउज़र या डिवाइस प्रोवाइडर खुद लीज़ रिकॉर्ड करता है, वह इसकी जगह सेशन
  रिकॉर्ड करता है। [Kernel](/integrations/kernel) अपना रीप्ले डाउनलोड करके यहाँ
  बाकी फ़ाइलों की तरह `<n>[-<name>].mp4` के नाम से सेव करता है। जो प्रोवाइडर
  रिकॉर्डिंग अपने पास रखता है वह फ़ाइल के बजाय URL से लिस्ट होता है।
- `close_session`, आइडल टाइमआउट, और सेशन TTL चल रही रिकॉर्डिंग सेव करते हैं, और
  क्लोज़ रिज़ल्ट उसकी फ़ाइलें दिखाता है।

<Warning>
रिकॉर्डिंग मास्क्ड नहीं होतीं: ये इंसान के देखने के लिए फ़ाइलें हैं, और कोई टूल
इनके पिक्सल नहीं लौटाता। रिकॉर्डिंग के दौरान साधारण इनपुट में टाइप किया गया
सीक्रेट वीडियो में पढ़ा जा सकता है।
</Warning>

#### प्रोजेक्ट टूल

`agents.default.tools` के प्रोजेक्ट टूल कैटलॉग में अपने नामों से, टारगेट के
प्लेटफ़ॉर्म के हिसाब से आते हैं। `mobileTools(...)` पास करने वाले मोबाइल प्रोजेक्ट
को `open_app`, `swipe`, और `alert` भी मिलते हैं, और `foldTools(...)` पास करने
वाले को फ़ोल्डेबल डिवाइस के लिए `fold` मिलता है।

| क्या थ्रो होता है | कब |
| --- | --- |
| `INVALID_CONFIG` | कॉन्फ़िग लोड पर किसी बिल्ट-इन जैसा नाम वाला प्रोजेक्ट टूल। |
| `UNKNOWN_TOOL` | ऐसा नाम जो कैटलॉग में नहीं है। मैसेज उपलब्ध नाम दिखाता है। |

## सेटअप

सर्वर `e2e` के साथ ही आता है। `e2e init` इसे `.mcp.json` (Claude Code),
`.cursor/mcp.json` (Cursor), और `.codex/config.toml` (Codex) में रजिस्टर करने
का ऑप्शन देता है। डिपेंडेंसी इंस्टॉल करें और प्रोजेक्ट डायरेक्टरी में MCP क्लाइंट
शुरू करें ताकि `npx` (Bun प्रोजेक्ट में `bunx`) इंस्टॉल किया हुआ e2e वर्ज़न
इस्तेमाल करे। हाथ से:

<CodeGroup>
```bash npm
claude mcp add --scope project e2e -- npx e2e mcp
```

```bash pnpm
claude mcp add --scope project e2e -- pnpm exec e2e mcp
```

```bash bun
claude mcp add --scope project e2e -- bunx e2e mcp
```
</CodeGroup>

जो क्लाइंट `mcpServers` कॉन्फ़िग इस्तेमाल करते हैं, उनमें ऊपर वाली एंट्री जोड़ें।
प्रोजेक्ट ट्रस्ट होने पर Codex प्रोजेक्ट की `.codex/config.toml` पढ़ता है।
रजिस्टर करने के बाद नया सेशन शुरू करें:

```toml title=".codex/config.toml"
[mcp_servers.e2e]
command = "npx"
args = ["e2e", "mcp"]
```

OpenCode प्रोजेक्ट की `opencode.json` में `mcp` से सर्वर पढ़ता है।
[MCP सर्वर](/mcp-server#set-it-up) में OpenCode टैब देखें।

सर्वर [MCP Registry](https://registry.modelcontextprotocol.io) में भी
`io.github.e2e-inc/e2e` नाम से लिस्ट है। वहाँ से इंस्टॉल करने वाला क्लाइंट लिस्ट
किया हुआ रिलीज़ `npx` से चलाता है और उसे प्रोजेक्ट डायरेक्टरी में शुरू करना होता
है। प्रोजेक्ट में तब भी e2e और उसका इंजन इंस्टॉल होना चाहिए, क्योंकि कॉन्फ़िग
उन्हें इंपोर्ट करता है। प्रोजेक्ट के e2e से अलग वर्ज़न वाला लिस्टेड रिलीज़ उन
कॉन्फ़िग key को मना कर सकता है जिन्हें वह नहीं जानता; ऊपर वाला रजिस्ट्रेशन हमेशा
मेल खाता है।

सर्वर को मॉडल नहीं चाहिए: ऑप्शनल `ai` पैकेज के बिना भी प्रोजेक्ट सेशन खोलता है
और डिटर्मिनिस्टिक टूल से ऐप चलाता है। सेशन जो टेस्ट [चलाता है](#running-a-test),
वह जिस एजेंट स्टेप को रीप्ले कैश सर्व न कर सके उसके लिए कॉन्फ़िगर मॉडल कॉल करता
है।

सर्वर को प्रोजेक्ट डायरेक्टरी में शुरू करें। कॉन्फ़िग खोज `e2e run` की तरह काम
करती है। दूसरे कॉन्फ़िग के लिए [`--config`](#config) और
[`open_session`](#open_session) देखें।

## बिना कॉन्फ़िग के

जिस डायरेक्टरी में कॉन्फ़िग फ़ाइल नहीं है, वहाँ `open_session` को `engine` चाहिए।
सेशन में उस इंजन पर एक टारगेट होता है। बाकी हर सेटिंग डिफ़ॉल्ट पर होती है, इसलिए
सेशन में कोई क्रेडेंशियल, सीक्रेट, या प्रोजेक्ट टूल नहीं होते।

```txt
open_session {engine: "@e2e-dev/web", app: {url: "http://localhost:3000"}}
open_session {engine: {package: "@e2e-dev/mobile", options: {platform: "ios"}}, app: {bundleId: "com.example.app"}}
```

जिस इंजन को कोई ऑप्शन नहीं चाहिए उसके लिए पैकेज का नाम ही काफ़ी है। ऑप्शन पास
करने या एक्सपोर्ट का नाम देने के लिए `engine` को ऑब्जेक्ट के रूप में लिखें:

| फ़ील्ड | टाइप | क्या करता है |
| --- | --- | --- |
| `package` | string | लोड करने वाला पैकेज। इसमें सबपाथ हो सकता है, जैसे `@e2e-dev/testmu/web`। |
| `export` | string | कॉल करने वाला एक्सपोर्ट। डिफ़ॉल्ट: डिफ़ॉल्ट एक्सपोर्ट। |
| `options` | object | वे ऑप्शन जो फ़ैक्टरी लेती है, `e2e.config.ts` की तरह। |

- **सिर्फ़ पैकेज का नाम** बिना ऑप्शन के पैकेज के डिफ़ॉल्ट एक्सपोर्ट को कॉल करता
  है। `@e2e-dev/web`, `@e2e-dev/mobile`, और `@e2e-dev/desktop` अपनी फ़ैक्टरी इसी
  तरह एक्सपोर्ट करते हैं। [आपका अपना इंजन](/writing-an-engine#open-it-by-name)
  भी ऐसा कर सकता है।
- **कोई ऑप्शन दूसरी फ़ैक्टरी कॉल हो सकता है।** जब किसी ऑप्शन वैल्यू में `package`
  हो और `export` और `options` के अलावा कोई key न हो, तो सर्वर उसे एक कॉल की तरह
  पढ़ता है। वह पहले वह कॉल चलाता है और उसका नतीजा ऑप्शन के रूप में पास करता है।
  इंजन को डिवाइस या ब्राउज़र प्रोवाइडर देने के लिए इसे इस्तेमाल करें:

  ```txt
  open_session {
    engine: {package: "@e2e-dev/mobile", options: {
      platform: "ios",
      device: {package: "@e2e-dev/limrun", export: "limrun", options: {region: "eu"}}
    }},
    app: {bundleId: "com.example.app"}
  }
  ```

  ऊपर की कॉल `mobile({ platform: 'ios', device: limrun({ region: 'eu' }) })`
  बनाती है। प्रोवाइडर अपनी API key सर्वर के एनवायरनमेंट से पढ़ता है।
- **लुकअप।** सर्वर हर पैकेज को पहले प्रोजेक्ट में, फिर चल रहे `e2e` के पास, फिर
  `~/.e2e/engines` में ढूँढता है। कहीं न मिलने पर एरर वह कमांड बताता है जो इसे
  हर प्रोजेक्ट के लिए इंस्टॉल कर देती है:
  `npm install --prefix ~/.e2e/engines @e2e-dev/web`। जो एजेंट इसे नहीं चला
  सकता (जैसे बिना नेटवर्क वाले सैंडबॉक्स में), वह आपसे चलाने को कहता है।
- **`app`** `url`, `bundleId`, और `appPath` लेता है, टारगेट के
  [`app`](/reference/config#the-app-under-test) की तरह। `@e2e-dev/web` को `url`
  चाहिए। `@e2e-dev/mobile` और `@e2e-dev/desktop` को `bundleId` या `appPath`
  चाहिए।
- **फ़ाइलें।** प्रोजेक्ट रूट सर्वर की वर्किंग डायरेक्टरी होती है, और सेशन वहीं
  `.e2e/` लिखता है।
- **टेस्ट।** `e2e run` और `open_session {test}` को कॉन्फ़िग चाहिए। सेशन की टेस्ट
  लाइनों को टेस्ट के रूप में रखने के लिए [`e2e init`](/reference/cli#e2e-init)
  से कॉन्फ़िग लिखें।
- **कई सेशन।** `engine` से खोले गए सेशन एक साथ चलते हैं। कॉन्फ़िग वाला सेशन
  उनके साथ नहीं खुलता और `CONFIG_IN_USE` से फ़ेल हो जाता है।

| क्या थ्रो होता है | कब |
| --- | --- |
| `CONFIG_NOT_FOUND` | बिना `engine` के `open_session`, और डायरेक्टरी में कोई कॉन्फ़िग नहीं है। |
| `ENGINE_NOT_INSTALLED` | `engine` का नाम वाले पैकेज तीनों लुकअप जगहों में से कहीं नहीं है। |
| `INVALID_ARGUMENT` | `package` पैकेज नाम नहीं है, `export` एक्सपोर्ट नाम नहीं है, `engine` के साथ `target`, `config`, या `test` दिया है, या डायरेक्टरी में कॉन्फ़िग है। बिना `engine` के `app` देने पर भी। |
| `INVALID_CONFIG` | बताया गया एक्सपोर्ट फ़ंक्शन नहीं है, किसी फ़ैक्टरी ने अपने `options` मना कर दिए, इंजन फ़ैक्टरी ने इंजन नहीं लौटाया, या इंजन ने `app` मना कर दिया। फ़ंक्शन न होने वाले एक्सपोर्ट पर मैसेज पैकेज के फ़ंक्शन की लिस्ट देता है। |

## आउटपुट

- ऑपरेटर आउटपुट `e2e mcp:` प्रीफ़िक्स के साथ stderr पर जाता है। stdout पर सिर्फ़
  प्रोटोकॉल चलता है।
- आपका कोड `console`, `process.stdout`, या `process.stderr` से जो लिखता है
  (कॉन्फ़िग का टॉप-लेवल कोड, प्रोजेक्ट टूल, सेशन का चलाया टेस्ट), वह सीक्रेट वैल्यू
  छिपाकर stderr पर जाता है।
- कॉन्फ़िग लोड होते वक्त प्रिंट हुआ आउटपुट लोड पूरा होने पर दिखता है। लोड फ़ेल हो
  तो वह आउटपुट रोक लिया जाता है, क्योंकि कॉन्फ़िग के सीक्रेट पता नहीं होते।
- सेशन के टेस्ट का छोड़ा हुआ रिजेक्टेड प्रॉमिस रन की तरह उस टेस्ट को फ़ेल करता
  है। टेस्ट बॉडी खत्म होने के बाद रिजेक्ट होने वाला प्रॉमिस `close_session` के
  नतीजे में `UNHANDLED_REJECTION` लाइन बनता है, और सेशन बंद हो चुका हो तो stderr
  पर चेतावनी। कोई भी दूसरा न पकड़ा गया एरर (किसी भी सेशन के टेस्ट चलाने से पहले
  का रिजेक्शन समेत) रेडैक्ट होकर लॉग होता है और सर्वर बंद कर देता है।

<Note>
सर्वर का stdio इनहेरिट करने वाली चाइल्ड प्रोसेस इसके पार लिखती है।
</Note>

## सेशन

सेशन एक टारगेट पर एक अटेम्प्ट होता है। कोई सेशन खुले बिना `call` करने पर
`NO_SESSION` से फ़ेल होता है।

सेशन तब बंद होता है:

- `close_session` पर,
- 30 आइडल मिनट के बाद,
- 4 घंटे के बाद,
- जब क्लाइंट डिस्कनेक्ट हो जाए,
- SIGINT या SIGTERM पर।

आइडल और लाइफ़टाइम सीमाएँ उन सेशन पर लागू होती हैं जो अपना खुद का अटेम्प्ट खोलते
हैं।

जब क्लाइंट सर्वर का stdin बंद कर दे या बंद हो जाए, तो वह डिस्कनेक्ट माना जाता है।
तब हर सेशन बंद होता है, सेशन की शुरू की हुई ऐप कमांड रुकती हैं, और सर्वर बंद हो
जाता है।

सेशन वही नियम लागू करते हैं जो टेस्ट करते हैं:

- नोड id सिर्फ़ सबसे ताज़ा ऑब्ज़र्वेशन के लिए मान्य होते हैं।
- सिंगल एक्शन सीक्रेट सिर्फ़ `type_secret` से भरते हैं। [`run_code`](#run_code)
  टेस्ट की तरह भरता है।
- कॉन्फ़िग लोड होते ही उसकी सीक्रेट वैल्यू टूल के हर टेक्स्ट, `locate` के मिले
  नोड, एक्शन नतीजे, `open_session` या `close_session` फ़ेलियर, क्लीनअप लाइन, और
  सर्वर की अपनी लॉग लाइनों से छिपाई जाती हैं।
- सेशन जो करता है वह टेस्ट रिज़ल्ट के रूप में दर्ज नहीं होता। सिर्फ़ सेशन का
  चलाया हुआ टेस्ट ही रीप्ले कैश पढ़ता या लिखता है
  ([टेस्ट चलाना](#running-a-test))। इसके आर्टिफ़ैक्ट
  `<output>/results/mcp/<target>-<attemptId>/` में और वीडियो `<output>/videos/`
  में जाते हैं। बाद का `e2e run` `<output>/results` साफ़ कर देता है; वीडियो बने
  रहते हैं।
- क्लाइंट से कैंसल की गई क्यू की हुई कॉल अपनी बारी आने पर नहीं चलती।

## रुके हुए टेस्ट से जुड़ना

पॉज़ हेडर में दिया ID इस्तेमाल करें। एक अटेम्प्ट के सारे पॉज़ में यह वही रहता
है। उसी e2e वर्ज़न के साथ रन की डायरेक्टरी से MCP शुरू करें।

```txt
open_session {attach: "k3f9"}
```

सिर्फ़ `attach` पास करें। अटैच्ड सेशन में उस टारगेट के सामान्य सेशन जैसे ही टूल
होते हैं। `<output>/videos/<session>/` में वीडियो सेव करने के लिए
`start_recording` और `stop_recording` इस्तेमाल करें। अगर रन पहले से अटेम्प्ट
रिकॉर्ड कर रहा हो, तो `start_recording` रन की वीडियो डायरेक्टरी बताते हुए एरर
लौटाता है।

डिटैच होने और टेस्ट को रुका छोड़ने के लिए `close_session` इस्तेमाल करें। जवाब में
डिटैच पर सेव हुई किसी भी रिकॉर्डिंग का पाथ होता है।

टेस्ट को आगे बढ़ाने और अटैचमेंट को तुरंत खत्म करने के लिए Enter दबाएँ या
`npx e2e run --step next` चलाएँ। चल रही कोई भी रिकॉर्डिंग बैकग्राउंड में सेव हो
जाती है। रनर सेव किया पाथ या एरर लॉग करता है। अगर MCP सर्वर अभी जुड़ा है, तो वह
भी वही नतीजा लॉग करता है।

रिपोर्ट और ट्रेस टेस्ट के अपने स्टेप दर्ज करते हैं। अटैच्ड कॉल के ऐप लॉग और
स्क्रीन अपडेट कॉल खत्म होने के बाद पहुँचें, तो ट्रेस में दिख सकते हैं।

## टेस्ट चलाना

`open_session {test}` सेशन के अटेम्प्ट पर प्रोजेक्ट का एक टेस्ट चलाता है, फिर जहाँ
टेस्ट रुका उसी स्क्रीन पर सेशन सौंप देता है। इससे कोडिंग एजेंट पूरा फ़्लो दोबारा
क्लिक किए बिना वहीं से फ़ेल टेस्ट ठीक कर सकता है।

```txt
open_session {test: "tests/checkout.e2e.ts:12"}
```

- **सिलेक्शन।** `test` वही लेता है जो `e2e run` पोज़िशनल के रूप में लेता है:
  उस लाइन पर डिक्लेयर टेस्ट के लिए `:line` वाली फ़ाइल, फ़ाइल, डायरेक्टरी, ग्लोब,
  या नाम। इसे सेशन के टारगेट पर ठीक एक ही टेस्ट चुनना चाहिए। लाइन वही होनी चाहिए
  जिस पर `test(` कॉल है; टेस्ट के अंदर की लाइन कुछ नहीं चुनती।
- **क्या चलता है।** टेस्ट के `beforeAll` हुक, उसके `test.extend()` फ़िक्स्चर,
  उसके `beforeEach` हुक, और उसकी बॉडी, ठीक रन वाले ही फ़िक्स्चर, लोकेटर,
  `expect`, `timeout`, `actionTimeout`, और `assertionTimeout` के साथ। सेशन पहले
  ऐप URL नहीं खोलता और न पिन किया ऐप लॉन्च करता है; टेस्ट ऐप खुद खोलता है।
- **कहाँ रुकता है।** पहले फ़ेलियर पर, या बॉडी के अंत में। कुछ भी टियरडाउन नहीं
  होता। शुरुआती टेक्स्ट नतीजे से शुरू होता है: पास, या फ़ेल होने पर कोड, मैसेज,
  फ़ेल लाइन और उसके आसपास का कोड, URL, कुछ मैच न करने वाले लोकेटर के सबसे करीबी
  नोड, और आखिरी 15 स्टेप। उसके बाद सेशन समरी, कैटलॉग, और स्क्रीन आती है।
- **टेस्ट लाइनें।** टेस्ट के अपने स्टेप कोई [टेस्ट लाइन](#test_lines) प्रिंट नहीं
  करते। सेशन की लाइनें एजेंट के पहले एक्शन से शुरू होती हैं, और `test_lines`
  उन्हें टेस्ट को आगे बढ़ाने वाली लाइनों के रूप में लौटाता है।
- **टियरडाउन।** `afterEach` हुक, फ़िक्स्चर टियरडाउन, और `afterAll` हुक
  `close_session` पर, या सेशन के अपने-आप बंद होने पर चलते हैं। उनके फ़ेलियर
  `Cleanup (afterEach)` और `Cleanup (afterAll)` लाइनों के रूप में दिखते हैं।
- **दोबारा चलाना।** `close_session`, फिर दोबारा `open_session {test}`। हर सेशन
  कॉन्फ़िग और टेस्ट फ़ाइलों को (उनके इंपोर्ट की हुई फ़ाइलों समेत) नए सिरे से लोड
  करता है।
- **रीप्ले कैश।** टेस्ट रन के पहले अटेम्प्ट की तरह कैश पढ़ता और लिखता है: स्टेप
  रीप्ले होते हैं, और बाद की कोई जाँच पास होने पर नई रिकॉर्डिंग सेव होती है।
  फ़ेलियर उन एंट्री को हटा देता है जिन्हें किसी जाँच ने कन्फ़र्म नहीं किया। बॉडी
  खत्म होने पर कैश सेटल हो जाता है, इसलिए `afterEach` की जाँच कुछ कन्फ़र्म नहीं
  करती। [`cache.strict`](/reference/config#cache) रन की तरह लागू होता है।
- **इसका हिस्सा नहीं।** कोई टेस्ट रिज़ल्ट, रिपोर्ट, या ट्रेस पेज नहीं। रीट्राई,
  और टेस्ट के `trace` और `video` मोड लागू नहीं होते। फ़ेलियर स्क्रीनशॉट और
  `screen-at-failure.txt` सेशन की आर्टिफ़ैक्ट डायरेक्टरी में जाते हैं।
- **स्क्रीनशॉट।** `toHaveScreenshot` के लिए हर सेशन अपने आप में एक रन गिना जाता
  है: एक सेशन की लिखी बेसलाइन से अगले सेशन में तुलना होती है।
- **कई सेशन।** दो सेशन का टेस्ट कोड बारी-बारी से चलता है: एक समय पर एक ही सेशन
  अपना टेस्ट या टियरडाउन चलाता है, क्योंकि `expect.poll`, `expect.soft`, और
  `test.skip` हर प्रोसेस में एक ही स्लॉट से चल रहा टेस्ट ढूँढते हैं। अपनी बारी का
  इंतज़ार करते समय कैंसल हुआ ओपन टेस्ट का कोई कोड नहीं चलाता।

| क्या थ्रो होता है | कब |
| --- | --- |
| `NO_TESTS` | `test` कोई चलने लायक टेस्ट नहीं चुनता। मैसेज `e2e run` की तरह कारण बताता है। |
| `TEST_AMBIGUOUS` | `test` कई टेस्ट चुन लेता है। मैसेज उन्हें `file:line` की तरह दिखाता है। |
| `SESSION_TEST_UNSUPPORTED` | टेस्ट सीरियल ग्रुप में है, सेटअप टेस्ट के `session` से शुरू होता है, या कई एजेंट के रूप में चलता है। |
| `COLLECTION_ERROR` | टेस्ट फ़ाइल कलेक्ट नहीं हो पाती, `e2e run` की तरह। |

## कई सेशन

`--max-sessions` तक कई सेशन एक साथ खुले रह सकते हैं, हर एक अपने अटेम्प्ट और अपने
ब्राउज़र या डिवाइस के साथ। पैरेलल एजेंट (जैसे कोडिंग एजेंट के सबएजेंट) इसी तरह
एक सर्वर शेयर करते हैं: हर एक अपना सेशन खोलता है और हर `tools`, `call`, और
`close_session` में अपना id पास करता है। [Bug Bash](/bug-bash) इसी का इस्तेमाल
करते हैं: रीप्रो को स्क्रिप्टेड टेस्ट में बदलने वाला वेरिफ़ाइंग सबएजेंट अपना खुद
का सेशन चलाता है।

| क्या थ्रो होता है | कब |
| --- | --- |
| `SESSION_REQUIRED` | कई सेशन खुले रहते हुए बिना `session` के कॉल। मैसेज खुले सेशन की लिस्ट देता है। |
| `NO_SESSION` | ऐसा `session` id जो खुला नहीं है। बंद हो रहे या खत्म हो चुके सेशन के लिए मैसेज कारण बताता है। |
| `SESSION_OPEN` | लिमिट से ज़्यादा `open_session`, या सर्वर बंद होते समय। |
| `CONFIG_IN_USE` | सेशन खुले रहते किसी दूसरे कॉन्फ़िग पर `open_session`, या `engine` से खोले गए सेशन के साथ किसी कॉन्फ़िग पर। |
| `ENGINE_IN_USE` | किसी पैकेज के अंदर बने इंजन पर दूसरा सेशन। |
| `CANCELLED` | ऐसा `open_session` जिसे क्लाइंट ने कैंसल किया या डिस्कनेक्ट किया, या जिसके दौरान सर्वर बंद हुआ, शुरू की गई चीज़ें रुकने के बाद। |

- सेशन `open_session` से लेकर अपने अटेम्प्ट के बंद होने तक अपना स्लॉट घेरे रखता
  है, इसलिए अभी बूट हो रहे या बंद हो रहे सेशन भी लिमिट में गिने जाते हैं।
- एक साथ खुले सेशन एक ही कॉन्फ़िग शेयर करते हैं: क्रेडेंशियल और सीक्रेट हर
  प्रोसेस में एक ही रजिस्ट्री से रिज़ॉल्व होते हैं।
- सर्वर बंद होते समय अभी खुल रहे सेशन को कैंसल करके उनका इंतज़ार करता है, हर सेशन
  बंद करता है, और नए सेशन मना कर देता है। कैंसल हुआ ओपन तब फ़ेल होता है जब उसने
  जो शुरू किया था (जैसे अपने `readyUrl` का इंतज़ार करती ऐप कमांड) वह रुक जाए।
- हर सेशन कॉन्फ़िग को नए सिरे से लोड करता है, पाथ से इंपोर्ट की गई फ़ाइलों (जैसे
  स्प्रेड किया हुआ बेस कॉन्फ़िग) तक, ताकि हर एक को अपने खुद के इंजन इंस्टेंस
  मिलें। टेस्ट चलाने वाला सेशन टेस्ट फ़ाइलें भी ऐसे ही लोड करता है। पैकेज के अंदर
  बना इंजन एक ही इंस्टेंस होता है जिसे हर सेशन शेयर करता है।
- एक ही ऐप कमांड पर चलने वाले सेशन उसकी प्रोसेस शेयर करते हैं: पहला सेशन उसे शुरू
  करता है, और आखिरी के बंद होने पर वह रुकती है। पोर्ट `0` के साथ डिक्लेयर URL को
  हर सेशन में अपना पोर्ट मिलता है, इसलिए अपनी प्रोसेस भी। जिस शेयर्ड स्टार्ट को
  इंतज़ार कर रहे हर सेशन ने छोड़ दिया हो वह कैंसल हो जाता है, और अगला सेशन उसे
  नए सिरे से शुरू करता है।
- मोबाइल पर हर सेशन को अपना सिम्युलेटर या एम्युलेटर चाहिए: हर डिवाइस के लिए एक
  टारगेट डिक्लेयर करें (हर एक में उसका `device` नाम देकर), और हर सेशन अपने
  टारगेट पर खोलें।
