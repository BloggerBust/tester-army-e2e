## रिपोर्ट अपलोड करें

हर जॉब के आख़िर में `.e2e/` अपलोड करें, टेस्ट फ़ेल हो तब भी। इसमें ये चीज़ें
होती हैं:

| पाथ | इसमें क्या है |
| --- | --- |
| `report.json` | रन रिपोर्ट। हर वह रन इसे लिखता है जो अपने टेस्ट तक पहुँचता है |
| `junit.xml` | `junit` रिपोर्टर (`--reporter list,junit`) के साथ: नतीजे, वे टेस्ट जिन्हें [टेस्ट फ़िल्टर](/filters) ने छोड़ा (skipped दिखते हैं), और `run` सूट में `APP_UNREACHABLE` जैसे स्टार्टअप फ़ेलियर |
| `results/` | हर टेस्ट के ट्रेस पेज, स्क्रीनशॉट और स्क्रीन डंप। `--video` के साथ, हर उस टारगेट का वीडियो भी जिसका इंजन रिकॉर्ड कर सकता है |

अपनी CI सर्विस के टेस्ट-रिपोर्ट इंटीग्रेशन को `.e2e/junit.xml` पर लगाएँ।
GitLab पर `junit.xml` हर फ़ेलियर के स्क्रीनशॉट का लिंक भी रखता है, तो वह
स्क्रीनशॉट टेस्ट रिपोर्ट में दिखता है।
`.e2e/` को कहीं और रखना हो, तो [`output`](/reference/config#output) ऑप्शन
इस्तेमाल करें।

## मॉडल क्रेडेंशियल

आपके प्रोवाइडर को जो क्रेडेंशियल चाहिए, वह जॉब को दें, जैसे
`AI_GATEWAY_API_KEY` ([मॉडल](/models) देखें)। जो टेस्ट कभी `agent` इस्तेमाल
नहीं करते, उन्हें कोई क्रेडेंशियल नहीं चाहिए।

<Warning>
जिस जॉब के पास key है, वह उसे अपने चलाए कोड को दे देता है: टेस्ट, कॉन्फ़िग
और डिपेंडेंसी। Key सिर्फ़ उन ब्रांच के बिल्ड को दें जिन पर आप भरोसा करते हैं।
जिस पुल रिक्वेस्ट के कोड पर आप भरोसा नहीं करते, उसे बिना सीक्रेट और बिना
write टोकन के चलाएँ। [सुरक्षा](/security) देखें।
</Warning>

Key CI सीक्रेट में रखें, और जहाँ हो सके, खर्च की लिमिट लगाएँ। GitHub फ़ोर्क
से आई पुल रिक्वेस्ट को सीक्रेट नहीं देता।

## CI में क्या बदलता है

`CI` में खाली स्ट्रिंग, `0` या `false` के अलावा कोई भी वैल्यू हो, तो CI मोड चालू
हो जाता है। यही डिफ़ॉल्ट अपनी मशीन पर चाहिए, तो `CI=1 npx e2e run` चलाएँ:

| सेटिंग | लोकल | CI |
| --- | --- | --- |
| `retries` | `0` | `1` |
| `workers` | आपके CPU कोर के आधे | `1` |
| `cache` सेट न हो तो | `read-write` | `read-only` |
| `.only` | चलता है | `ONLY_IN_CI` के साथ रिजेक्ट |
| `command.reuseExisting` | माना जाता है | नज़रअंदाज़, एक नोटिस के साथ |

वर्कर और रीट्राई के डिफ़ॉल्ट बदलने हैं, तो फ़्लैग इस्तेमाल करें:

<CodeGroup>
```bash npm
npx e2e run --workers 4 --retries 0
```

```bash pnpm
pnpm exec e2e run --workers 4 --retries 0
```

```bash bun
bunx e2e run --workers 4 --retries 0
```
</CodeGroup>

CI से कोई [टेलीमेट्री](/telemetry#in-ci) नहीं भेजनी, तो जॉब के `env` में
`E2E_TELEMETRY_DISABLED: '1'` जोड़ दें।

## मोबाइल जॉब

[होस्टेड डिवाइस सर्विस](/mobile#hosted-devices) न हो, तो हर प्लेटफ़ॉर्म को अपनी
अलग मशीन, बिल्ड और डिवाइस चाहिए:

| | iOS | Android |
| --- | --- | --- |
| मशीन | Xcode और सिम्युलेटर रनटाइम वाला macOS | KVM (नेस्टेड वर्चुअलाइज़ेशन) वाला Linux |
| बिल्ड | Release सिम्युलेटर `.app`, बिना साइनिंग | Release `.apk` |
| डिवाइस | बूट किया हुआ सिम्युलेटर | बूट किया हुआ एम्युलेटर |

दोनों प्लेटफ़ॉर्म पर Release बिल्ड बनाएँ। React Native या Expo का debug बिल्ड
अपना JavaScript Metro से लोड करता है। ये जॉब Metro शुरू नहीं करते, इसलिए ऐप एरर
स्क्रीन पर खुलता है। उदाहरणों में ऐसा React Native प्रोजेक्ट है जिसकी रिपॉज़िटरी
में `ios/` और `android/` हैं। आपके Expo प्रोजेक्ट में ये नहीं हैं, तो पहले
`npx expo prebuild` चलाएँ।

बिल्ड इंस्टॉल करें, फिर सूट चलाएँ:

<CodeGroup>
```bash npm
# iOS
xcrun simctl install booted path/to/MyApp.app
npx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
npx e2e run --target android --reporter list,junit
```

```bash pnpm
# iOS
xcrun simctl install booted path/to/MyApp.app
pnpm exec e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
pnpm exec e2e run --target android --reporter list,junit
```

```bash bun
# iOS
xcrun simctl install booted path/to/MyApp.app
bunx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
bunx e2e run --target android --reporter list,junit
```
</CodeGroup>

ये कमांड मानकर चलती हैं कि `ios` और `android` नाम के दो टारगेट हैं। दोनों में
ऐप के `bundleId` के साथ `mobile()` इंजन है।
[अपने ऐप को टारगेट करें](/mobile#point-at-your-app) देखें। बिल्ड सूट से
इंस्टॉल करवाना है, तो `app.appPath` सेट करें और `device.installApp()` कॉल करें।

ये नियम हर सर्विस पर लागू होते हैं:

- **हर प्लेटफ़ॉर्म का अलग जॉब।** `--target ios` Mac पर चलाएँ और
  `--target android` KVM वाले Linux पर। होस्टेड Mac में Apple Silicon होता है,
  जो नेस्टेड वर्चुअलाइज़ेशन नहीं कर सकता। इसलिए उन पर Android एम्युलेटर शुरू
  नहीं होता।
- **डिवाइस को अलग स्टेप में बूट करें।** कोई डिवाइस बूट न हो, तो इंजन
  agent-device से एक बूट करवाता है। लेकिन नए Linux रनर पर कोई एम्युलेटर इमेज
  नहीं होती। अलग स्टेप से यह भी साफ़ दिखता है कि बूट फ़ेल हुआ या टेस्ट।
- **iOS रनटाइम पिन करें।** नाम से चुना गया सिम्युलेटर (`iPhone 17`) इमेज का
  डिफ़ॉल्ट iOS चलाता है, और ऐक्सेसिबिलिटी ट्री iOS रिलीज़ के बीच बदल जाता है।
  ऐसे में रनर इमेज अपडेट होने पर कोई लोकेटर असर्शन फ़ेल हो सकता है, जबकि आपके
  कोड में कुछ नहीं बदला। उदाहरण एक तय रनटाइम पर सिम्युलेटर बनाते हैं और उसे UDID
  से बूट करते हैं। `iOS-26-5` की जगह वह रनटाइम लिखें जो इमेज में है
  (`xcrun simctl list runtimes`)।
- **`~/.agent-device/apple-runner/derived` कैश करें।** agent-device पहली बार
  किसी सिम्युलेटर को चलाते समय वहीं अपना XCUITest रनर बिल्ड करता है। पूरा
  `~/.agent-device` कैश न करें। बाकी हिस्से में पिछले डेमन का स्टेट होता है, और
  उसकी रिस्टोर की हुई कॉपी अगले रन को `Failed to communicate with daemon` पर
  रोक सकती है।
- **लोकल रिकॉर्डिंग रीप्ले करें।** रीप्ले कैश की key में ऐप होता है, डिवाइस
  नहीं। इसलिए आपके सिम्युलेटर पर रिकॉर्ड हुआ स्टेप CI वाले पर रीप्ले होता
  है। [रीप्ले कैश कमिट करें](/cache#commit-the-replay-cache)।

## पुल रिक्वेस्ट पर गेट लगाएँ

शून्य के अलावा कोई भी एग्ज़िट कोड जॉब को फ़ेल कर देता है। एजेंट का कोई स्टेप
फ़ेल हो, तब भी यही होता है। फ़ेल हुए रन पर मर्ज रोकना है, तो e2e जॉब को
required चेक बना दें। [रन को डीबग करना](/debugging#read-the-failure) में
हर एग्ज़िट कोड की लिस्ट है, और यह भी कि जॉब दोबारा चलाने से फ़ायदा हो सकता
है या नहीं।

चेक को प्रेडिक्टेबल रखने के लिए:

- हर `agent.act` को एक [एटॉमिक लक्ष्य](/core-concepts#goals) दें। फिर उसका
  नतीजा लोकेटर असर्शन या `agent.assert` से चेक करें।
- [रीप्ले कैश कमिट करें](/cache#commit-the-replay-cache)। रीप्ले हुआ
  `agent.act` कोई मॉडल कॉल नहीं करता। बिल्ट-इन एजेंट में कैश मिस, हैंड-ऑफ़ और
  एजेंट की हर परख (`agent.assert`, `agent.waitFor`, `agent.extract`), इन सब पर
  मॉडल कॉल होती है।
- फ़्लेकी टेस्ट पर नज़र रखें। जो टेस्ट सिर्फ़ CI रीट्राई पर पास होता है, रिपोर्ट
  उसे फ़्लेकी मार्क करती है।
- `--max-failures <n>` जोड़ें, तो इतने टेस्ट फ़ेल होते ही रन रुक जाता है। फिर
  टूटा हुआ डिप्लॉय बाकी हर स्टेप पर मॉडल कॉल नहीं खर्च करता। जॉब का एग्ज़िट कोड
  1 होता है।
- टेस्ट चलने के समय पर लिमिट लगानी है, तो `--max-duration <ms>` जोड़ें। घड़ी
  टेस्ट शुरू होने पर चलती है, ऐप स्टार्टअप के दौरान नहीं। जॉब का एग्ज़िट कोड 1
  होता है।

## सिर्फ़ असर वाले टेस्ट चलाएँ

पुल रिक्वेस्ट पर `--changed-since` पास करें। तब [टेस्ट फ़िल्टर](/filters) वे
टेस्ट छोड़ सकता है जिन पर बदलाव का असर पड़ने की उम्मीद कम है। अगर फ़िल्टर
टेस्ट को स्कोर देता है, जैसे डिसीज़न फ़िल्टर देता है, तो हर टारगेट पहले उन टेस्ट
की फ़ाइलें चलाता है जिनके फ़ेल होने के चांस सबसे ज़्यादा हैं। फ़्लैग न हो, जैसे
`main` पर, तो पूरा सूट चलता है।
[डिसीज़न फ़िल्टर जोड़ें](/filters#add-the-decision-filter) देखें।

CI में डिफ़ॉल्ट एक वर्कर होता है। तब फ़ाइलों का क्रम सिर्फ़ रेलेवेंस बैंड तय करते
हैं, और बराबरी पर कलेक्शन का क्रम चलता है। वजह यह है कि e2e
[टाइमिंग हिस्ट्री](#cache-the-timings-history) तभी पढ़ता है जब एक से ज़्यादा
वर्कर हों। [सबसे संभावित को पहले शुरू करें](/filters#start-the-likeliest-first)
देखें।

## टाइमिंग हिस्ट्री कैश करें

एक से ज़्यादा वर्कर हों, तो `e2e run` सबसे लंबी फ़ाइलें पहले शुरू करता है। जिन
फ़ाइलों का समय उसके पास नहीं है, वे इनसे भी पहले चलती हैं। यह क्रम
`<output>/timings.json` (डिफ़ॉल्ट `.e2e/timings.json`) से तय होता है। यह कुछ KB
की फ़ाइल है, और रन इसे तब अपडेट करता है जब उसने कम से कम एक फ़ाइल पूरी चलाई हो।
नए CI चेकआउट में यह फ़ाइल नहीं होती। इसलिए रन से पहले इसे अपने CI कैश से
रिस्टोर करें और रन के बाद सेव करें।
[GitHub Actions](/ci/github-actions#cache-the-timings-history) पेज पर इसका स्टेप है।

- यह फ़ाइल बस सलाह देती है। फ़ाइल गायब हो, खराब हो या इनवैलिड हो, तो उसे
  हिस्ट्री नहीं माना जाता, और रन पिछली `report.json` से काम चलाता है। रिस्टोर की
  हुई फ़ाइल फ़ाइलों का क्रम बदल सकती है, नतीजा कभी नहीं।
- रन किसी फ़ाइल का समय तभी लिखता है जब उसने पूरी फ़ाइल चलाई हो। `--grep` या
  `--last-failed` रन किसी फ़ाइल का कुछ हिस्सा ही चलाए, तो उसकी एंट्री जैसी थी वैसी
  रहती है।
- CI में डिफ़ॉल्ट एक वर्कर है। हिस्ट्री का फ़ायदा चाहिए, तो
  [`workers`](/reference/config#workers) सेट करें या `--workers` पास करें।
- कैश की key ब्रांच के हिसाब से रखें, और फ़ॉलबैक में `main` रखें। तब नई पुल
  रिक्वेस्ट `main` की हिस्ट्री से शुरू होती है। [शार्डिंग](#sharding) करते हैं,
  तो key में शार्ड इंडेक्स भी जोड़ें।
- `--timings <file>` किसी दूसरे पाथ से पढ़ता और उसी में लिखता है।

## शार्डिंग

`--shard <index/total>` सूट का एक हिस्सा चलाता है। हर जॉब वही कमांड अपने इंडेक्स
के साथ चलाता है, और हर मशीन सूट को एक ही तरीके से बाँटती है। जिस शार्ड में कोई
टेस्ट न हो, वह `NO_TESTS` के साथ फ़ेल होता है। अगर मैट्रिक्स में टेस्ट से ज़्यादा
शार्ड हो सकते हैं, तो `--pass-with-no-tests` जोड़ें। बाँटने के नियम
[CLI रेफ़रेंस](/reference/cli#flags) में हैं।

GitHub Actions पर मैट्रिक्स हर शार्ड के लिए एक जॉब चलाता है:

```yaml
jobs:
  e2e:
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3]
    steps:
      # ...
      - run: npx e2e run --shard ${{ matrix.shard }}/3 --reporter list,junit
```

हर शार्ड की `report.json` और `junit.xml` ऐसे नाम से अपलोड करें जिसमें शार्ड
इंडेक्स हो। e2e अभी शार्ड रिपोर्ट मर्ज नहीं कर सकता।

## फ़ेल हुए टेस्ट दोबारा चलाना

`--last-failed` सिर्फ़ वे टेस्ट चलाता है जो पिछले रन में पास नहीं हुए। यह लिस्ट
आउटपुट डायरेक्टरी की `report.json` से आती है। इसे पहले रन वाले स्टेप में ही
चलाएँ:

```yaml
      - run: npx e2e run || npx e2e run --last-failed
```

दोबारा वाला रन पहले रन के आर्टिफ़ैक्ट रहने देता है। अपने आर्टिफ़ैक्ट वह हर टेस्ट
की डायरेक्टरी में `rerun-<n>/` के अंदर लिखता है। इसलिए एक ही अपलोड में दोनों आ
जाते हैं। किसे "पास नहीं हुआ" माना जाता है, यह [CLI रेफ़रेंस](/reference/cli#flags)
में है।

अलग जॉब के रनर पर पिछली रिपोर्ट नहीं होती। पहले उसे आउटपुट डायरेक्टरी में
डाउनलोड करें, या फ़ेल हुआ जॉब दोबारा चलाएँ।
