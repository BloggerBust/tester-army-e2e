रीप्ले कैश किसी `agent.act()` स्टेप के एक्शन रिकॉर्ड करता है, लेकिन तभी जब बाद
की कोई जाँच नतीजे को कन्फ़र्म कर दे। अगले रन में रनर ये एक्शन बिना मॉडल कॉल के
रीप्ले करता है। अगर कोई कंट्रोल या उम्मीद के मुताबिक आख़िरी स्थिति अब मेल नहीं
खाती, तो एजेंट मौजूदा स्क्रीन से काम संभाल लेता है।
[सेल्फ़-हीलिंग टेस्ट](/self-healing) देखें।

`agent.assert`, `agent.waitFor` और `agent.extract` हमेशा लाइव चलते हैं। रन
समरी में नतीजों की गिनती दिखती है:

```text
           AI  4.1k tokens · 2 model calls · openai/gpt-6-luna-fast
        Cache  4 replayed · 1 handed off · 1 missed · 1 not saved
```

`not saved` पास हुए और फ़्लेकी टेस्ट के वे स्टेप गिनता है जिनका
[`step.cache.write`](#when-a-recording-is-written) पास हुए अटेम्प्ट में
`unconfirmed`, `no-change` या `not-written` था।

## रिकॉर्डिंग कब लिखी जाती है

टेस्ट के आख़िर में उसके नतीजे की जाँच रखें। `read-write` मोड में रनर अटेम्प्ट के
आख़िर में हर `act` की रिकॉर्डिंग सेव करता है, बशर्ते बाद का कोई वेरिफ़िकेशन स्टेप
पास हुआ हो। आख़िर की एक जाँच अपने से पहले के हर `act` को कन्फ़र्म कर देती है।

```ts title="tests/cart.e2e.ts"
import { expect, test } from 'e2e';

test('adds an item', async ({ app, agent, screen }) => {
  await app.open('/cart');

  await agent.act('add one item to the cart');

  await expect(screen.getByRole('status')).toHaveText('1 item');
});
```

| वेरिफ़िकेशन माना जाता है | वेरिफ़िकेशन नहीं माना जाता |
| --- | --- |
| `expect(locator).toHaveText(...)` और दूसरे लोकेटर मैचर | सादी वैल्यू पर `expect(value).toBe(...)` |
| `expect(browser).toHaveURL(...)` और दूसरे इंजन असर्शन | `expect.poll(...)` |
| `locator.waitFor()`, `browser.waitForURL()` | `locator.textContent()` और वैल्यू पढ़ने वाली दूसरी कॉल |
| `agent.assert(...)`, `agent.waitFor(...)` | `agent.extract(...)`, कोई दूसरा `act`, अटेम्प्ट का पास होना |

`step.cache.write` सिर्फ़ रिपोर्ट में आता है। इससे पता चलता है कि अटेम्प्ट ख़त्म
होने पर रिकॉर्डिंग का क्या हुआ:

| `step.cache.write` | मतलब |
| --- | --- |
| `saved` | अगले रन के लिए रिकॉर्ड हो गई। |
| `kept` | एंट्री जैसी थी, वैसी ही है। |
| `unconfirmed` | सेव नहीं हुई: स्टेप के बाद कोई जाँच पास नहीं हुई। टेस्ट को लोकेटर या इंजन असर्शन से, या `agent.assert` से ख़त्म करें। या `locator.waitFor()` या `agent.waitFor` से उस स्थिति का इंतज़ार करें। |
| `evicted` | एंट्री डिलीट हो गई: उसका रीप्ले फ़ेलियर या रिपेयर पर ख़त्म हुआ, या अटेम्प्ट फ़ेल होने से पहले किसी जाँच ने उसे कन्फ़र्म नहीं किया। |
| `no-change` | कुछ रिकॉर्ड नहीं हुआ: न कोई कंट्रोल दिखा, न गायब हुआ, न उसकी स्थिति बदली, और रूट भी वही रहा। इसमें वह स्टेप भी आता है जिसका इकलौता बदलाव [किसी दूसरी साइट के फ़्रेम](/browser#reach-into-an-iframe) के अंदर हुआ। ऐसा स्टेप हर रन में लाइव चलता है। |
| `not-written` | सेव नहीं हुई: स्टोर ने राइट रिजेक्ट कर दिया, या रिकॉर्डिंग लेने से मना कर दिया, जैसे फ़ाइल स्टोर की साइज़ लिमिट से बड़ी रिकॉर्डिंग। |

जिस स्टेप ने कोई एक्शन नहीं लिया, वह कुछ रिकॉर्ड नहीं करता। उसकी रिपोर्ट में कोई
`write` भी नहीं होता।

फ़ेल होने वाला अटेम्प्ट भी वे स्टेप सेव करता है जो फ़ेलियर से पहले वेरिफ़ाई हो चुके
थे। जो एंट्री वेरिफ़ाई नहीं हुईं, और जो रीप्ले फ़ेलियर में शामिल थे, उन्हें वह
डिलीट कर देता है। किसी फ़ेल होते असर्शन को ठीक करते समय सेटअप वाले लक्ष्यों की
रिकॉर्डिंग बचाए रखनी है? तो सेटअप के आख़िर में उसकी स्थिति का इंतज़ार रखें, जैसे
`locator.waitFor()`। इसके लिए कस्टम स्टोर में `delete` मेथड होना चाहिए। रन
कैंसल करने पर कैश जैसा था, वैसा ही रहता है।

<Accordion title="ऐसे फ़ेलियर जिनमें किसी मॉडल ने जवाब नहीं दिया">
अगर किसी अटेम्प्ट के सारे फ़ेलियर ऐसे हैं जिनमें किसी मॉडल ने जवाब नहीं दिया,
तो वह कोई एंट्री नहीं हटाता, क्योंकि इनसे ऐप के बारे में कुछ पता नहीं चलता:

- `MODEL_UNAVAILABLE`: कोई मॉडल कॉन्फ़िगर नहीं है, या GitHub Copilot उस अकाउंट
  को यह मॉडल नहीं देता।
- `MODEL_PROVIDER_FAILED`: प्रोवाइडर ने एरर लौटाया, जैसे key गायब थी या रिजेक्ट
  हुई, रेट लिमिट लगी, या 5xx आया। या किसी रिक्वेस्ट को 120 सेकंड में कोई जवाब नहीं
  मिला।

तो मॉडल तक पहुँच न होने पर भी `read-write` रन अपनी रिकॉर्डिंग रखता है। इसमें वह
स्टेप भी शामिल है जो ऐसे `agent.assert` से पहले रीप्ले हुआ, जो अपने मॉडल तक नहीं
पहुँच सका।

ये फ़्लो का फ़ेलियर माने जाते हैं: मॉडल का ऐसा जवाब जो किसी काम का नहीं
(`MODEL_OUTPUT_INVALID`, `CONTEXT_OVERFLOW`), मॉडल का मना करना (`MODEL_REFUSED`),
`STEP_TIMEOUT` (तब भी जब कोई रिक्वेस्ट अभी खुली हो), और उसी अटेम्प्ट का कोई भी
दूसरा फ़ेलियर, जैसे `afterEach` का कोई असर्शन।
</Accordion>

## क्या मेल खाना चाहिए

कैश एंट्री एक टेस्ट, एक टारगेट, एक निर्देश, पैरामीटर के एक सेट और एक एजेंट से
बंधी होती है। इनमें से कुछ भी बदले, तो कैश मिस होता है:

- टेस्ट, उसके `describe` ग्रुप या टारगेट का नाम बदलना, या टेस्ट फ़ाइल को कहीं और
  ले जाना,
- निर्देश या कोई आम पैरामीटर बदलना,
- किसी दूसरे कॉन्फ़िगर किए गए एजेंट से चलाना (`agent: ['buyer', 'admin']` हर
  एजेंट की अलग एंट्री रिकॉर्ड करता है), या एजेंट का `context` या टेस्ट का
  `agentContext` बदलना (उसमें कोई सीक्रेट हो, तो key में सिर्फ़ उसका नाम जाता है),
- दूसरे इंजन पर जाना, या प्रोजेक्ट id या ऐप की पहचान बदलना।

मॉडल बदलने से कैश मिस नहीं होता, और इंजन अपग्रेड करने से भी नहीं। नया वर्ज़न
किसी नोड को अलग तरह से रिज़ॉल्व करे, तो वह नोड रीप्ले के समय मिस होता है।

नया मॉडल परखना हो, तो `--no-cache` इस्तेमाल करें। अगर एंट्री में दर्ज है कि उसे
किसने रिकॉर्ड किया, तो रीप्ले में `step.cache.recordedBy` दिखता है। पुरानी
एंट्री में, या जिनमें यह जानकारी नहीं है, यह फ़ील्ड नहीं होता।

टाइमस्टैम्प या नया ईमेल पता हर रन में मिस होगा। ऐसी वैल्यू को `unique()` में
लपेट दें। फिर रीप्ले के समय रनर मौजूदा वैल्यू डाल देता है:

```ts
import { unique } from 'e2e';

const name = `E2E ${Date.now()} Company`;
await agent.act('create a company named {name}', { params: { name: unique(name) } });
await expect(screen.getByRole('heading', { name })).toBeVisible();
```

फ़्लो में जो डेटा भरा या जाँचा जाता है, उसके लिए `unique()` इस्तेमाल करें। जो
ऑप्शन फ़्लो बदलते हैं, जैसे प्लान का नाम, उनके लिए आम पैरामीटर रखें। रनर
मौजूदा वैल्यू वहाँ भी डालता है जहाँ URL उसे अपने तरीके से लिखता है (`%20`,
`+`)। स्क्रीन कई लाइनों वाली वैल्यू को एक लाइन में दिखाए, तो रनर वहाँ भी यही
करता है। अगर कोई `unique()` वैल्यू किसी दूसरे पैरामीटर की वैल्यू के बराबर है
या उसके अंदर आती है, तो स्टेप रिकॉर्ड नहीं होता: `step.cache.notRecorded` में
`param-collision` आता है, और अगला रन उसे रिकॉर्ड करता है।

प्रीव्यू URL हर डिप्लॉय पर बदलते हों, तो
[`app.identity`](/reference/config#the-app-under-test) सेट करें, ताकि कैश की
पहचान एक ही रहे। डिवाइस पर रीप्ले
[स्क्रीन टाइटल](/reference/mobile#replay-cache-on-a-device) को पाथ की तरह
इस्तेमाल करता है।

## टेस्ट ठीक करते समय उसे दोबारा चलाएँ

फ़ेल होता टेस्ट ठीक करते समय कैश को `read-write` मोड में चालू रखें। लोकल पर यही
डिफ़ॉल्ट है। [स्ट्रिक्ट कैश मोड](#fail-on-a-stale-recording) से बाहर रहें,
क्योंकि वह कभी नहीं लिखता। `CI` सेट हो और मोड सेट न हो, तो मोड `read-only` होता
है। फ़ेल हुआ रन वे रिकॉर्डिंग रखता है जिन्हें किसी जाँच ने फ़ेलियर से पहले
[कन्फ़र्म किया था](#when-a-recording-is-written)। अगला रन इन लक्ष्यों को बिना
मॉडल कॉल के रीप्ले करता है, जब तक हर रीप्ले स्क्रीन से मेल खाता रहे।

1. सिर्फ़ वही टेस्ट चलाएँ। इसके लिए उस लाइन का नंबर दें जहाँ उसका `test(` शुरू
   होता है:
   `npx e2e run tests/cart.e2e.ts:3`।
2. टेस्ट का नाम न बदलें, और जो लक्ष्य पास हो रहा है, उसके शब्द भी न बदलें। दोनों
   से [कैश मिस होता है](#what-must-match)। नाम बदलने पर टेस्ट के हर लक्ष्य का, और
   शब्द बदलने पर सिर्फ़ उसी लक्ष्य का।
3. अगर रीट्राई चालू हैं (कॉन्फ़िग में `retries`, या `CI` सेट है), तो
   `--retries 0` जोड़ें। टेस्ट या उसके `describe` पर दिया `retries` ऑप्शन फ़्लैग
   पर भारी पड़ता है। रीट्राई रीप्ले नहीं करता, इसलिए वह हर लक्ष्य लाइव चलाता है।
4. टेस्ट पास हो जाए, तो उसे एक बार `--no-cache` के साथ चलाएँ। हर लक्ष्य लाइव
   चलेगा। इससे पता चलता है कि एजेंट बिना रिकॉर्डिंग के भी वहाँ तक पहुँच जाता है।

## रीप्ले कैसे काम करता है

1. रनर शुरुआती स्क्रीन जाँचता है: रूट वही होना चाहिए।
2. रनर हर रिकॉर्ड किए गए कंट्रोल को रोल, नाम, टेस्ट id और आसपास के कॉन्टेक्स्ट से
   ढूँढता है, और उस पर वही एक्शन दोहराता है। कोई कंट्रोल न दिखे, तो रनर उसका
   इंतज़ार करता है। मैच साफ़ न हो, तो रुक जाता है।
3. रनर आख़िरी रूट जाँचता है, और यह भी कि ऑरिजिनल स्टेप ने क्या बदला था: कौन से
   कंट्रोल दिखे, उनकी चेक्ड, सिलेक्टेड, एक्सपैंडेड या प्रेस्ड स्थिति के साथ, और
   कौन से गायब हुए।
4. आख़िर में रनर बिना मॉडल कॉल के स्टेप पूरा कर देता है। या एजेंट को आगे बढ़ने
   देता है, साथ में यह ब्योरा देकर कि क्या चला और रीप्ले क्यों रुका।

टाइप की गई वैल्यू वैसे ही रीप्ले होती हैं जैसे रिकॉर्ड हुई थीं। सीक्रेट भरने वाला
एक्शन मौजूदा वैल्यू को नाम से रिज़ॉल्व करता है, और ऑथराइज़ेशन से दोबारा गुज़रता है।

जैसे ही रिकॉर्ड किए गए बदलाव दिखते हैं, रीप्ले पूरा हो जाता है। हो सकता है तब तक
उनके नीचे का कंटेंट लोड न हुआ हो। स्टेप के बाद लोड होने वाला कंटेंट जाँचना हो, तो
`agent.assert` की जगह `agent.waitFor` इस्तेमाल करें। `agent.waitFor` उस कंटेंट
का इंतज़ार करता है, जबकि `agent.assert` स्क्रीन को एक बार परखता है।

रूट यानी ऑरिजिन, पाथ और क्वेरी। रिकॉर्ड की id और फ़्रैगमेंट इसमें नहीं गिने
जाते। पाथ या क्वेरी में आने वाले id, टोकन, टाइमस्टैम्प और कैश बस्टर id
प्लेसहोल्डर की तरह पढ़े जाते हैं। इसलिए `/orders/42?t=1727780000` और
`/orders/7?t=1727780999` एक ही रूट हैं।

क्वेरी की बाकी हर वैल्यू रूट का हिस्सा है: `?mode=safe` और `?mode=unsafe` अलग
हैं। `/companies` और `/companies?tab=notes` भी अलग हैं, और कोई नया ट्रैकिंग
पैरामीटर जुड़ने पर भी रूट अलग हो जाता है। `/products/summer-sneaker` और
`/products/winter-boot` भी अलग रूट हैं।

ऐप के अपने ऑरिजिन पर लोकेशन की तुलना उसके पाथ से होती है। इसलिए रिकॉर्डिंग उस
प्रीव्यू डिप्लॉयमेंट पर भी चलती है जिसका `app.identity` वही है। किसी भी दूसरे
ऑरिजिन का पेज अलग रूट है।
</Accordion>

<Accordion title="आख़िरी जाँच स्क्रीन को कैसे पढ़ती है">
- रीप्ले के दौरान कम से कम एक रिकॉर्ड किया गया बदलाव होना ज़रूरी है। जो नतीजा
  एक्शन से पहले ही स्क्रीन पर था, उससे कुछ साबित नहीं होता। अगर स्टेप का आख़िरी
  एक्शन किसी दूसरे रूट पर ले गया, तो रूट का यही बदलना सबूत है।
- अगर रीप्ले से कोई ऐसा अलर्ट आया जो रिकॉर्डिंग में कभी नहीं दिखा, तो रीप्ले रुक
  जाता है। वेब इंजन [Next.js](/frameworks/nextjs#fix-next-js-problems) App
  Router के रूट अनाउंसर को ऑब्ज़र्व नहीं करता, इसलिए अनाउंसर का टाइटल दोहराना कभी
  नहीं गिना जाता।
- जो टेक्स्ट हर रन में बदलता है, जैसे तारीख, अवधि या id, उसे तब छोड़ दिया जाता है
  जब स्टेप के डेल्टा (स्टेप से हुए बदलाव) की किसी भी तरफ़ कोई स्टेबल बदलाव हो। फ़र्क़
  नहीं पड़ता कि कुछ दिखा या गायब हुआ। ऐसा कोई बदलाव न हो, तो वह टेक्स्ट जाँच में
  रहता है, और उसकी वैल्यू बदलने पर रीप्ले एजेंट को सौंप दिया जाता है। अलर्ट में वह
  प्लेसहोल्डर की तरह पढ़ा जाता है। जिस नोड की पहचान सिर्फ़ ऐप की बनाई टेस्ट id
  (`node-<uuid>`) से होती है, उसे भी ऐसे ही छोड़ा जाता है। अगर उसे रखा गया, तो
  दिखने वाले नोड की id उस पैटर्न की कोई भी हो सकती है। गायब हुए नोड की जाँच अब भी
  उसकी सटीक id से होती है।
- मान लीजिए स्टेप ने जिस स्क्रीन पर एक्शन लिया, उसी पर स्टेप की वजह से कोई गिनती
  दिखने लगी। अगर वह गिनती बताती है कि किस चीज़ की है, जैसे `3 records imported`
  या `42件`, तो रीप्ले में भी उसे वैसा ही दिखना चाहिए। जो गिनती सिर्फ़ बदली
  (`41 items` से `42 items`), या जो उस स्क्रीन पर है जहाँ स्टेप नेविगेट करके
  गया, उसे तभी छोड़ा जाता है जब डेल्टा में उसकी अपनी तरफ़ कोई स्टेबल बदलाव हो।
  वरना गिनती जाँच में रहती है, चाहे दूसरी तरफ़ कोई स्टेबल बदलाव हो। बैज जैसी
  अकेली संख्या ऊपर वाले टेक्स्ट नियम से चलती है।
- बिना नाम वाला कंट्रोल अपनी जगह से ढूँढा जाता है। यानी नाम वाली जिस पंक्ति, लिस्ट
  आइटम या ग्रुप में वह है, उसके अंदर उसकी तरह के बिना नाम वाले कंट्रोल में उसकी
  जगह क्या है। जो कंट्रोल सिर्फ़ जनरेट की गई टेस्ट id से पहचाना जाता है, वह भी इसी
  तरह id पैटर्न से ढूँढा जाता है, या तब, जब उस पैटर्न वाला वही अकेला कंट्रोल था।
</Accordion>

## कोई स्टेप रीप्ले क्यों नहीं हुआ

हर `act` स्टेप `step.cache` रिपोर्ट करता है। उस स्टेप के लिए कैशिंग बंद हो, तो
यह फ़ील्ड नहीं होता। `agent.act()` इसे `result.cache` के रूप में लौटाता है,
`write` के बिना। [ट्रेस पेज](/debugging#traces) इसे स्टेप के नीचे दिखाता है।

| रन समरी | `step.cache.mode` | मतलब |
| --- | --- | --- |
| `replayed` | `self-finalized` | रिकॉर्डिंग बिना मॉडल कॉल के पूरी हो गई। |
| `handed off` | `agent-concluded` | रीप्ले शुरू हुआ, फिर एजेंट ने काम संभाल लिया। |
| `missed` | `missed` | एजेंट ने स्टेप शुरू से चलाया। |

`handed off` और `missed`, दोनों में `step.cache.reason` होता है।
`step.cache.detail` बताता है कि रीप्ले कहाँ रुका और क्यों
(`at action 2 of 3, tap button "Apply": ...`)। `end-mismatch` के बाद यह बताता है
कि रिकॉर्ड किए गए कौन से नोड नहीं दिखे और कौन से गायब नहीं हुए। साथ में यह ऐसे
हर अलर्ट का नाम भी बताता है जो रिकॉर्डिंग में कभी नहीं आया। या फिर यह बताता है
कि नतीजा रीप्ले के एक्शन से पहले ही दिख चुका था। `step.cache.entry` एंट्री की
key है, और फ़ाइल स्टोर में उसकी फ़ाइल का नाम (`<entry>.json`) भी।

| वजह | क्या हुआ | क्या करें |
| --- | --- | --- |
| `no-entry` | इस स्टेप और इसके पैरामीटर से कोई रिकॉर्डिंग मेल नहीं खाती। | अगला वेरिफ़ाइड पास इसे रिकॉर्ड कर लेगा, बशर्ते स्टेप का `step.cache.write` `no-change` न हो। |
| `retry` | रीट्राई कभी रीप्ले नहीं करते, सिर्फ़ `--strict-cache` या `cache.strict` में करते हैं। | कुछ नहीं। |
| `invalid-entry` | फ़ाइल पढ़ी नहीं जा सकती, 1 MiB से बड़ी है, या किसी दूसरे स्कीमा वर्ज़न की है। | `npx e2e cache clear`। |
| `truncated` | रिकॉर्डिंग किसी लिमिट से टकरा गई, [नीचे](#limits-and-gaps) देखें। | स्टेप को बाँट दें, या सीक्रेट को `Secret` की तरह पास करें। |
| `wrong-context` | ऐप उस रूट पर नहीं था जिस पर स्टेप रिकॉर्ड हुआ था। [रीप्ले कैसे काम करता है](#how-a-replay-works) देखें। | स्टेप से पहले वही स्क्रीन खोलें। |
| `target-not-found` | रिकॉर्ड किया गया कोई कंट्रोल 15 सेकंड में नहीं दिखा। या उसका कोई नाम नहीं है, और उसे उसके जैसे दूसरे कंट्रोल से अलग करने के लिए कोई नाम वाला कंटेनर भी नहीं है। | UI बदल गया है: अगला पास होने वाला रन इसे फिर से रिकॉर्ड कर लेगा। बिना नाम वाले कंट्रोल को लेबल दें, या उसे नाम वाली पंक्ति या ग्रुप में रखें। |
| `target-ambiguous` | मेल खाने वाले कंट्रोल की गिनती बदल गई। | बार-बार आने वाले कंट्रोल को अलग-अलग नाम दें, या यूनीक टेस्ट डेटा इस्तेमाल करें। |
| `gap` | किसी एक्शन को रीप्ले नहीं किया जा सकता, [नीचे](#limits-and-gaps) देखें। | यह हिस्सा एजेंट लाइव करता है। स्टेबल वैल्यू `params` में रखें। |
| `action-failed` | ऐप ने रीप्ले किया गया एक्शन रिजेक्ट कर दिया। | ऐप चेक करें। |
| `action-uncertain` | रीप्ले किया गया एक्शन फ़ेल हुआ, और पता नहीं कि उसका असर हुआ या नहीं। एजेंट से कहा जाता है कि दोबारा एक्शन लेने से पहले वह यह चेक कर ले। | ऐप चेक करें। |
| `viewport-changed` | सिर्फ़ एक पॉइंट (कोऑर्डिनेट) पर किया गया टैप, होवर या ड्रैग किसी दूसरे साइज़ के व्यूपोर्ट पर रिकॉर्ड हुआ था। | व्यूपोर्ट का साइज़ तय रखें। |
| `end-mismatch` | हर एक्शन चला, लेकिन [आख़िरी जाँच](#how-a-replay-works) फ़ेल हो गई। | पिछले रन का बचा डेटा, आने-जाने वाला बैनर, या कोई रिग्रेशन। यूनीक टेस्ट डेटा और `afterEach` में क्लीनअप से मदद मिलती है। |

फ़ेलियर में कैश का हाथ है या नहीं, यह देखने के लिए एक बार कैश के बिना चलाएँ:

<CodeGroup>
```bash npm
npx e2e run --no-cache
```

```bash pnpm
pnpm exec e2e run --no-cache
```

```bash bun
bunx e2e run --no-cache
```
</CodeGroup>

### सीमाएँ और गैप

रिकॉर्डिंग `truncated` होती है, जब स्टेप ने:

- 50 से ज़्यादा एक्शन लिए, जो सिर्फ़ तब हो सकता है जब `maxSteps` 50 से ऊपर हो,
- 4,096 कैरेक्टर से लंबी वैल्यू या URL टाइप किया, या ऐसी वैल्यू या URL जिसमें
  कोई रजिस्टर किया गया सीक्रेट है,
- ऐसे कंट्रोल पर एक्शन लिया जिसका कोई काम का ब्योरा नहीं है।

`gap` ऐसा एक्शन है जिसे कैश दोहरा नहीं सकता: कुछ बदलने वाला
[प्रोजेक्ट टूल](/tools), या ऐसी वैल्यू जो एजेंट ने स्क्रीन से पढ़ी, स्क्रीनशॉट
देखकर टाइप की, या तारीख से निकाली। `step.cache.derived` बताता है कि कौन सा नियम
लगा: `whole-node` (किसी कंट्रोल का पूरा नाम या टेक्स्ट), `minted-token` (ऐसा कोड
या id जो ऐप ने अपने अलग शब्द की तरह दिखाया, या
`autocomplete="one-time-code"` वाले फ़ील्ड में टाइप की गई कोई भी वैल्यू), `date`
या `pixels`। निर्देश या `params` से आई वैल्यू रीप्ले होती हैं, और वे भी जो एजेंट
ने खुद बनाईं। one-time-code फ़ील्ड में सिर्फ़ वही पूरा कोड रीप्ले होता है जो
निर्देश या `params` में साफ़ लिखा हो।

## रिकॉर्डिंग में क्या होता है

हर एंट्री `.e2e/cache/` में एक JSON फ़ाइल है। फ़ाइल का नाम उसकी key के हैश से
बनता है। इसमें एक्शन, जिन कंट्रोल पर एक्शन हुआ उनका ब्योरा, टाइप किया गया
टेक्स्ट, स्टेप की समरी और आख़िरी जाँचें होती हैं: रूट, और ज़्यादा से ज़्यादा आठ
कंट्रोल जो दिखे और आठ जो गायब हुए। एंट्री में प्रॉम्प्ट, बातचीत, स्क्रीनशॉट,
ऑब्ज़र्व किए गए ट्री या सीक्रेट की वैल्यू नहीं होतीं। सीक्रेट भरने पर सिर्फ़
सीक्रेट का नाम सेव होता है।

<Warning>
बाकी टाइप की गई वैल्यू जैसी टाइप हुईं, वैसी ही सेव होती हैं। रिकॉर्डिंग शेयर करने
से पहले उन्हें देख लें। [कैश पर भरोसा](/reference/security#cache-trust)
देखें।
</Warning>

## मोड

| मोड | रीप्ले करता है | रिकॉर्ड करता है | डिफ़ॉल्ट |
| --- | --- | --- | --- |
| `'read-write'` | हाँ | हाँ | लोकल पर |
| `'read-only'` | हाँ | नहीं | CI में, जब `cache` सेट न हो |
| `'off'` | नहीं | नहीं | एक रन के लिए `--no-cache` |

```ts title="e2e.config.ts fragment"
cache: 'off',
// or
cache: { mode: 'read-write', dir: '.e2e/cache' },
```

`--no-cache` कॉन्फ़िग को ओवरराइड करता है। `read-only` मोड में पुरानी पड़ चुकी
एंट्री तब तक रहती हैं जब तक कोई `read-write` रन उन्हें बदल न दे। कस्टम
`cache.store` फ़ाइल स्टोर की जगह ले लेता है, और CI में उसका डिफ़ॉल्ट `read-only`
नहीं होता। `e2e explore` और `e2e mcp` सेशन कैश इस्तेमाल नहीं करते। लेकिन जो
टेस्ट कोई सेशन चलाता है ([`open_session {test}`](/reference/mcp#running-a-test)),
वह टेस्ट कैश को वैसे ही इस्तेमाल करता है जैसे किसी रन का पहला अटेम्प्ट।

## कई चेकआउट में कैश शेयर करें

किसी प्रोजेक्ट के हर चेकआउट को एक ही डायरेक्टरी पर पॉइंट करने के लिए
`E2E_CACHE_DIR` सेट करें, या एक रन के लिए `--cache-dir` दें। दोनों में से कोई भी
`cache.dir` की जगह लेता है, और प्रोजेक्ट रूट से रिज़ॉल्व होता है (`~` या शुरू का
`~/` आपकी होम डायरेक्टरी है)। मोड पर इनका कोई असर नहीं होता। कस्टम
`cache.store` के साथ `--cache-dir` देना एरर है, और `E2E_CACHE_DIR` को नज़रअंदाज़
किया जाता है। पैरलल रन एक ही डायरेक्टरी शेयर कर सकते हैं: हर राइट अपनी फ़ाइल को
एटॉमिक तरीके से बदलता है। एंट्री की key में प्रोजेक्ट शामिल होता है, इसलिए हर चेकआउट को
एक ही `projectId` (या `package.json` का `name`) दें। दोनों न हों, तो हर चेकआउट
का पाथ ही उसकी पहचान बन जाता है, और उनके बीच कुछ भी रीप्ले नहीं होता।

- चेकआउट एंट्री शेयर करते हैं। इनमें से किसी में भी रन फ़ेल हो, तो एंट्री हट जाती
  है। और जिन चेकआउट में ऐप की पहचान एक है लेकिन ऐप कोड अलग, वे एक-दूसरे की एंट्री
  ओवरराइट करते हैं (जो आख़िर में लिखे, उसी की चलती है)।
- जब तक ओवरराइड सेट है, `cache.dir` में कमिट किया गया कैश पढ़ा नहीं जाता।
- हर प्रोजेक्ट के लिए अलग डायरेक्टरी रखें। एक डायरेक्टरी में दो प्रोजेक्ट हों, तो
  `cache.strict` में झूठा `REPLAY_STALE` आ सकता है।

```bash
E2E_CACHE_DIR=~/.cache/my-app/e2e npx e2e run
```

## रीप्ले कैश कमिट करें

<span id="commit-your-traces" />

`e2e init` `.gitignore` में `.e2e/cache/` जोड़ देता है। इसलिए हर मशीन अपनी
रिकॉर्डिंग खुद बनाती है, और CI बिना किसी रिकॉर्डिंग के शुरू होता है। रीप्ले शेयर
करने हों, तो वह लाइन हटाएँ और डायरेक्टरी कमिट करें। जब तक आप
`cache: 'read-write'` सेट न करें, CI `read-only` रहता है। कमिट की गई एंट्री को
टेस्ट डेटा की तरह मानें। जिस पुल रिक्वेस्ट में वे दोबारा रिकॉर्ड हुईं, उसी में
उन्हें रिव्यू करें।

कुछ बदला न हो, तो लोकल रन कमिट की गई डायरेक्टरी को नहीं छेड़ते। रीप्ले हुआ स्टेप
अपनी एंट्री कभी दोबारा नहीं लिखता। और जिस लाइव रिकॉर्डिंग के एक्शन, पाथ और एंकर
पहले जैसे हों, वह भी नहीं लिखी जाती। इसलिए धीरे-धीरे बदलते UI की एंट्री तभी
रिपेयर होती है जब कोई कंट्रोल मिलना बंद हो जाए। फ़ाइल तब बदलती है जब:

- कोई स्टेप पहली बार रिकॉर्ड हो, या हैंड-ऑफ़ के बाद रिकॉर्ड हो,
- कोई स्टेप रीप्ले के बाद फ़ेल हो, ऐसे `end-mismatch` पर ख़त्म हो जिसे एजेंट को
  रिपेयर करना पड़ा, पास तो हो पर रिकॉर्ड करने को कुछ न हो, या अटेम्प्ट ख़त्म होने
  तक कन्फ़र्म न हो (इन सब में एंट्री डिलीट हो जाती है),
- `e2e` का कोई अपग्रेड एंट्री मैच करने का तरीका बदल दे। तब हर एंट्री को नई key
  मिलती है, और अगला रन उन्हें फिर से रिकॉर्ड करता है।

## पुरानी पड़ चुकी रिकॉर्डिंग पर फ़ेल करें

डिफ़ॉल्ट रूप से, कमिट की गई रिकॉर्डिंग रीप्ले होना बंद कर दे, तो भी कुछ फ़ेल नहीं
होता। एजेंट वह स्टेप संभाल लेता है, और जब तक कोई उसे दोबारा रिकॉर्ड न करे, हर CI
रन मॉडल कॉल का खर्च उठाता है। `--strict-cache` (या `cache: { strict: true }`)
के साथ स्टेप `REPLAY_STALE` के साथ फ़ेल होता है, और कोई मॉडल कॉल नहीं होती:

<CodeGroup>
```bash npm
CI=1 npx e2e run --strict-cache
```

```bash pnpm
CI=1 pnpm exec e2e run --strict-cache
```

```bash bun
CI=1 bunx e2e run --strict-cache
```
</CodeGroup>

`REPLAY_STALE` एग्ज़िट कोड 2 देता है, और इसका रीट्राई नहीं होता।

| स्ट्रिक्ट मोड में फ़ेल होता है | फिर भी लाइव चलता है |
| --- | --- |
| `invalid-entry`, `wrong-context`, `target-not-found`, `target-ambiguous`, `viewport-changed`, `action-failed`, `action-uncertain`, `end-mismatch`: ऐप या एंट्री बदल गई | ऐसा स्टेप जो कभी रिकॉर्ड नहीं हुआ (नया या बदला हुआ निर्देश या पैरामीटर) |
| `no-entry`, जब कैश डायरेक्टरी में उसी स्टेप की रिकॉर्डिंग किसी दूसरी key से रखी हो | `gap` या `truncated` रिकॉर्डिंग |
| | ऐसा स्टेप जिसका स्टोर से पढ़ना फ़ेल हो जाए |
| | ऐसा स्टेप जिसके टेस्ट का `report.json` वाला `testId`, टारगेट का नाम या एजेंट का नाम 300 कैरेक्टर से लंबा हो, जब `e2e` के किसी पुराने वर्ज़न ने उसे दूसरी key से रिकॉर्ड किया था और तब से इस वर्ज़न के किसी `read-write` रन ने उसे रीप्ले नहीं किया |

दूसरी key वाली रिकॉर्डिंग तब बनती है जब `e2e` का कोई अपग्रेड key बदल दे, या
प्रोजेक्ट id, ऐप की पहचान या एजेंट का कॉन्टेक्स्ट बदले। मैसेज में उस फ़ाइल का नाम
होता है। अगर रिकॉर्डिंग मौजूदा वर्ज़न से बनी है, तो मैसेज यह भी बताता है कि क्या
बदला। जब कोई भी उस फ़ाइल को रीप्ले न करे, तो उसे डिलीट कर दें। यह जाँच कस्टम
`cache.store` पर लागू नहीं होती।

स्ट्रिक्ट रन कोई एंट्री न लिखता है, न डिलीट करता है, `read-write` मोड में भी
नहीं। इसलिए नया स्टेप सिर्फ़ ऐसे रन में रिकॉर्ड होता है जिसमें स्ट्रिक्ट बंद हो।
कॉन्फ़िग में `cache.strict` रखने से बेहतर है कि CI में `--strict-cache` इस्तेमाल
करें। पुरानी पड़ चुकी एंट्री ठीक करने के लिए:

1. टेस्ट को फ़्लैग के बिना `read-write` मोड में चलाएँ। अगर कॉन्फ़िग में
   `cache.strict` सेट है, तो उसे बंद कर दें।
2. बदली हुई एंट्री कमिट करें। कस्टम `cache.store` को कमिट की ज़रूरत नहीं, उसे नई
   एंट्री उसी रन से मिल जाती है।

## कैश देखें

<CodeGroup>
```bash npm
npx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
npx e2e cache stats   # entry count and size
npx e2e cache clear   # delete every entry
```

```bash pnpm
pnpm exec e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
pnpm exec e2e cache stats   # entry count and size
pnpm exec e2e cache clear   # delete every entry
```

```bash bun
bunx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
bunx e2e cache stats   # entry count and size
bunx e2e cache clear   # delete every entry
```
</CodeGroup>

<Note>
AI यूसेज में दिखने वाला `cached` प्रतिशत प्रोवाइडर का प्रॉम्प्ट कैश है। इससे मॉडल
कॉल सस्ती पड़ती है। रीप्ले कैश तो कॉल को ही छोड़ देता है।
</Note>
