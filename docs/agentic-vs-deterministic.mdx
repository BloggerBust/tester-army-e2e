---
title: Agentic or deterministic
description: Choose agentic or deterministic actions and assertions for your end-to-end tests.
---

Agentic testing lets you describe what a user wants to do and what the screen
should show in natural language. The agent picks the actions and checks the
outcome, so you don't spend time maintaining selectors when the UI changes.

Deterministic testing spells out every interaction and assertion in code.
Both test user outcomes, and e2e lets you mix them freely in the same test.

## When to use agentic tests?

Use agentic tests when UI changes keep forcing you to update selectors
in your tests. They also suit flows that take many interactions but are
easy to describe in plain English, such as filling out and submitting a form.

`agent.act` lets you describe a user intention, such as applying a
discount code. The agent figures out which controls to use and what to do.
`agent.assert` checks whether the screen shows the result you describe,
such as a discount applied to the total.

For example, inside a test with the `app` and `agent` fixtures:

```ts
await app.open('/checkout');
await agent.act('apply the discount code SUMMER');
await agent.assert('the checkout shows code SUMMER applied with a 10% discount');
```

You don't need to name the discount field, the button that applies it,
or the element that shows the result.

Tests tied to CSS classes or test IDs need edits when those identifiers
change. Move a button or redesign a form, and the agent can still carry
out the user's intention using what's on screen.

Agentic tests enable monitoring with real data on staging or production
without seeding deterministic data, because agents adapt to your app.
Use a test account there: the model sees what's on screen. See
[Security](/security).

For a complex flow, describe the steps toward one outcome in plain
English. See [Goals](/core-concepts#goals) for when to split the flow
into calls and wait for an intermediate state.

## When to use agentic assertions?

Agentic assertions are useful when several wordings or layouts would
satisfy the same requirement. For example, a validation message can
explain what's wrong without matching one exact sentence:

```ts
await agent.assert('the error message explains that an email address is required');
```

For a visual check, add `vision: true` so the model also sees a screenshot:

```ts
await agent.assert('the chart trends upward', { vision: true });
```

`agent.assert` checks the current screen and fails if the statement is
false or the evidence is insufficient. Use `agent.waitFor` when the UI
still needs time to reach the expected state. See
[Assertions](/core-concepts#assertions) for both methods.

## When to use deterministic tests?

Use locators for low-level mechanics that are themselves under test (such as
an empty submission, a keyboard shortcut, or a drag offset), sign-in setup
tests, or projects that run without a model. You specify each field and button
in code, as in this discount test:

```ts
await app.open('/checkout');
await screen.getByLabel('Discount code').fill('SUMMER');
await screen.getByRole('button', 'Apply').tap();
await expect(screen.getByRole('status')).toHaveText('10% off');
```

These actions and checks make no model calls. Prefer roles and labels so
the test refers to controls the user recognizes. Deterministic tests don't
have to depend on CSS classes or test IDs.

Use deterministic assertions when you can express the expected result
as an exact value, count, or state. They check it without model judgment.
If a validation message must use specific wording, check that text with
`expect`.

## Combine agentic with deterministic tests

Choose actions and assertions independently. You can let the agent find
its way through a changing UI, then check an exact value with `expect`:

```ts
await agent.act('apply the discount code SUMMER');
await expect(screen.getByRole('status')).toHaveText('10% off');
```

You can also use locators to fill and submit a form, then use
`agent.assert` to check whether its validation message explains the problem.

Adaptation follows the goal you write. A vague instruction can allow a
result you didn't intend. If a specific path matters, name it in the goal
or use locators for those actions. An `expect` after `agent.act` catches
a goal that passed the wrong way.

Model calls add latency, cost, and occasional mistakes. The
[replay cache](/cache) solves most of that by replaying recorded `agent.act`
actions with zero model calls, while assertions always run live. When the UI
changes and a recording no longer matches, the agent steps in to adapt unless
you enable strict cache mode. See [Self-healing tests](/self-healing).
